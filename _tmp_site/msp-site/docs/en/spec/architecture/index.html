架构 — Architecture

协议修订 2026-10-10 ｜ 状态 ✅ 已实现（QUIC / DHT 扩展点为 🔵 规划中）

本页定义 MSP 的整体形状：分层与层间契约、四个核心概念、三个正交扩展轴、角色与 Preset、能力协商、连接策略与启动时序、Peer 视图与扩展钩子。它对应 MCP 规范的 Architecture 页——先讲清部件与边界，再进入报文细节。

1. 概述​

MSP 的架构由一句话决定：把「交流方式」从协议核心里赶出去，做成可插拔的模式。

由此产生五层结构，以及四条窄到只有一个数据结构的层间契约：

┌─────────────────────────────────────────────────────────────────┐
│ 应用层      MSPNode                                             │
│   @node.tool · @node.signal_source · @node.on · node.publish    │
│   node.call · node.ensure_connected · node.register_pattern     │
└────────────────────────────┬────────────────────────────────────┘
                             ▼
┌─────────────────────────────────────────────────────────────────┐
│ 模式层      PatternHandler（pattern_id / fallback_to /          │
│             conflicts_with / on_signal / install_api）          │
│   Request-Reply · PubSub · MultiRound · Task                    │
│   Streaming · CallbackPush · AsyncPolling         （🔵 规划中）  │
└────────────────────────────┬────────────────────────────────────┘
                             ▼
┌─────────────────────────────────────────────────────────────────┐
│ 协议层      MSPProtocol                                         │
│   核心信号 HELLO·ACK·PING·PONG·ERROR                            │

│   Discovery：DirectoryScan · ManualConnect ·（🔵）DHT            │
│   Presence ：DirectoryWrite · ManualAdvertise ·（🔵）DHT         │

层间契约​

边界契约效果
发现 → 传输只传 Endpoint换发现机制不改传输
传输 → 协议只传 bytes加传输后端不改协议
协议 → 模式只传 Signal + 按 pattern 路由加通讯模式不改协议
模式 → 应用通过 install_api(node) 注入语法糖加模式不改 MSPNode

这四条契约是 MSP「每层皆可扩展」的全部机制。 每一层都只依赖下层的一个数据结构，不认识下层的实现细节。

各层不得做的事​

层不得
传输层解析报文内容、理解 type／pattern、做重连或去重
协议层理解任何具体模式的语义、认识工具名或路径含义、内置 TLS／认证／授权逻辑
模式层绕过协议层直接收发字节、修改 Signal 信封字段语义
发现层建立连接、假设对端一定可达（发现只产出候选端点）

协议层不认识工具、路径、任务，只认识 Signal 与 pattern —— 这是「协议核心极小」能够成立的原因，也是第三方实现只需理解 base-protocol.md 与 patterns.md §3 即可互通的原因。

2. 四个核心概念​

概念定义规范出处
节点 Node通讯参与方，具有全局唯一 node_id。不预设客户端／服务端角色——一个节点可以同时发布、订阅、提供工具、调用工具§5
信号 Signal通讯的最小数据原子。所有交互的统一载体，仅以 type 区分base-protocol.md §2
端点 Endpoint节点的传输身份 {transport_type, address, node_id}。发现层产出它，传输层据它建连discovery.md
路径 Path信号的逻辑地址，点号分段（notify.web.download），支持 * / ** 通配publish-subscribe.md

三条设计原则是这四个概念的直接推论，也是本规范的解读框架：

Everything is a node. 工具、模型、传感器、宿主程序、远端服务，都是节点，地位对等。 Everything is a signal. 握手、订阅、工具调用、任务、心跳，都是信号，只有 type 不同。 Every layer is extensible. 发现、宣告、传输、模式，每一层都可插拔，不触碰核心。

3. 三个正交扩展轴​

「扩展」在 MSP 里是三件互不相关的事，各自独立——换一种发现机制不改协议层，加一种传输后端不改协议层，加一种通讯模式同样不改协议层：

轴扩展单位接入方式参考实现代价
发现 / 宣告一个 Discovery / Presence 实现注册进 DISCOVERY_REGISTRY / PRESENCE_REGISTRY，在 Preset 里点名0 行核心改动
传输一个 Transport 实现注册进 TRANSPORT_REGISTRY，在 Preset 里点名0 行核心改动
模式一个 PatternHandler 实现注册进 PATTERN_REGISTRY，在 Preset 里点名；协议层按 pattern 查表路由0 行核心改动

「核心改动 ≤ 60 行」是这套架构的验收标准。 参考实现中，让模式层得以零改动扩展的全部代价，是协议层里的一次查表（patterns.md §3）；让任意层都能注入语法糖的全部代价，是 _install_layer_api 的约 4 行（§11）。

新增一种通讯模式不需要修订本规范的核心页：模式是可选扩展，只需在 patterns.md §7 登记，并说明与他者的映射关系。

4. 发现与宣告：两个正交接口​

发现与宣告是两个方向相反、彼此独立的接口，不得被合并成一个「节点管理」抽象：

接口回答的问题产物 / 输入
Discovery「我怎么找到别人」产出 Endpoint
Presence「别人怎么找到我」消费 Endpoint，写进某个共享通道
class Discovery(ABC):
    def list_endpoints(self) -> list[Endpoint]: ...        # 初始全量扫描
    def watch(self, on_add, on_remove) -> None: ...        # 动态产出端点

class Presence(ABC):
    def announce(self, endpoint: Endpoint) -> None: ...     # 宣告自己
    def withdraw(self, node_id: str) -> None: ...           # 撤销宣告
    def update(self, endpoint: Endpoint) -> None: ...       # 更新端点

正交的含义：一个节点可以只发现不宣告（观察者）、只宣告不发现（纯服务方）、或两者都做（完全对等）。这四种组合直接对应 §5 的预设表。

两层的统一契约是 Endpoint：transport_type 决定用哪个传输后端，address 的具体结构随后端变化（transports.md），node_id 在手动发现时可以为空（尚未知对端身份）。

发现只产出候选，不保证可达。 一个端点出现在共享目录里不意味着对端在监听、不意味着握手会成功。可达性是连接时才知道的事实。因此发现层不得触发任何阻塞行为，拨号必须异步（§8）。

详细条文（共享目录声明文件格式、事件 + 轮询双机制、租约 TTL、HTTP 注册表、DHT）见 discovery.md。

5. 角色与 Preset​

5.1 角色是组合，不是硬编码​

一个节点启用哪些发现、宣告、传输与模式，取决于它的角色。MSP 用 Preset 声明这四类资源：

字段含义
discovery启用哪些发现机制
presence启用哪些宣告机制
transports启用哪些传输后端
patterns启用哪些通讯模式
primary_transport对外宣告哪个后端（决定 Endpoint.transport_type）
capabilities角色能力位（pub / sub / req / rep）
connect_policy发现时的连接策略：eager（发现即连）/ lazy（只接受，按需拨号）

角色不是协议机制。 经典协议里的「客户端／服务端」在 MSP 里只是上表在不同维度上的取值组合：

经典角色在 MSP 里是
MCP 服务端宣告工具、不发现对端，仅启用 msp/request-reply（≈ CLOUD_SERVICE）
MCP 客户端发现工具节点、不宣告工具，仅启用 msp/request-reply
A2A 智能体既发现又宣告、既提供也调用工具，启用 msp/multi-round / msp/task（≈ FULL_PEER）

MCP 的 client／server 是不对称的组合（一端只服务、一端只调用），A2A 的 agent 是对称的组合。MSP 不预设任何一端，把取值权留给节点本身——因此一个 MSP 节点可以同时扮演 MCP 服务端、MCP 客户端与 A2A 智能体，而在角色固化的协议里这需要分别维护三个组件。

规范条文：

  1. 未指定预设时，节点必须使用 FULL_PEER。
  2. primary_transport 必须在 transports 中；否则节点启动必须失败并报错，不得静默降级到其它后端。
  3. Preset 中列出的名称必须已在对应注册表中注册；未注册即启动失败。
  4. 预设可以被覆盖：在同一节点上可以运行时追加（见 §5.3）。
  5. LOCAL_AI_UDS 仅在支持 AF_UNIX 的平台可用（transports.md）。

规范条文：register_pattern 必须是幂等的（重复声明不产生副作用）；节点运行中调用时必须立即推送清单（base-protocol.md §4.4）。

6. 能力协商​

6.1 握手即协商​

能力清单（Manifest）在握手时交换，因此双方在建连前就知道彼此支持哪些通讯模式、提供哪些工具、会发布哪些路径：

   node_a                                         node_b
     │  ── hello {manifest: {patterns: [...],      │
     │            tools: [...], signals: [...]}} ─► │
     │                                             │  比对 patterns：
     │                                             │  · 交集 = 可用的交流方式
     │                                             │  · 缺失 = 需要降级或放弃
     │  ◄──────── ack {manifest: {...}} ────────── │
     │  同样比对                                    │
     ▼                                             ▼

这比「先连接、再试探」更高效，也为模式降级（fallback_to）提供了信息基础：调用方在发出请求前就能判断「对方是否支持 msp/multi-round」，而不必发出去等一个失败。

规范条文：

  1. 双方必须在握手报文中携带完整的能力清单（不是增量）。
  2. 清单必须包含该节点已启用的全部模式 ID（patterns）。
  3. 节点不得在未宣告某模式的情况下使用该模式的信号类型。收到此类信号时按宽容读取处理（base-protocol.md §2.3）。
  4. 清单可以包含尚未实现的能力声明——但这会使对端「看到许诺但用不了」。实现应当只宣告自己真正实现的能力（capabilities.md §现状对当前实现正是此状态）。

6.2 能力位与授权是两回事​

存放位置语义可交换
能力位 pub / sub / req / repManifest.capabilities「我自称会什么」✅ 随清单交换
授权 grants本地 Preset「我允许你做什么」❌ 不得交换

授权绝不依赖对端自报。 一个节点宣称自己有 req 能力，不意味着别人必须接受它的调用。详见 security.md §授权。

6.3 模式元数据​

Manifest.pattern_metadata 允许模式挂载自己定义的元数据（键为 pattern_id）：

"patternMetadata": {
  "msp/task": { "name": "...", "skills": [ ... ] }
}

规范条文：Manifest 核心不感知、不校验该字段的内容，原样随清单交换。格式由各模式自己定义（msp/task 用它承载 A2A 的 Agent Card 投影，见 task.md）。

7. Peer：邻居的只读视图​

一个邻居的信息天然散落在多处：Endpoint 在节点层，Connection 与能力清单在协议层。Peer 把它们聚合为一个对象。

Peer 是视图而非存储：不持有任何状态，每次属性访问都从所属节点实时读取。对端更新清单或断开后，同一个 Peer 对象立即反映最新状态——没有副本要同步。因此 Peer 对象可以随意创建和丢弃。

成员类型未发现 / 未连接时
endpointEndpoint | NoneNone
manifestdict | None（浅拷贝）None
connectionConnection | NoneNone
is_discoveredboolFalse
is_connectedboolFalse
tools() / signals() / patterns()list[]
supports(pattern_id)boolFalse
has_tool(name) / has_signal(path)boolFalse

规范条文：

  1. 只查询，不操作。 call 仍放在节点上；publish 是广播、不面向单个对端，故不属于 Peer。
  2. 宽容未知对端。 查询未知 peer_id 必须返回 None / [] / False，不得抛异常。
  3. manifest 必须返回副本，修改返回值不得污染节点内部状态。
  4. 视图的枚举 API：node.peers()（全部已知邻居，含未连接）、node.connected_peers()（仅已连接），均按 node_id 排序。

8. 连接策略与 settle​

8.1 connect_policy​

策略发现时的行为连接时机
eager发现即异步拨号发现时
lazy只记入邻居表首次 call() / fetch_manifest() 时（ensure_connected）

两种策略都必须保证同一件事：任何需要连接的用户 API 必须在内部调用 ensure_connected(peer_id) 兜底，使「邻居已知但未连接」不会变成调用方的负担。

并发建连必须去重：每个对端一把连接锁，避免多个线程同时触发重复拨号（重复连接会被对端去重，但代价是一次无谓的握手与冷却记录，见 base-protocol.md §4.3）。

8.2 对等端故障：错误即值、软冷却、不删邻居​

对端随时可能不可达（崩溃、重启、断网）。「对端没了」是常态，不是异常：

机制解决什么规定
错误即值对端没了不该打断调用方程序call() 对不可达／未知／超时／中途断连一律返回 ToolResult(error=...)，不得抛异常
疑似死亡 = 软冷却区分「暂时连不上」与「真死了」连接失败记 now + connect_backoff，冷却期内快速失败不再重拨；成功即清除
不删邻居硬删会让只是暂时失败的对端永久消失连接失败不得从邻居表移除该对端
目录租约 + TTL = 硬清理自动清理真正死掉的节点宣告方周期续租，发现方丢弃过期声明（discovery.md）

软标记与硬清理分离：连接失败是「疑似」，声明过期才是「确认」，两个时间尺度互不干扰。这是 MSP 处理对端故障的核心取舍，任何实现都应当保持这一分离，否则会退化成「一次网络抖动就永久失去一个对端」。

8.3 启动时序与 settle​

问题：start() 里各层的时序是混的——传输监听是同步的，宣告是同步的，发现也是同步的（watch() 先跑一次全量扫描），但 eager 的拨号在后台线程里。于是 start() 返回时的状态是「邻居已知、连接未必在」：

  • 紧接着 publish() 会扇出到空的连接集合——广播模型下这既不是异常也不是错误码，而是静默丢失；
  • 紧接着 call() 靠 ensure_connected() 现场兜底（能连上，但把首次调用的延迟推给调用方）。

对使用者来说，这意味着「start() 之后要不要再 sleep 一下」变成了必须靠经验回答的问题。测试里遍地 wait_until(lambda: "a" in node.connections()) 就是这个问题的外部症状。

决策：start(settle=True, settle_timeout=0.5) —— 启动完成后等一次「发现驱动的在建拨号全部落地（成功或失败）」，返回是否在超时前稳定；另提供独立的 node.settle(timeout)。

node.start()                          # settle=True 默认：返回时发现驱动的拨号已落地
ok = node.start(settle_timeout=1.0)   # 自定义上界；False 表示仍有拨号在飞
node.start(settle=False)              # 纯非阻塞：连接在后台形成
node.settle(0.5)                      # 或单独等待；返回是否在超时前稳定

三条性质是刻意的：

  1. 默认开启：成功路径上拨号通常几十毫秒落地，settle 立即返回，几乎无额外成本；只有连不上的对端才会耗尽超时。默认关等于把这个坑留给每个调用方。
  2. 只等待，不发起：settle() 从不调用 ensure_connected()。它等的只是「已经有人在做」的连接。因此 connect_policy="lazy" 下它是 no-op（没有在建拨号，立即返回 True），绝不会把 lazy 节点变成 eager——settle 与 connect_policy 正交。
  3. 登记先于起线程：发现回调必须在起拨号线程之前同步把该对端计入「在建」集合，线程在 finally 里注销并唤醒。若反过来在拨号线程内部登记，settle 可能赶在拨号线程被调度之前看到空集合，把「还没开始」误判成「已经稳定」——默认开启的保证就成了假的。

边界（诚实版本）：

  • 只覆盖发现驱动的拨号：call() / fetch_manifest() / msp/task 自己发起的建连不在计数内。
  • 不承诺「连上所有未来节点」：start() 返回之后才 announce 的节点走正常发现路径。
  • 超时是上界不是错误：False 只表示仍有拨号在飞，节点照常可用。
  • 不做「至少连上 N 个」：这类要求会把「对端未就绪」升级成启动失败，与「错误即值」的容错取向冲突。需要强保证时，使用方应当在 settle 之后自行检查 connections()。

9. 启动与停止顺序​

start() 必须按以下顺序执行（顺序本身是契约的一部分）：

  1. 传输层 listen_all()            所有后端开始监听
  2. 确定对外端点                    primary_transport → Endpoint
  3. 写入 manifest                   合并 Preset 的模式与能力位 → push_manifest
  4. 宣告层 announce(endpoint)       别人现在可以发现我了
  5. 发现层 watch(on_add, on_remove) 同步跑一次全量扫描 → 邻居入表
  6. 各传输后端启动 accept 循环
  7. 启动全部 signal_source 生成器线程
  8. settle（默认 0.5 s）

第 3 步必须先于第 4 步：能力清单在握手时交换，而握手由对方发起——若宣告先于清单就绪，一个反应快的对端可能在清单写入前拨进来，双方就会交换到一份不完整的能力清单。

stop() 必须逆序执行：撤销宣告 → 停止发现 → 关闭协议层（关闭全部连接、唤醒全部在途请求）→ 关闭传输层。未启动的节点调用 stop() 不得报错（构造期已启动的心跳线程仍需停止）。

11. 扩展钩子 install_api​

问题：想要「运行时动态添加发现源」这类语法糖，又不愿为核心加一行改动。

决策：任意层组件可以定义 install_api(node)；MSPNode 在构造完组件后调用它（若存在），组件即可往 node 上挂便捷方法，而不改核心：

node.start()
node.add_manual_source("http://registry2:8080/nodes")  # 运行时动态加发现源
  • 通讯模式用它挂 node.multiround、node.task；
  • 手动发现用它挂 node.add_manual_source(...)。

约定（PatternHandler.install_api 的契约，同样适用于 discovery / presence）：

  1. 保存 self._node = node 作为反引用，供自身公开方法内部使用，避免用户手动传 protocol / node_id；
  2. 挂到 node 上的短名必须唯一，不得与核心 API 冲突；
  3. install_api 不应当做重活（不建立连接、不启动线程）。

代价：核心约 4 行（_install_layer_api）。「核心零改动」与「语法糖」不可兼得时，选少量核心改动换取任意层注入 API 的能力。

12. 规范条文汇总​

必须（MUST）：

  1. 层间必须只通过四条契约传递数据（Endpoint / bytes / Signal+pattern / install_api）。
  2. 传输层不得解析报文内容；协议层不得理解具体模式语义。
  3. Discovery 与 Presence 必须保持为两个独立接口。
  4. 未指定 Preset 时必须使用 FULL_PEER；primary_transport 必须属于 transports，否则启动失败。
  5. 双方必须在握手中交换完整能力清单，包含全部已启用模式 ID。
  6. 节点不得在未宣告某模式的情况下使用该模式的信号类型。
  7. 授权不得随清单交换，不得依赖对端自报。
  8. 任何需要连接的用户 API 必须内部调用 ensure_connected() 兜底。
  9. 同一对端的并发建连必须被去重（每对端一把锁）。
  10. call() 不得因对端不可达／超时／断开而抛异常，必须返回错误值。
  11. 连接失败不得从邻居表移除对端；只有声明过期才清理。
  12. start() 必须按 §9 的顺序执行，清单写入先于宣告。
  13. settle() 不得发起连接；connect_policy="lazy" 下必须是 no-op。
  14. 「在建拨号」必须在起线程之前登记。
  15. Peer 必须是纯查询视图，未知对端返回空值而非抛异常。

应当（SHOULD）：

  1. 实现应当只宣告自己真正实现的能力。
  2. 新扩展应当只改注册表与 Preset，不改核心。
  3. 需要强连接保证时，使用方应当在 settle 之后自行检查 connections()。

13. 已知缺口​

#缺口后果
1无「网络就绪」的完整承诺settle 只覆盖发现驱动的拨号；call / fetch_manifest / msp/task 发起的建连不计入
2lazy 节点不参与 settle在 lazy 节点上 settle() 恒为 True，不能用作「已连上对端」的判据
3发现 on_remove 只删邻居表，不断开连接对端撤下宣告后，已建立的连接靠心跳失联才断开（最长 heartbeat_timeout）
4无中央注册表的一致性保证多注册表源并存时，同一 node_id 的不同端点可以同时存在于邻居表（后到者覆盖，见 _on_endpoint）
5能力清单无「未实现」标记见 §6.1 第 4 条：对端会看到许诺但用不了的条目
6无拓扑感知广播扇出不做带宽优化，N 个对端即 N 次发送（这是刻意的取舍，不是缺陷；见 publish-subscribe.md §安全考量）
7无节点身份持久化node_id 由使用方自行保证唯一；协议不提供分配或冲突检测
