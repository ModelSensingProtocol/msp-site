MSP 规范 — Model Sensing Protocol Specification

协议修订2026-10-10
对应实现msp-py 0.1.0（Alpha）
文档状态草案 — 覆盖全部已实现层，并完整定义规划中的能力（逐条标注状态）
规范性用语RFC 2119（见 规范性用语）

Everything is a node. Everything is a signal. Every layer is extensible.

本目录是 MSP 的规范（normative）：它定义互操作所要求的行为——双方各自独立实现，按本规范实现即可互通。

规范之外还有两类文档，分工如下：

文档回答什么性质
本目录（docs/spec/）「实现必须做什么才能互通」规范性
设计文档「为什么这样设计、放弃了什么」说明性
技术白皮书「它解决什么问题、与 MCP/A2A 的关系」说明性
README「怎么用」教程性
src/msp/参考实现本身事实来源

规范与实现的冲突处理：当条文与参考实现不一致时，以本规范为准并记为缺陷；参考实现是规范的第一个实现，不是规范本身。

1. 修订历史​

MSP 的协议修订号沿用 ISO 日期（YYYY-MM-DD），与 MCP 的修订策略一致：修订号标识一组互操作的报文契约，而不是某次代码发布。

修订日期变更
2026-10-102026-10-10首个规范草案。冻结 Signal 信封、核心信号类型、握手与去重规则、错误码、模式路由契约、Endpoint 与声明文件格式、路径匹配算法、msp/task 与 msp/multi-round 报文；完整定义规划中的能力面、安全模型与 QUIC / DHT 扩展点。

版本化策略​

  1. 修订号变更必须伴随修订历史新增一行；不带日期的改动只能落在说明性文字上。
  2. 向后兼容的增补（新增可选字段、新增模式 ID、新增信号类型）在同一修订内以「追加」形式给出，接收方应当忽略未知字段与未知信号类型所要求的语义（见 宽容读取）。
  3. 不兼容变更（改字段语义、改匹配算法、改握手次序）必须发新修订号，且必须在修订历史中标注影响面。
  4. 模式 ID 命名空间：msp/ 前缀由本规范保留；第三方模式必须使用自有前缀（如 acme/streaming），不得占用 msp/。

2. 规范性用语​

本规范中的关键词按 RFC 2119 解释。中文条文使用下表左列，等价于右列的英文关键词；引用实现时两者可互换。

中文英文含义
必须MUST绝对要求。不满足即不符合本规范
不得MUST NOT绝对禁止
应当SHOULD除非有正当理由，否则需遵守；偏离时应当能说明理由
不应当SHOULD NOT除非有正当理由，否则需避免
可以MAY可选，实现可自由取舍

正文中加粗的关键词承担规范效力；未加粗的同类词（如「需要」「建议」）是叙述，不构成要求。

状态标注：每一页与每一节都带一个状态标记，读者据此判断条文能否在当前实现上验证。

标记含义
✅ 已实现参考实现已落地，条文可直接验证
🟡 部分实现已落地主路径，存在条文列明的已知缺口
🔵 规划中条文已完整定义，参考实现尚未落地；实现者可以不实现，但一旦实现必须符合条文

5. 规范常量速查​

以下常量在所有页面中含义一致，各页不再重复定义。它们是互操作契约的一部分，不得随意改动。

5.1 核心信号类型（Signal.type）​

核心信号类型共 9 个（下表 8 行，因 ping 与 pong 合为一行）。ping / pong 的 payload 为 {}；其余类型的载荷字段以各页定义为准。

type方向有 reqid语义页
hello发起方 → 接受方否握手请求，payload.manifest 携带能力清单base-protocol
ack接受方 → 发起方否握手应答，payload.manifest 携带能力清单同上
signal任意 → 全部已连对端否发布一条数据信号，path + payloadpublish-subscribe
tool_call调用方 → 被调方是工具调用请求，payload.tool / payload.argsrequest-reply
tool_result被调方 → 调用方是工具调用结果，payload.content / structuredContent / error同上
manifest_update任意 → 全部已连对端否能力清单推送，payload.manifest 携带完整清单（非增量）base-protocol
ping / pong双向否心跳探活base-protocol
error任意视情况错误通告，payload.code / payload.messagebase-protocol

🔵 规划中的核心信号类型（条文见 base-protocol.md §6.3–6.4）：

type分类有 reqid语义
cancel请求是请求取消某次在途调用。协作式：不保证对端真的停下，也不免除对端的应答义务
progress通知是进度上报，按调用方给出的 progressToken 关联；不得被当作可靠传输

模式可定义模式私有信号类型（如 input_required、task_submit）。它们与核心类型共用同一个 type 字段空间，但必须同时携带 pattern 字段以便路由；msp/ 命名空间外的模式必须为自己的类型加前缀，避免跨模式撞名。

5.2 模式 ID​

pattern_id状态说明
msp/request-reply✅ 核心call() / tool_call / tool_result
msp/publish-subscribe✅ 核心publish() / signal + 接收方本地过滤
msp/multi-round✅ 扩展执行中追问
msp/task✅ 扩展任务状态机 + 产物
msp/streaming🔵 规划stream_start / stream_chunk / stream_end
msp/callback-push🔵 规划长任务回调式回传
msp/async-polling🔵 规划显式轮询语义（互操作兜底）

msp/request-reply 与 msp/publish-subscribe 是核心模式：直接实现在协议层，因为信号路由、reqid 关联与广播扇出依赖协议层状态。其余为可扩展模式：一个独立文件 + 一个注册表条目，不改协议核心。

5.3 命名规范​

对象分隔符格式示例
node_id无[a-z0-9_-]+file_monitor
Signal path.segment(.segment)*notify.web.download
Pattern ID/[namespace/]namemsp/multi-round
Tool name无[a-z0-9_-]+get_weather
Task ID无实现自定task-3f2a…

路径分层遵循「域优先」：<域>.<实体>.<动作>，域在最前（notify.web.download，而非 web.notify.download）。域是稳定、面向功能的分类；实体是可变、面向实现的来源。域放最前，接收方用 notify.** 即可一劳永逸地捕获全部现有与未来通知。

Pattern ID 使用斜杠是全局命名空间需要（反向域名前缀），与 Signal path 的点号分层是两个不同概念，不得混用。

5.4 错误码​

错误码取 JSON-RPC 2.0 的约定值，使工具调用子集在语义上可直接映射（见 interop）。

code名称本规范中的用途参考实现现状
-32600无效请求收到未知 type 时回 error✅ 核心发出（_dispatch_core 兜底分支，码为字面量）
-32601方法不存在工具调用指向未注册工具🟡 核心未发出：错误以字符串进 tool_result.payload.error（未知工具: X），不带 code；该码目前只出现在 msp.mcp 的 JSON-RPC 桥中
-32602参数无效参数不满足工具声明的 inputSchema🟡 核心未发出：核心不做运行时 schema 校验，参数不符表现为 TypeError → payload.error
-32603内部错误工具执行中抛出异常🟡 核心未发出：异常文本原样进 payload.error，不带 code
-32000 ~ -32099实现自定义授权拒绝已用 -32000（见 security）；仅当信号带 reqid 时回错，广播类静默丢弃；模式层尚未使用✅ 已实现（-32000）

工具执行失败不在 tool_result 内携带 code：它走「错误即值」通道（request-reply §6.3）。因此实现方不得期待在 payload 中读到 code；把 payload.error 字符串映射回错误码是适配层（如 JSON-RPC 桥）的职责。

5.5 角色能力位​

能力位含义交换方式
pub本节点会发布信号Manifest.capabilities
sub本节点会订阅信号同上
req本节点会调用他人工具同上
rep本节点会应答他人调用同上

能力位是自述（「我自称会什么」），与授权（「我允许你做什么」）严格分离。授权不得依赖对端自报，也不得随清单交换（见 security）。

参数默认值说明

call 超时5.0 s未显式指定时
heartbeat_interval15.0 sPING 周期
heartbeat_timeout45.0 s超过此值未收到任何消息即判定失联

6. 与其他协议的关系​

关系结论页
MCPMCP ⊆ MSP：工具调用场景下 MCP 的行为可被行为保持地映射进 MSP；反之不成立interop
A2AA2A 是一个协议栈而非一种模式；MSP 只搬其「任务语义」，落地为 msp/taskpatterns/task
JSON-RPC 2.0编码层不采用其信封，但在工具调用子集上做语义对齐；互通靠可选桥，不改核心interop

7. 一致性​

一个实现声称「符合 MSP 修订 2026-10-10」，必须满足：

  1. 报文形态：能解析并生成 Signal 信封（base-protocol §2），含未知字段的宽容处理。
  2. 握手：实现 HELLO/ACK 交换与能力清单交换（base-protocol §4）。
  3. 核心模式：实现 msp/request-reply 与 msp/publish-subscribe 的全部条文。
  4. 路由：按 Signal.pattern 路由，未知模式不得导致连接中断（patterns §3）。
  5. 宽容读取：对未识别的字段、信号类型、内容块类型、模式 ID，不得视为协议错误而断开连接（base-protocol §2.3）。
  6. 可选的扩展：可扩展模式、传输后端、发现机制、能力面与安全机制均为可选；不实现是合规的，实现则必须符合对应条文。

互通的最低公分母是：一条 TCP 连接 + Signal 信封 + msp/request-reply。任何两个只满足这一点的实现都能互相调用工具。

8. 参与演进​

规范变更走「先改唯一权威源、再改散文、最后改实现」的顺序，并在 修订历史 留痕：

  1. 改 schema/<修订>/msp.yaml —— 数据模型的唯一权威源：字段名、类型、必填性、默认值、约束，以及 Signal.type（+pattern）→ payload 的绑定；
  2. 在对应页面提出条文（含状态标记）——散文负责解释「为什么这样设计」，不得再抄一份字段清单（那正是漂移的来源）；
  3. 重新生成 schema/<修订>/msp.schema.json（tools/gen_schema.py），并让 tools/check_schema_drift.py 的三方对账通过：权威源 ↔ 参考实现 ↔ 散文页；
  4. 更新参考实现与测试；
  5. 新增修订行，标注是追加还是破坏性变更。

为什么先改 YAML：字段只在 YAML 里定义一次，msp.schema.json、本目录各页的字段表与 tests/test_schema_source.py 都由它派生或与它对账。MCP 用同样的形态（schema.ts 为源、JSON Schema 与文档为产物），只换了个宿主语言。

新增通讯模式不需要修订本规范的核心页：模式是可选扩展，只需在 patterns.md 登记并在 interop 说明与他者的映射关系。
