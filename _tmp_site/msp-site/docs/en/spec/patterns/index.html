MSP 模式层（Pattern Layer）

协议修订2026-10-10
状态✅ 已实现（msp/streaming、msp/callback-push、msp/async-polling 为 🔵 规划中）
本页定义通讯模式的抽象契约（PatternHandler）、协议层到模式层的路由判定顺序、核心模式与可扩展模式的划分依据、降级与互斥语义、模式登记流程，以及三个规划中模式的完整报文定义

常量来源：信号类型、模式 ID、错误码、默认参数一律以 README.md 为准。本页不得引入索引之外的新常量；模式私有信号类型在正文中逐条声明。

1. 概述​

1.1 模式层的存在理由​

模式层把「一种交互的语义」做成可插拔单元，目的是让新增模式不修改协议核心。

协议核心知道的只有一件事：一个 Signal 从哪条连接来、type 是什么、pattern 是什么。它不知道「请求—响应要等回包」，也不知道「发布要扇出」。这些属于语义，属于模式。

把语义从核心剥离带来三条可验证的收益：

  1. 新增模式 = 新增一个文件 + 一条注册表条目。协议层的 _dispatch 判定顺序不需要任何改动（见 §3），因为路由键 Signal.pattern 早就在信封里。
  2. 模式之间互不感知。msp/task 不知道 msp/multi-round 存在；两者都用到 input_required / input_response 这两个同名信号类型，靠 pattern 字段区分归属，互不冲突。
  3. 模式可以失败而不拖垮连接。没有登记的模式处理不了自己的信号，但路由契约保证它会降级到协议层默认分发，而不是让连接断开（见 §3.4）。

1.2 在分层中的位置​

 用户 API 层     MSPNode（node.call / node.publish / node.on / node.tool …）
      │
 模式层          PatternHandler 实例（msp/multi-round、msp/task …）
      │  ▲            ▲
      │  └── protocol._send() ──┐
      ▼                         │
 协议层          MSPProtocol.patterns（路由表）· _dispatch（路由）
      ▼
 传输层          Connection.send / receive（只搬字节）

模式层位于协议层之上，但不拥有协议层：它通过 protocol.patterns 被登记，通过 protocol._send() 发包，通过 on_signal(protocol, peer_id, sig) 收包。

2. 契约：PatternHandler​

PatternHandler（src/msp/patterns/base.py）是一个抽象基类（abc.ABC）。所有可扩展模式的实现必须是它的子类。

2.1 类属性​

成员类型必需语义
pattern_idstr必须模式的唯一标识，与 Signal.pattern、Manifest.patterns 中的字符串逐字一致
fallback_tostr | None可以省略，缺省 None降级目标模式 ID（§6）
conflicts_withlist[str]可以省略，缺省 []与之互斥的模式 ID 列表（§4.3）

pattern_id 必须符合 README.md §5.3 的 Pattern ID 格式 [namespace/]name。使用 msp/ 前缀的模式必须由本规范定义；第三方模式必须使用自有前缀（例如 acme/streaming），不得占用 msp/。

参考实现示例（msp/multi-round）：

class MultiRoundHandler(PatternHandler):
    pattern_id = "msp/multi-round"
    fallback_to = "msp/request-reply"

2.2 抽象方法 on_signal​

@abstractmethod
def on_signal(self, protocol, peer_id: str, sig) -> None: ...
形参类型语义
protocolMSPProtocol协议层实例，供 Handler 调用 _send 等方法
peer_idstr发送该信号的对端 node_id
sigSignal完整信号对象

必须满足：

  1. on_signal 必须在协议层的读循环线程上被调用（路由是同步派发，不退避到工作线程）。因此它不得在其中执行长耗时操作。
  2. 需要执行长时间工作（工具调用、网络往返、等待对端回答）的 Handler，必须把工作移交给独立线程（threading.Thread(...).start()），理由见 §3.5。
  3. on_signal 的返回值为 None；模式的「响应」必须通过 protocol._send() 显式发出，不得依赖返回值回传。

2.3 可选方法 install_api​

def install_api(self, node) -> None:
    """向节点注入语法糖并保存节点反引用。默认什么都不做。"""
    pass

约定（源自 base.py 的文档字符串，并被 msp/multi-round、msp/task 遵循）：

  1. 应当保存 self._node = node，供自身公开方法内部使用，避免用户手动传 protocol / node_id。
  2. 可以在 node 上挂短名（如 node.multiround = self、node.streaming = self）。
  3. 短名必须唯一，且不得与 MSPNode 的核心 API 冲突。核心 API 至少包括：node_id、manifest、endpoint、preset、protocol、transport、discoveries、presences、start、stop、settle、publish、on、on_connected、on_disconnected、call、tool、signal、signal_source、declare_signal、register_pattern、pattern、ensure_connected、neighbors、connections、peer、peers、connected_peers、peer_manifest、fetch_manifest。
  4. 基类的默认实现是空操作，所以不注入语法糖的模式可以不覆写。

2.4 激活时机​

Handler 由注册表在激活时实例化，用户不应当手动构造（node.register_pattern 的文档字符串把「与 Preset 启动路径一致」列为理由）。激活过程见 §3.6。

3. 路由契约​

本节是模式层与协议层之间唯一的接口约定，必须与 MSPProtocol._dispatch 逐行对应。

3.1 三步判定顺序​

收到任何信号，协议层必须按以下顺序判定，且必须在前一步命中时立即返回、不再继续：

第 1 步 — 核心信号类型

若 sig.type ∈ {hello, ack, ping, pong, error}，必须交给协议层自处理（_dispatch_core），不得查模式表。

这一条意味着：即使一个 hello 信号携带了 pattern 字段，也不会被路由到任何 Handler。核心信号类型是模式层的禁区。

第 2 步 — 带 pattern 且已登记

否则，若 sig.pattern 非空且 sig.pattern 命中 protocol.patterns（即本节点已激活该模式的 Handler），必须调用该 Handler 的 on_signal(protocol, peer_id, sig)，然后返回。

protocol.patterns 是一个 dict[str, PatternHandler]，键为 pattern_id。

第 3 步 — 默认核心分发

否则（sig.pattern 为空，或 sig.pattern 非空但未登记），必须交给 _dispatch_core。未知 type 必须回 error，载荷 code = -32600、message = "未知信号类型: <type>"（_reply_error 会带上原信号的 reqid）。

3.2 判定流程图​

                      收到 Signal
                           │
        ┌──────────────────┴──────────────────┐
        │ type ∈ {hello, ack, ping, pong,     │ 是
        │         error} ?                    ├──────▶ _dispatch_core（协议层自处理）
        └──────────────────┬──────────────────┘
                           │ 否
        ┌──────────────────┴──────────────────┐
        │ pattern 非空 且 pattern 已登记 ?     │ 是
        └──────────────────┬──────────────────┘──────▶ handler.on_signal(protocol, peer_id, sig)
                           │ 否
                           ▼
                    _dispatch_core
                    ├─ signal          → _on_signal（本地回调过滤）
                    ├─ tool_call       → _on_tool_call（独立线程执行）
                    ├─ tool_result     → _on_tool_result（唤醒 reqid 等待者）
                    ├─ manifest_update → _on_manifest_update
                    ├─ ping            → 回 pong
                    ├─ pong            → 忽略（last_seen 已在读循环更新）
                    ├─ error           → _on_error（记日志）
                    └─ 其它 type       → 回 error(code=-32600)

3.3 路由键的写入方​

发信号的一方必须在构造信号时显式声明 pattern：

protocol._send(peer_id, Signal.make(
    type=self.TOOL_CALL,          # 模式私有信号类型
    source=self._node.node_id,
    target=peer_id,
    reqid=reqid,
    payload={"tool": tool, "args": args},
).with_pattern(self.pattern_id))  # ← 路由键

Signal.with_pattern(pattern) 就地设置 pattern 字段并返回 self，便于链式调用。

核心模式的信号不写 pattern：tool_call / tool_result 的 pattern 为 None（见 request-reply.md），signal 的 pattern 为 None（publish 不设置该字段，见 publish-subscribe.md）。它们因此稳定地走第 3 步。

3.4 未登记模式的行为（必须遵守）​

  1. 必须：未知 pattern 不得导致连接中断。第 2 步判定失败后必须继续走第 3 步。
  2. 必须：带未登记 pattern 的信号按第 3 步降级处理。若其 type 是已知核心类型，就按该类型处理（例如 type="tool_call" 且带未知 pattern 的信号会被当作普通工具调用执行）。
  3. 必须：未知 type 回 error(code=-32600)，message 形如 未知信号类型: <type>，且不得因此关闭连接。
  4. 应当：实现方对「收到未登记 pattern 的信号」记一条调试日志；参考实现当前没有记录，见 §10 的 G3。

注意第 3.4.2 条的一个后果：给 tool_call 加上一个未登记的 pattern，并不等于「拒绝对端」——它只是失去了模式层的特殊语义，仍会按核心语义执行。安全过滤不得依赖 pattern 字段（见 §9）。

3.5 on_signal 的运行线程与阻塞禁令​

_dispatch 由 _read_loop 同步调用，而 _read_loop 是该连接的唯一读线程。因此：

  • on_signal 中执行长耗时操作，会阻塞该连接后续所有消息的接收；
  • 若长耗时操作本身还要等待对端回包（例如多轮模式的 ask()），会形成死锁——对端的回答正是被自己阻塞掉的那条消息。

所以任何需要执行工具、等待对端、或做阻塞 I/O 的 Handler 必须：

threading.Thread(target=self._run_tool, args=(...), daemon=True).start()

这一约定在 msp/multi-round（_on_tool_call → _run_tool）与协议核心（_on_tool_call → _run_tool）中一致，是本规范的必须级要求在模式层的同构表述。

3.6 激活路径​

Handler 进入路由表有两条等价路径，必须都落到同一个激活动作：

路径触发行为
Preset 启动Preset.patterns 中的每个 ID构造 cls() 并激活；核心模式 ID 跳过
运行时登记node.register_pattern(pattern_id, metadata=None)从 PATTERN_REGISTRY 取类，若存在且未激活则构造并激活

激活动作（MSPNode._activate_pattern）固定为三件事，顺序必须是：

  1. handler.install_api(node) — 注入语法糖；
  2. node._patterns[handler.pattern_id] = handler — 节点侧索引（node.pattern(id) 的查询源）；
  3. protocol.patterns[handler.pattern_id] = handler — 协议层路由表。

第 1 步在第 3 步之前，是为了让 install_api 里挂的短名与公开方法在路由生效时已经可用。

4. 核心模式与可扩展模式​

4.1 划分​

类别模式 ID实现位置PATTERN_REGISTRY 条目
核心模式msp/request-reply协议层（MSPProtocol 的 call / _on_tool_call / _run_tool / _on_tool_result）无
核心模式msp/publish-subscribe协议层（MSPProtocol 的 publish / on / _on_signal）无
可扩展模式msp/multi-round独立文件 patterns/multi_round.py有
可扩展模式msp/task独立文件 patterns/task.py有
规划中msp/streaming / msp/callback-push / msp/async-polling尚未实现尚未登记

判定「是核心模式」的依据是常量集合，不是约定：

CORE_PATTERNS = frozenset({"msp/request-reply", "msp/publish-subscribe"})

MSPNode.__init__ 与 register_pattern 必须用这个集合判定并跳过 Handler 实例化。因此 protocol.patterns 与 node._patterns 中不会出现核心模式的条目——这不是遗漏，而是核心模式不参与模式层路由的证据。

4.2 为什么这两个是核心​

三个理由，每一个都指向协议层状态：

  1. 信号路由依赖协议层。_dispatch 本身就是协议层的函数；如果 request-reply / publish-subscribe 也走 on_signal，那么「收包 → 路由」的第 2 步会立刻命中它们，第 3 步的默认分发（含 manifest_update、ping）反而成为不可达代码。核心语义必须坐在路由之下，不能坐在路由之上。
  2. reqid 关联依赖协议层状态。pending_calls: dict[str, tuple[threading.Event, list]] 是协议层字段，_on_tool_result 需要用它唤醒等待者。把它搬进 Handler 意味着连接断开时（_handle_disconnect）要跨层回调每个 Handler 去清理各自的等待表——把一个内聚的失效处理拆成 N 份。
  3. 广播扇出依赖协议层状态。publish 需要遍历 connections: dict[str, Connection] 并直接调用 conn.send()。Handler 只能通过 protocol._send(peer_id, ...) 逐个发；扇出循环、ConnectionClosed 处理与去重连接（_finish_handshake 的规范方向）都属于协议层。

另外有一条兼容性理由：tool_call / tool_result / signal / manifest_update 是 README.md §5.1 冻结的核心信号类型。若把它们交给模式层，则「只用 request-reply 的最小实现」（互通的最低公分母）也必须加载模式层，抬高了下限。

4.3 conflicts_with 的语义​

conflicts_with: list[str] 声明「本模式与被列出的模式不得同时激活」。

  • 该属性的语义是声明式的：它不得被理解为「会自动关闭对方」。参考实现当前不读取 conflicts_with（见 §10 的 G2），因此不得依赖运行时自动校验。
  • 一个实现若在激活模式时读取 conflicts_with 并拒绝冲突组合，必须以明确错误终止启动，不得静默忽略其中一方。
  • 两个模式若只共享信号类型名而语义不同（如 msp/multi-round 与 msp/task 都定义 input_required / input_response），不构成冲突——因为二者都用不同的 pattern 值路由，报文空间不重叠。

5. 模式如何取得协议层能力与 install_api 的推广​

5.1 取得协议层能力​

on_signal 的第一个形参就是 MSPProtocol 实例。Handler 通过它使用协议层能力：

能力用法性质
发包protocol._send(peer_id, sig)私有方法，但属于既定惯例
广播protocol.publish(path, payload)公开方法
本节点 IDprotocol.node_id公开属性
连接表查询protocol.connections公开属性

关于 _send 的下划线前缀，本规范如实写明：

protocol._send() 是私有方法，但在模式层中是既定惯例（established convention）。 msp/multi-round 与 msp/task 的全部定向发包都通过它完成；protocol 对象是 on_signal 的显式形参，正是为了把这一能力合法地交给 Handler。不得用「它是私有方法」为由要求模式层改用 conn.send()——那会绕过连接登记与 RuntimeError("未连接到 X") 的统一失败语义。

调用约定：

  1. _send(peer_id, sig) 在未连接时抛 RuntimeError(f"未连接到 {peer_id}")，连接刚好关闭时抛 ConnectionClosed。Handler 应当捕获这两者并记调试日志，不得让异常穿透到读循环（会触发 _read_loop 的 except Exception 分支，断开与对端的连接）。
  2. 发信号时必须填 source=protocol.node_id；定向回包应当填 target=<对端 node_id>；需要关联的往返必须填 reqid。
  3. Handler 不得直接操作 protocol.connections 做删除/替换——连接生命周期的唯一权威是协议层。

5.2 install_api 的推广​

install_api 是任意层组件的通用扩展点，不只是模式层：

层实现该方法的组件注入的语法糖
模式层MultiRoundHandlernode.multiround
模式层TaskHandlernode.task
发现层ManualConnectnode.add_manual_source(...)（运行时动态加发现源）
宣告层参考实现中暂无—

注入点只有一处，代价约 4 行：

def _install_layer_api(self, component) -> None:
    install = getattr(component, "install_api", None)
    if install is not None:
        install(self)

调用时机：MSPNode.__init__ 在构造每个 discovery / presence 实例之后立即调用；模式层的 install_api 则由 _activate_pattern 调用（§3.6）。

规范条文：

  1. 任意层组件可以定义 install_api(node)；定义了就必须接受且仅接受一个位置参数 node；
  2. 组件应当在其中保存节点反引用（self._node = node）；
  3. 挂到 node 上的名字必须唯一，且不得与 §2.3 列出的核心 API 冲突；
  4. install_api 不得在其中发起网络 I/O 或阻塞等待——它运行在 MSPNode.__init__ 路径上。

6. fallback_to 与降级语义​

6.1 属性语义​

fallback_to 声明「当对端未宣告本模式时，本模式应当降级为哪个模式」。它必须是另一个已定义的 Pattern ID，且不应当形成环（A → B → A）。

6.2 方向判定​

降级的触发条件是对端能力清单，不是本地配置：

  1. 发送方应当先读取 protocol.peer_manifests[peer_id]["patterns"]（或 node.peer(peer_id).supports(pattern_id)）；
  2. 若目标模式在列表中（或对端是 FULL_PEER 这类全模式预设）→ 用本模式；
  3. 否则 → 用 fallback_to 指明的模式，或直接拒绝发起。

6.3 当前实现状态（如实）​

参考实现未实现自动降级。 依据：

  • fallback_to 在 MultiRoundHandler（multi_round.py:56）与 TaskHandler（task.py:302）上各声明一次（值均为 "msp/request-reply"），全代码库没有任何读取点；
  • MSPProtocol.call() 不检查 peer_manifests[peer_id]["patterns"]，直接把 tool_call 发出去；
  • MSPNode.call() 同样不检查；
  • 对端未激活该模式时，信号按 §3.4 降级到第 3 步的默认分发——这恰好是 request-reply 的语义，所以「预期中的降级」在核心模式方向上是偶然成立的，而不是被显式实现。

因此：

  • 应当：实现方在发起扩展模式交互前自行检查 peer.supports(pattern_id)，并自行选择降级或拒绝；
  • 不得：把「对端未宣告该模式」当作连接级错误；
  • 可以：实现自动降级，但一旦实现，必须在降级时保持 reqid 关联语义不变（降级只换报文形态，不换关联键的作用域）。

6.4 Manifest 侧的对应字段​

对端支持的模式列表来自 Manifest.patterns（序列化为 patterns: list[str]）。注意 JSON 键名是 snake_case 的 patterns，而 Manifest 内部的多数字段序列化为 camelCase（patternMetadata、inputSchema、mimeType）。模式私有元数据住在 patternMetadata: {pattern_id: dict}，由 Manifest.set_pattern_metadata() 写入。

6.5 与其他降级路径的区别​

「降级」在本规范里出现三次，语义不同，不得混用：

说法触发条件落点级别
fallback_to 降级对端未宣告目标模式换用另一套模式报文（发送方选择）应当
路由降级pattern 未在 protocol.patterns 中登记走第 3 步默认核心分发（协议层自动）必须
传输降级连接不可达 / 冷却中PeerUnavailable → ToolResult(error=...)必须

前两者只在「模式装配不全」时才有区别：fallback_to 是主动换模式，路由降级是被动退回核心语义。

7. 规划中的模式​

本节三个模式状态为 🔵 规划中。按 README.md §2 的定义：实现者可以不实现，但一旦实现必须符合条文。

三个模式共用下列总则：

  • 模式私有信号类型必须同时携带 pattern 字段（值为对应 pattern_id）才能被路由；
  • 载荷字段必须逐字使用本节给出的键名；Signal 信封字段用 snake_case（type / source / target / path / reqid / payload / timestamp / pattern），payload 内部字段应当沿用 camelCase（与 structuredContent、blobId、mimeType 的既有风格一致），本节逐字段写明；
  • 三种模式都不得新增核心信号类型；
  • 三种模式都必须在 Manifest.patterns 中宣告后才能被对端发起；未宣告即发起时按 §6.2 判定降级（msp/async-polling 正是 msp/streaming 与 msp/callback-push 的兜底目标）。

7.1 msp/streaming — 分块流式传输​

用途：把一次性的长结果拆成多个增量块推送，使接收方在结果完整之前就能消费（增量渲染、边下边用、进度感知）。

私有信号类型：stream_start（开启流）、stream_chunk（数据块）、stream_end（结束，携带终态摘要）、stream_cancel（双向，任一方请求取消，可选实现）。四个类型必须携带 reqid 与 pattern="msp/streaming"。

载荷字段（键名必须逐字一致）：

信号字段类型必需语义
stream_startstreamIdstr必须流标识；与 reqid 并存——reqid 用于关联，streamId 用于日志与多流复用
totalChunks / totalBytesint | null可以已知总量；未知时省略或 null
contentTypestr可以载荷 MIME 类型，缺省 application/octet-stream
orderingstr可以"ordered"（默认）或 "unordered"，声明块是否可乱序到达
metaobject可以模式无关的附加元数据（如工具名、任务 ID）
stream_chunkseqint必须块序号，从 0 起单调递增；ordering="unordered" 时仍必须给出，接收方据此重排
datastr必须块内容；二进制必须按 Base64 编码
encodingstr可以"utf-8"（默认）或 "base64"
finalbool可以缺省 false；true 等价于随后 stream_end 的简写
stream_endstatusstr必须"ok" / "canceled" / "error"
chunks / bytesint可以实际发出的块数 / 字节数
checksumstr可以整体校验和（如 sha256:<hex>）
errorobject可以status="error" 时必须给出，形如 {"code": int, "message": str}

stream_chunk 与 stream_end 的 streamId 同样必须给出，且与 stream_start 一致。

消息流：

 发送方                                接收方
   │ ── stream_start(reqid=R) ─────────▶ │  准备接收（注册 streamId）
   │ ── stream_chunk(seq=0) ───────────▶ │  消费块 0
   │ ── stream_chunk(seq=1) ───────────▶ │  消费块 1
   │        ⋮                            │
   │ ◀── stream_cancel(reqid=R) ──────── │  （可选）接收方要求停止
   │ ── stream_end(status="canceled") ─▶ │  发送方确认终止
   │ ── stream_end(status="ok") ───────▶ │  终态：流关闭，reqid 可回收

终态：每个流必须以恰好一个 stream_end 结束。收到终态后该 reqid 与 streamId 必须被双方注销。

错误：

情形处理
未知 streamId 的 stream_chunk必须丢弃并记日志；应当回 stream_cancel
seq 重复必须以首个到达者为准，丢弃后来的
seq 跳号ordering="ordered" 时应当等待重排窗口；超时后必须以 status="error" 结束
终态前连接断开必须置本地流为失败并释放资源，不得永久保留半成品
载荷校验失败必须以 status="error" 结束

背压：streaming 不得假设发送方可以无界推送。接收方可以用 stream_cancel 施加粗粒度背压；实现可以定义细粒度流控（如窗口 chunk_window / stream_ack），但一旦定义必须在 patternMetadata["msp/streaming"] 中声明，并遵循 README.md §1 的「追加」规则；发送方不得因对端处理慢而阻塞读循环——推送必须在自己的线程里进行。

与大对象 blob_ref 的关系：二者不得互相替代。

维度msp/streamingblob_ref 内容块
用途增量消费（边到边用、进度、增量渲染）大对象的引用传递，内容走独立通道按需取
是否承载完整数据是（分块承载）否（只承载 blobId / mimeType / size / checksum）
出现在哪里独立信号流tool_result.payload.content 的一个块，type="blob_ref"

需要在传输过程中被消费的用 streaming；只是体积大、可延后取用的用 blob_ref。blob_ref 的取值通道（blob_chunk 信号流）属于 base-protocol.md 的范畴，本页不定义其报文。

互斥与降级：conflicts_with = []（与 msp/task 的产物广播可以并存）；fallback_to = "msp/request-reply"，降级语义 = 「一次性把完整结果作为 tool_result 返回」。

7.2 msp/callback-push — 长任务回调式回传​

用途：提交一个长任务后不阻塞等待，任务完成时由被委托方主动推一条回调信号给提交方（也可推给提交方指定的第三方观察者）。

私有信号类型：callback_register（注册回调）、callback_ack（接受或拒绝的回执）、callback_push（结果回传）、callback_cancel（撤销，可选实现）。四个类型必须携带 reqid 与 pattern="msp/callback-push"。

载荷字段：三个信号的 callbackId 均必须给出并互相回显。

信号字段类型必需语义
callback_registercallbackIdstr必须本次回调的标识，由提交方生成
topicstr必须逻辑主题，实现自定（可用 node_id 或 task.<id>）
deliverTostr可以结果投递目标 node_id；省略时即注册方自身
pathstr可以投递方式为广播时指定 signal.path
expiresAtfloat可以Unix 时间戳，超过后注册必须失效
expectstr可以"result"（默认）或 "progress"
callback_ackcallbackId / acceptedstr / bool必须回显与是否接受
ttlfloat可以被委托方愿意保留注册的秒数
reasonstr可以accepted=false 时应当给出
callback_pushstatestr必须"progress" / "completed" / "failed" / "canceled"
contentlist可以content 块列表，格式与 tool_result.payload.content 完全一致
structuredContentany可以结构化结果，格式与 tool_result.payload.structuredContent 一致
errorstr可以失败原因；state="failed" 时应当给出
seqint可以state="progress" 时的进度序号

消息流：

 提交方                                被委托方
   │ ── callback_register(reqid=R) ────▶ │  登记 callbackId → (deliverTo, topic)
   │ ◀── callback_ack(accepted=true) ─── │  回执
   │                                     │  ……任务异步执行……
   │ ◀── callback_push(state=progress) ── │  （可选）进度
   │ ◀── callback_push(state=completed) ─│  终态
   │ ── callback_cancel(reqid=R) ──────▶ │  （可选）撤销

终态：callback_push.state ∈ {completed, failed, canceled} 之一必须是本次回调的最后一条推送；此后该 callbackId 必须被双方注销。

错误：

情形处理
callback_ack.accepted=false提交方必须停止等待推送，并按 fallback_to 走显式轮询
注册过期（expiresAt 已过）被委托方必须丢弃该 callbackId；推送失败不得无限重试
推送目标不可达被委托方必须丢弃该注册并记日志；不得阻塞任务线程
未知 callbackId 的 callback_push接收方必须丢弃并记日志
重复终态推送接收方必须以首个终态为准

互斥与降级：conflicts_with = []（与 msp/task 可并用——msp/task 负责状态机与多观察者广播，本模式负责定向回传）；fallback_to = "msp/async-polling"，降级语义 = 「不注册回调，改为提交方按 callbackId 显式轮询」。

7.3 msp/async-polling — 显式轮询语义（互操作兜底）​

用途：互操作兜底。当对端既不支持 streaming 也不支持 callback-push 时，用「提交 → 轮询 → 取结果」这一最朴素的语义完成长任务协作。它是三个规划模式中能力最弱但最可移植的一个，也是另外两者的兜底目标。

私有信号类型（七个，必须携带 reqid 与 pattern="msp/async-polling"）：poll_submit → poll_submit_result、poll_status → poll_status_result、poll_fetch → poll_fetch_result，以及可选的 poll_cancel。

载荷字段：

  • poll_submit：tool（str，必须）、args（object，可以）、jobId（str，可以，省略时由执行方生成）、ttl（float，可以，作业保留秒数）。
  • poll_submit_result：jobId（必须）、state（必须）、accepted（bool，必须）。
  • poll_status：jobId（必须）。poll_status_result：jobId（必须）、state（必须）、progress（float，可以，0.0–1.0）、eta（float，可以）。
  • poll_fetch：jobId（必须）、offset（int，可以，分片取结果时用）。poll_fetch_result：jobId（必须）、state（必须）、content（list，可以）、structuredContent（any，可以）、error（str，可以）。

state 取值（本模式私有，不得与其他模式的状态字符串混用）：pending（已接受，未开始）、running（执行中）、completed（终态，结果可 poll_fetch）、failed（终态）、canceled（终态）、not_found（终态，未知或已过期的 jobId）。

消息流：

 提交方                                执行方
   │ ── poll_submit(reqid=R1) ─────────▶ │  接受作业，返回 jobId
   │ ◀── poll_submit_result(jobId=J) ─── │  state=pending
   │ ── poll_status(reqid=R2, J) ──────▶ │
   │ ◀── poll_status_result(state=running)│
   │        ⋮  （提交方自定轮询间隔）      │
   │ ── poll_status(reqid=R3, J) ──────▶ │
   │ ◀── poll_status_result(state=completed)
   │ ── poll_fetch(reqid=R4, J) ───────▶ │
   │ ◀── poll_fetch_result(content=…) ── │  终态数据交付

终态：poll_status_result.state 或 poll_fetch_result.state 为终态之一时本次协作结束；执行方可以在 ttl 之后回收该 jobId，此后查询必须返回 not_found（而不得返回 failed）。

错误：

情形处理
未知 / 过期 jobId必须回对应结果信号并置 state="not_found"；不得回 error 信号
轮询过快执行方可以回 state="running" 并附 eta；不得因此断开连接
poll_fetch 在非终态调用必须回 state=running 且不得附带 content
取消协作式：必须置取消标志并尽快回 state="canceled"；不得承诺强杀执行线程

互斥与降级：conflicts_with = []；fallback_to = None——本模式是兜底链的末端，再往下只剩「用 msp/request-reply 同步等一个短工具」，那不属于本模式的定义范围（见 §6.2）。

7.4 三者的选择顺序（应当）​

需要增量消费 ─────▶ msp/streaming ──（对端未宣告）──▶ msp/callback-push
   需要结果主动回传 ──▶ msp/callback-push ──（对端未宣告）──▶ msp/async-polling
       兜底 ──▶ msp/async-polling ──（对端未宣告）──▶ msp/request-reply

8. 模式登记​

新增一个可扩展模式必须完成以下步骤（对应 README.md §8 的演进顺序）：

步骤动作落点
1在 README.md §5.2 的模式 ID 表新增一行，附状态标记规范
2在本页 §7（规划中）或新增页（已实现）给出完整条文：信号类型、载荷字段、消息流、终态、错误、互斥、fallback_to规范
3在 schema.md 同步报文形态规范
4新建 src/msp/patterns/<name>.py，实现 PatternHandler 子类实现
5在 PATTERN_REGISTRY 增加一条 "<pattern_id>": <HandlerClass>实现
6若需随预设启动，加入相应 Preset.patterns；否则用 node.register_pattern(pattern_id) 运行时登记实现
7补测试；若为不兼容变更，在修订历史新增修订号实现 + 规范

约束：

  • 第 4–5 步必须成对出现。只在注册表加条目而没有 Handler 文件会让 PATTERN_REGISTRY 导入失败。
  • 模式 ID 使用 msp/ 前缀时必须先走完第 1–3 步；第三方模式必须自带前缀。
  • 模式私有信号类型不得与 README.md §5.1 的九个核心类型重名；msp/ 之外的模式必须为自己的类型加前缀（acme_stream_start），避免跨模式撞名。
  • 模式不得要求修改 _dispatch 的判定顺序（§3.1）。

一个最小骨架：

# src/msp/patterns/streaming.py
class StreamingHandler(PatternHandler):
    pattern_id = "msp/streaming"
    fallback_to = "msp/request-reply"

    def install_api(self, node) -> None:
        self._node = node          # 约定：保存反引用
        node.streaming = self      # 约定：挂短名（不得与核心 API 冲突）

    def on_signal(self, protocol, peer_id: str, sig: Signal) -> None:
        ...  # 按 sig.type 分派；重活交给独立线程
# src/msp/patterns/__init__.py
PATTERN_REGISTRY["msp/streaming"] = StreamingHandler   # 新增一条注册表条目

注意：msp/streaming 等三个规划模式一旦落地，必须同时在 PATTERN_REGISTRY 中出现，不得被加入 CORE_PATTERNS——它们不依赖协议层状态，属于可扩展模式。

9. 安全考量​

#考量条文
1pattern 不是安全边界路由契约规定未登记 pattern 的信号降级到默认分发（§3.4），攻击者可以省略或伪造 pattern 绕过模式层的任何自建检查。授权判定必须基于信号类型与载荷（如 tool_call 的 payload.tool），不得基于 pattern
2type 字段被多模式共享msp/multi-round 与 msp/task 都定义 input_required。不得用 type 单独判定语义，必须配合 pattern；不得认为 type 相同则载荷可互换
3install_api 会往 node 上挂名字覆盖核心 API（如 node.call = ...）会直接破坏节点行为（见 §2.3 命名禁令）。加载路径 PATTERN_REGISTRY 是静态导入，属供应链信任问题，不是运行时可被远端触发的漏洞
4模式层与协议层同权Handler 通过 protocol._send 可对任意已连对端发信号（msp/task 的观察者广播即此类用法）。模式必须由节点运营者安装，不得支持对端远程注册模式
5streaming 的资源耗尽面（🔵）分块流把「一条大消息」拆成「N 条小消息」，接收方为每个未完成流保留缓冲区会引入内存放大攻击面。实现必须为每个 streamId 设资源上限，超限时以 stream_end(status="error") 结束（同一意图见 ttl 与 expiresAt）
6授权过滤的落点不在模式层出站扇出的 sub 授权过滤属于协议层 publish 的循环（见 publish-subscribe.md、security.md）。模式不得自行实现「谁能看」的策略，否则会出现多处策略漂移
