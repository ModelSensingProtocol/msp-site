msp/multi-round — 执行中追问

协议修订2026-10-10
模式 IDmsp/multi-round
状态标记✅ 已实现（主路径可验证）；§9 列出的边界为 🟡 部分实现
降级目标msp/request-reply（fallback_to）
规范性用语RFC 2119，见规范索引
本页定义被调方在一次 tool_call 的同一个 reqid 内多次向调用方索取补充信息，再给出最终结果

1. 概述​

1.1 解决的工程问题​

工具参数经常要等到执行中才能确定：订票工具直到要下单才发现缺出发日期，检索工具直到拼查询语句才发现缺时间范围。若没有本模式，双方只有两种笨办法：

  1. 工具失败一次，把「缺少什么」编码进 tool_result.payload.error，调用方解析后再调一次——一次交互被拆成两次，服务端要重建上下文，reqid 变了，ctx 里的中间状态全丢。
  2. 工具干脆把参数一次要全，逼调用方把所有细节塞进 args，哪怕其中一半用不上。

msp/multi-round 给第三种选择：在同一次调用的 reqid 内就地补齐。工具函数在独立线程里执行到一半，调用 ctx.ask(...) 阻塞等待；调用方收到追问、作答、回传；工具带着答案继续跑。被调方的执行栈、局部变量、已发出的中间副作用都还在原地。

1.2 与现有模式的关系​

  • 本模式是 msp/request-reply 的超集：起手报文仍是 tool_call，收尾报文仍是 tool_result，关联键仍是 reqid。区别只在于往返过程中被调方可以反向插话。
  • 「多轮」不等于「有人参与」。作答方是调用方提供的 input_fn；它可以查本地配置、走默认值、按规则推导、读本地模型——可以完全没有人在回路里。
  • 本模式只新增两个模式私有信号类型（input_required / input_response），核心 SignalType 零改动。协议层为此付出的代价，只有模式路由里的一条查表。

2. 契约​

2.1 模式标识与降级​

项值源码位置
pattern_id"msp/multi-round"MultiRoundHandler.pattern_id
fallback_to"msp/request-reply"MultiRoundHandler.fallback_to
conflicts_with[]（继承 PatternHandler 默认值，本模式未声明）PatternHandler.conflicts_with

降级语义：fallback_to 声明的意图是——当对端不支持本模式时，改用 msp/request-reply 重发（退化为一次普通工具调用，追问能力消失）。当前参考实现不发生自动降级：fallback_to 在全仓库只被声明、没有任何代码读取。但 call_multiround() 现在会先建连再检查 peer(peer_id).supports("msp/multi-round")，对端未宣告本模式时立即抛 RuntimeError（不再发出去后靠总超时兜底，见 §12 G2）——检查已实现，降级仍未实现。

实现者可以实现自动降级，但一旦实现必须满足：降级前不得发出任何 input_required；降级后本次交互的报文形态必须完全符合 msp/request-reply（不得带 pattern 字段）；降级应当通过调用方显式可见的方式告知（如返回值或异常），而不得静默改变语义。

事实澄清：当对端没有注册本模式 handler 时，带 pattern 的 tool_call 会落到协议层的默认分支（_dispatch 第 3 步），被核心工具注册表当作普通工具调用处理。这不是规范意义上的降级，而是无模式路由的兜底：同名工具若只在模式自带注册表里注册过，核心表查不到，会回一个 error 为「未知工具: X」的 tool_result。见 §6.1。

2.2 信号类型​

信号 type方向有 reqid语义
tool_call调用方 → 被调方是起手请求；与核心同名类型共用，靠 pattern 区分
input_required被调方 → 调用方是追问；reqid 与起手 tool_call 必须相同
input_response调用方 → 被调方是应答；reqid 必须与追问相同
tool_result被调方 → 调用方是终止结果；reqid 必须与起手相同

input_required / input_response 是本模式私有的 type 值。所有本模式信号必须携带 pattern = "msp/multi-round"——它是协议层的路由键（见 §6.1 与 模式层契约）。

2.3 线程与阻塞模型​

侧约束理由
被调方必须在独立线程中执行工具函数工具的 ctx.ask() 是阻塞调用；若在执行读循环的线程里跑，调用方回传的 input_response 永远读不到，必死锁
被调方可以在一次工具执行中多次调用 ctx.ask()每次调用生成一对 reqid 相同的新追问/应答
调用方收到 input_required 时应当在收到它的线程之外完成阻塞式询问参考实现在读循环线程内同步调用 input_fn；见 §9
两侧不得假定追问次数有上界协议不设次数上限；调用方用总超时兜底

ctx.ask(prompt, timeout=30.0)：prompt（str，必填）原样进入 input_required.payload.prompt；timeout（float，默认 30.0）是单次追问的等待上界；返回 input_response.payload.answer 的原值；超时抛 TimeoutError（文案 "等待客户端补充信息超时"）。调用方的总超时由 call_multiround(..., timeout=60.0) 独立控制，与单次追问超时不是同一个值，不得互相推导。

3. 报文（逐信号）​

信封字段的通用规则见 Signal 信封。以下示例中，信封为 snake_case（type / source / pattern / target / path / reqid / payload / timestamp），payload 内部字段名逐字取自源码。

3.1 tool_call​

字段位置类型必填值
type信封string必须"tool_call"
pattern信封string必须"msp/multi-round"
source / target信封string必须调用方 / 被调方 node_id
reqid信封string必须本次交互的关联标识，贯穿全部四类报文
payload.tool载荷string必须工具名
payload.args载荷object必须工具实参；参考实现取不到时用 {}
{ "type": "tool_call", "source": "client_node", "pattern": "msp/multi-round", "target": "server_node",
  "path": null, "reqid": "mr-1", "payload": { "tool": "book_flight", "args": { "destination": "Paris" } } }

reqid 的生成方式属实现自由。参考实现按 handler 实例计数生成 mr-<n>（n 从 1 递增），与核心模式使用 Signal.new_reqid()（16 位十六进制随机串）不同。应当保证同一节点内并发交互的 reqid 互不相同。

3.2 input_required​

字段位置类型必填值
type信封string必须"input_required"
pattern信封string必须"msp/multi-round"
source / target信封string必须被调方 / 调用方 node_id
reqid信封string必须与起手 tool_call 相同
payload.prompt载荷string必须追问文案
{ "type": "input_required", "source": "server_node", "pattern": "msp/multi-round", "target": "client_node",
  "path": null, "reqid": "mr-1", "payload": { "prompt": "出发日期？" } }

载荷只有 prompt 一个字段。 参数名、期望类型、取值范围、候选项、上下文片段在参考实现中均不存在；接收方不得假定存在，发送方若自行扩展应当新增字段而不得改变 prompt 的含义（宽容读取见base-protocol §2.3）。接收方取不到 prompt 时应当按空串处理。

3.3 input_response​

字段位置类型必填值
type信封string必须"input_response"
pattern信封string必须"msp/multi-round"
source / target信封string必须调用方 / 被调方 node_id
reqid信封string必须与该次 input_required 相同
payload.answer载荷any必须应答值，任意 JSON 可序列化类型
{ "type": "input_response", "source": "client_node", "pattern": "msp/multi-round", "target": "server_node",
  "path": null, "reqid": "mr-1", "payload": { "answer": "2026-10-15" } }

answer 的类型不受本规范约束：字符串、数字、布尔、对象、数组、null 均可，被调方不得假定其为标量。参考实现在 input_fn 抛异常时把 answer 置为 {"error": "<异常文本>"}——这是实现约定而非协议语义，被调方不得把它当作取消或超时的信号。

3.4 tool_result​

字段位置类型必填值
type信封string必须"tool_result"
pattern信封string必须"msp/multi-round"
reqid信封string必须与起手 tool_call 相同
payload.content载荷any必须工具返回值的原样值；返回 falsy 值（None / "" / 0 / False / {} / []）时归一为 []
payload.error载荷string必须成功时为 ""；失败时为异常文本
{ "type": "tool_result", "source": "server_node", "pattern": "msp/multi-round", "target": "client_node",
  "path": null, "reqid": "mr-1",
  "payload": { "content": { "destination": "Paris", "date": "2026-10-15", "airline": "国航" }, "error": "" } }

与核心 msp/request-reply 的 tool_result 有三处实质差异，实现者必须按本模式的形态处理：① 本模式不产出 structuredContent，返回值只出现在 content 里；② 本模式的 content 是工具返回值的原样值（可能是对象、字符串、数组；但 falsy 值会被 content or [] 归一为 []），不是规范化后的内容块数组（核心模式会先经 _normalize_tool_result 再写入 content）；③ 本模式总是同时携带 content 与 error，成功时 error 是空串，因此调用方应当判断 error != ""，而不得用字段是否存在来判断成败。

4. 消息流​

4.1 正常路径：两次追问 + 最终结果（同一个 reqid）​

   调用方 (client_node)                                    被调方 (server_node)
        │ ① tool_call  reqid=mr-1  payload={tool:"book_flight",args:{…}}      │
        ├──────────────────────────────────────────────────────────────────────▶│
        │                                     读循环只做分发，起独立线程跑工具
        │                                     工具执行中，发现缺参数
        │ ② input_required  reqid=mr-1  payload={prompt:"出发日期？"}           │
        │◀──────────────────────────────────────────────────────────────────────┤
        │                                     ctx.ask("出发日期？") 阻塞，<=30s
        │ input_fn("出发日期？") → "2026-10-15"                                 │
        │ ③ input_response  reqid=mr-1  payload={answer:"2026-10-15"}           │
        ├──────────────────────────────────────────────────────────────────────▶│
        │                                     唤醒 ask()，工具继续执行
        │ ④ input_required  reqid=mr-1  payload={prompt:"偏好航空公司？"}       │
        │◀──────────────────────────────────────────────────────────────────────┤
        │                                     ctx.ask("偏好航空公司？") 阻塞
        │ ⑤ input_response  reqid=mr-1  payload={answer:"国航"}                 │
        ├──────────────────────────────────────────────────────────────────────▶│
        │                                     工具返回，工作线程结束
        │ ⑥ tool_result  reqid=mr-1  payload={content:{…},error:""}             │
        │◀──────────────────────────────────────────────────────────────────────┤
        │ 唤醒 call_multiround()，返回 content                                  │
        ▼                                                                       ▼

四个关键不变式：① ②③④⑤⑥ 的信封 reqid 必须恒等于 ①；② 同一 reqid 只必须产生一个 tool_result；③ 追问与被调方的线程数无关，可以在同一线程内串行发生多次；④ 调用方无需宣告自己支持本模式，也无需预知追问次数。

4.2 错误路径对照​

  (a) 追问超时      被调方: ask() 抛 TimeoutError → tool_result{content:[],error:"等待客户端补充信息超时"}
  (b) 工具异常      被调方: tool_result{content:[],error:"<异常文本>"}
  (c) 未知工具      被调方: tool_result{content:[],error:"未知工具: <name>"}  ← 立即回，不起线程
  (d) 调用方总超时  调用方: TimeoutError（丢弃该 reqid 的等待表项）→ 之后到达的 input_required 被静默丢弃
  (e) 对端无 handler 对端: error{code:-32600,message:"未知信号类型: input_required"}（带原 reqid）
                    调用方: 不识别该 error，继续等到总超时

5. 数据与类型约定​

概念类型约束
答案Any任意 JSON 可序列化值；input_fn 的返回值原样进入 answer
追问文案string单段文本，不含结构化 schema
工具返回值Any原样进入 tool_result.payload.content；falsy 值（None / "" / 0 / False / {} / []）→ []
错误文本string人类可读；本模式不定义数值错误码

本模式不定义新的错误码。工具执行失败走 tool_result.payload.error（错误即值），协议级失败沿用错误码表（如 -32600）。参数不符合工具声明的 inputSchema 时应当用 -32602 语义的工具失败表达，而不是发 error 信号。

6. 错误处理与边界​

6.1 对端不宣告 / 未激活本模式——调用方应当在调用前检查 peer(peer_id).supports("msp/multi-round")；参考实现的 call_multiround() 现在自己做这件事：先 ensure_connected()，再查 supports()，未宣告即抛 RuntimeError（调用方仍应当自行检查以决定是否走降级路径）。对端若没有注册本模式 handler：带 pattern 的信号在路由表中查不到，落入协议层默认分支。tool_call 会被当作普通工具调用处理（可能误命中核心注册表里的同名工具）；input_required / input_response 则命中「未知信号类型」分支，回 error（code = -32600）。该 error 携带原 reqid，协议层 _on_error 会按 reqid 唤醒等待中的调用并回 ToolResult(error=...)（原实现只记日志、必须等满总超时，见 §12 G3）。

6.2 input_required 无人应答——被调方 ctx.ask() 的等待表项只登记在被调方本地。调用方若丢弃了 reqid 对应的等待表项（总超时、进程退出、逻辑分支遗漏），到达的 input_required 会被静默忽略，不回 input_response；被调方只能等到单次追问超时。协议不定义「拒绝追问」这一报文；实现者若需要，应当用 input_response.payload.answer = null 表达「无答案」。

6.3 超时——单次追问（被调方 ctx.ask）默认 30.0 s，触发后抛 TimeoutError、弹出表项，工具通常随即失败并回 error；整次调用（调用方 call_multiround）默认 60.0 s，触发后抛 TimeoutError、弹出 reqid 表项，且不向对端发送取消。两者无约束关系：追问次数 × 单次超时可以超过整次超时。调用方应当令整次超时 ≥ 预期追问次数 × 单次追问超时；参考实现不做校验。

6.4 连接断开——被调方的应答类信号（tool_result / input_response）统一经 _send() 发出，捕获 (RuntimeError, ConnectionClosed) 并降级为日志；连接已断时该次结果丢失且无任何补偿，工具函数已产生的副作用不回滚，但不会再让异常从工作线程冒出（原实现会让工作线程异常退出，见 §12 G8）。调用方在等待中断开连接时，等待表项由协议层的断线清理唤醒（ToolResult(error="连接断开")）。本模式不定义断线重连后的续传。

6.5 reqid 不匹配——被调方 _on_input_response 按 reqid 查等待表项，查不到即静默丢弃；调用方 _on_tool_result / _on_input_required 同样按 reqid 查表，查不到即静默丢弃。两侧都不校验来源 node_id ✅ 已修复：两侧现在都按连接身份（而非可伪造的 sig.source）核对「这条应答是否来自我调用的那个对端」，不匹配即丢弃。这一条是必需的——参考实现的 reqid 是 mr-1、mr-2 这类可预测值，不得把它当作安全令牌（security §3.10）。见 §8。

6.6 重入与并发——并发多次调用可以：每个调用有独立 reqid、独立的事件与结果槽。但同一 reqid 内并发两次 ctx.ask() 不被支持：等待表项以 reqid 为键、只有一个槽位。工具函数不得从多个线程同时对同一 reqid 调用 ask()；参考实现会检测到重入并抛 RuntimeError（原实现静默覆盖、前一次必然超时，见 §12 G6）。重入危险：input_fn 在调用方的读循环线程里执行，若 input_fn 内部再发起一次到同一对端的调用并等待其回复，回复永远读不到，双方互等至超时。

6.7 回调异常——input_fn 抛出的任何异常都会被调用方捕获，并转成 answer = {"error": "<异常文本>"} 后照常回传，追问不会因此中断；被调方必须自行判断该对象是否是「失败」约定。

6.8 与 MCP elicitation 的差异​

维度MCP elicitationmsp/multi-round
请求关联另起一次反向请求，有独立的请求标识，与原调用不共享延续原调用的 reqid，全程同一个关联键
原调用状态原调用是否仍在等待由应用层维持原调用在被调方原地阻塞，执行栈不丢
追问次数一次反向请求对应一次征询同一 reqid 内可以无限次追问
载荷带 JSON Schema 的受约束结构（字段名、类型、枚举）只有一段 prompt 文本，无 schema
权限方向约定由 server 向 client 征询双向：只要一方持连接即可发起（此处由被调方发起）
复用既有原语需新增反向请求通道复用 tool_call 的 reqid 关联，核心零改动

结论：elicitation 解决的是「服务端能不能问一句」，本模式解决的是「这一次调用的上下文能不能活着等到答案」。两者可共存；在 MSP 中如要表达 elicitation 语义，应作为独立能力面（见 capabilities）而不是复用本模式。

7. 规范条文汇总​

必须：① 本模式的四类信号必须携带 pattern = "msp/multi-round"；② 一次交互内 input_required、input_response、tool_result 的 reqid 必须与起手 tool_call 相同；③ 被调方必须在独立线程（或等价的非读循环执行体）中执行工具函数；④ input_required.payload.prompt 与 input_response.payload.answer 必须存在；⑤ 同一 reqid 只必须产生一个 tool_result；⑥ 未识别的字段、信号类型不得导致连接中断（宽容读取）。

应当：⑦ 调用方应当在调用前确认对端宣告了本模式；⑧ 调用方应当令整次超时覆盖预期的全部追问；⑨ 被调方应当把失败表达为 tool_result.payload.error，而不是 error 信号；⑩ 实现者若要跳过一次追问，应当回 answer = null，而不是不回。

不得：⑪ 调用方不得假定追问次数、answer 的类型或 prompt 的结构；⑫ 被调方不得在读循环线程内调用 ctx.ask()；⑬ msp/ 命名空间外的模式不得复用 input_required / input_response 这两个 type；⑭ 降级实现不得静默改变已发出的语义（见 §2.1）。

可以：⑮ 实现可以不实现本模式；一旦实现必须符合本页条文。⑯ 实现可以在本页之外扩展 input_required.payload 的字段。

8. 安全考量​

  • 来源未校验：两侧都只按 reqid 关联，不校验 source。参考实现的 reqid 可预测（mr-<n>），因此应当把「收到 input_response」视为未经认证的输入，绝不得把它当作授权、身份或金额这类高价值决策的唯一依据。实现者应当改用不可预测的 reqid 并校验来源节点。
  • 追问即数据入口：answer 会直接进入工具函数的控制流。工具必须按普通不可信输入校验它（长度、类型、取值范围），不得把它拼进命令、路径或查询而不做转义。
  • 信息泄露：prompt 由被调方控制，会被原样交给调用方的 input_fn。调用方应当把 prompt 当作不可信文本渲染或记录，避免注入本地日志格式或终端控制序列。
  • 无授权层：本模式不做任何授权判定；谁能调用工具由连接与部署策略决定，见 security。
