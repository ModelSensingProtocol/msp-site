核心模式：发布—订阅（msp/publish-subscribe）

协议修订2026-10-10
状态✅ 已实现（含发送侧 sub 授权过滤）
本页定义核心通讯模式 msp/publish-subscribe：广播模型（publish 扇出到所有已连对端、无订阅表）、接收方本地过滤（on(path)）、路径语法与通配符匹配算法（pattern_matches 逐行对应）、匹配边界与易错点、虚拟总线与版本化路径、安全考量

本页是 patterns.md 的具体化。msp/publish-subscribe 是核心模式，直接实现在协议层，不进 PATTERN_REGISTRY，也没有 Handler 实例（理由见 patterns.md §4.2）。

1. 概述​

msp/publish-subscribe 的语义一句话：发布方把一条 type="signal" 的报文扇出到所有已连对端；接收方在本地用路径模式过滤，命中的回调才触发。

它的关键设计取舍是没有订阅表：

  • 线上没有 subscribe / unsubscribe 信号。发布方不知道谁「订阅」了什么，也不需要知道。
  • 发布不需要协商。publish() 直接把信号发给全部已连对端，包括从未表达过兴趣的对端。
  • 过滤责任在接收方。是否消费由接收方的 on() 模式决定。

这条取舍换来的是协议面的极小化：一个只实现 msp/publish-subscribe 的节点不需要维护任何对端订阅状态，也不需要处理订阅与断线的时序竞态（对端掉线后订阅是否还在？——不存在这个问题，因为没有订阅）。

代价是带宽：N 个已连对端就是 N 次发送，与「有多少人真的感兴趣」无关。这是刻意的取舍，不是缺陷（见 architecture.md §已知缺口）。

2. 契约​

2.1 报文形态​

publish(path, payload) 构造恰好如下信号：

Signal.make(
    type=SignalType.SIGNAL,   # "signal"
    source=self.node_id,
    path=path,
    payload=payload,
)

必须满足：

字段值级别
type恒为 "signal"必须
source恒为本节点 node_id必须
path调用方给出的路径，必须符合 segment(.segment)*（[README.md §5.3](https://github.com/hxh230802/MSP/blob/master/docs/spec/README.md#53-命名规范)）必须
payload调用方给出的字典必须
targetNone（广播无单一目标）必须为 None
patternNone（核心模式不写路由键）必须为 None
reqidNone（广播不需要应答关联）必须为 None
timestamp由 Signal.make 自动填充必须

注意：payload 内部没有 path 字段——路径是信封字段 Signal.path，不是载荷字段。实现不得把路径塞进 payload。

2.2 扇出语义​

publish() 必须：

  1. 在锁内快照连接表（list(self.connections.items())），不得持锁执行网络发送；
  2. 对每一个已连对端发送同一份报文的编码结果；
  3. 对发送时抛 ConnectionClosed 的对端，必须触发该对端的断连清理（_handle_disconnect(peer_id, conn)），并继续发送给其余对端；
  4. 不得因为某个对端失败而中断整个扇出循环；
  5. 不得返回任何成功/失败计数——publish() 的返回值是 None。广播是「尽力而为」（best-effort），不是「全部送达」。

「尽力而为」的准确含义：若调用 publish() 时某对端的连接已经关闭，那它收不到；若连接在发送过程中关闭，扇出循环会感知并清理；若对端进程已经死了但 TCP 还没察觉，报文会被写入内核缓冲区然后随连接超时一起消失。没有送达确认，也不应有——需要确认就用 msp/request-reply。

2.3 接收方本地过滤​

接收方必须按以下规则处理收到的 signal：

  1. _dispatch 第 1 步不命中（signal 不是核心信号类型）；
  2. _dispatch 第 2 步不命中（pattern 为 None）；
  3. _dispatch_core 命中 SignalType.SIGNAL → _on_signal(peer_id, msg)；
  4. _on_signal 在锁内快照回调列表，然后在锁外遍历；
  5. 对每个 (path_filter, func)：
    • 若 path_filter is None → 无条件调用；
    • 否则若 pattern_matches(path_filter, msg.path) 为真 → 调用；
    • 否则跳过。

必须满足：

#条文级别
1path=None 的回调必须匹配全部路径必须
2每个命中回调必须被调用一次；多个回调命中时必须全部调用必须
3单个回调抛出的任何异常必须被捕获（记 warning 日志），不得影响后续回调必须
4回调必须在协议层读循环线程上被调用（不是工作线程）必须
5回调不得执行长耗时操作——它会阻塞该连接的消息接收（同 patterns.md §3.5）不得
6回调注册必须可以随时进行，包括在读循环运行期间（注册表在锁内修改）必须
7回调不得从回调内部注销自身——当前没有注销 API（见 §10 G1）不得

回调签名是 func(sig)，其中 sig 是完整的 Signal 对象（可取 sig.source / sig.path / sig.payload / sig.timestamp）。

2.4 注册 API​

协议层 on(path=None, callback=None) 支持两种用法：

# 用法一：装饰器
@proto.on(path="ai.state")
def handler(sig): ...

# 用法二：直接注册
proto.on(path="ai.state", callback=handler)

节点层 node.on(path=None) 只暴露装饰器形态：

@node.on("ai.state")
def handler(sig): ...

@node.on()          # path=None：接收全部
def spy(sig): ...

必须满足：

  1. 同一回调可以被注册多次，它就会被调用多次——实现不得去重；
  2. 注册必须返回被装饰的函数本身（装饰器形态），使函数仍可正常调用；
  3. path 参数必须允许为 None；
  4. 不得为 path 参数做格式校验——非法的路径模式不是错误，只是永不匹配（见 §4.5）。

2.5 自动重复发布​

@node.signal_source(path)（别名 @node.signal(path)）装饰一个生成器函数。节点启动后，每个信号源在独立线程里持续迭代：

for payload in func():
    if not running: break
    if not isinstance(payload, dict): continue
    publish(path, payload)

必须满足：

  1. 生成器的每次 yield 必须是一个 dict；非 dict 的产出必须被跳过（不报错、不发布）；
  2. 第一个产出到达前允许有任意延迟（常用于等订阅者就绪）；
  3. 生成器函数内抛出的异常必须被捕获、记日志为「信号源异常终止」，不得影响其它信号源或节点；
  4. signal_source 必须同时声明路径（等价于调用一次 declare_signal(path)），使该路径出现在 Manifest.signals 中；
  5. 节点停止后不得继续发布——_running 为假时循环中断。

3. 路径语法​

路径是信号的逻辑地址，与传输地址、node_id 无关。

3.1 字符与分层​

项规定
分隔符点号 .
格式segment(.segment)*
段内字符应当为 [a-z0-9_-]（与 node_id / 工具名同风格）；不得包含点号、空格、通配符
大小写应当全小写；匹配必须大小写敏感（ai.state ≠ Ai.State）

3.2 域优先约定​

路径必须遵循 <域>.<实体>.<动作>，域在最前：

层级含义例子
域稳定、面向功能的分类notify、system、ai、sensor、log、metric、auth、task
实体信号的来源或主体web、file、state、temperature
动作具体发生了什么download、modified、progress、changed

正确与错误的对比例子：

写法评价
notify.web.download✅ 域优先：接收方 notify.** 一劳永逸覆盖全部现有与未来通知
web.notify.download❌ 实体优先：新增一个通知来源就要改过滤规则

域优先的规范后果：接收方应当按域为单位订阅（notify.**、log.**、metric.**），而不是按实体逐个订阅。这是「不为新增来源修改过滤规则」得以成立的前提。

3.3 与 Pattern ID 的区别​

路径用点号，Pattern ID 用斜杠，两者不得混用：

对象分隔符格式例子
Signal path.segment(.segment)*notify.web.download
Pattern ID/[namespace/]namemsp/publish-subscribe

不得在路径里出现 msp/... 形式的分段，也不得把路径当作 Signal.pattern 的值。

3.4 通配符​

通配符只允许出现在模式的末尾，且只允许两种形式：

形式名称语义
*单段通配恰好一段（≥ 1 个非空分段）
**多段通配零或多段（包含前缀本身）

必须满足：

通配符必须只出现在模式末尾。出现在中间的 * 是字面量，不会产生通配语义，且该模式永不匹配任何路径（见 §4.5 易错点 1）。

3.5 路径声明（可选）​

node.declare_signal(path, schema=None, description="") 可以把一条路径写进 Manifest.signals，供订阅者参考：

  • 这是声明，不产生信号；
  • schema 是可选的 JSON Schema，只用于对外宣告，发布时不做校验、订阅时不做强制；
  • signal_source 会隐式声明路径。

因此清单中的路径列表可以与运行时实际发布的路径不一致——实现不得把它当成准入清单。

4. 通配符匹配算法​

匹配是纯函数：pattern_matches(pattern, path) -> bool。接收方对每个注册的模式独立调用它。本节逐行对应参考实现。

4.1 算法​

pattern_matches(pattern, path):
    # 分支 1：精确相等
    if pattern == path:
        return True

    # 分支 2：多段通配 ".**"
    if pattern.endswith(".**"):
        prefix = pattern[:-3]                  # 去掉末尾 3 个字符 ".**"
        return path == prefix or path.startswith(prefix + ".")

    # 分支 3：单段通配 ".*"
    if pattern.endswith(".*"):
        prefix = pattern[:-2]                  # 去掉末尾 2 个字符 ".*"
        if not path.startswith(prefix + "."):
            return False
        return "." not in path[len(prefix) + 1:]   # 剩余部分不能再含点

    # 分支 4：其余一律不匹配
    return False

三条判定必须按上述顺序执行，命中即返回。

4.2 分支逐一说明​

分支条件结果关键点
1pattern == pathTrue无通配符的常规路径走这一支。注意：这一支对含 * 的字符串也生效——当模式与路径逐字相同时（例如两侧都是 ai.*）返回 True
2模式以 .** 结尾path == prefix 或 path.startswith(prefix + ".")prefix 是去掉 .** 后的剩余部分。注意 path == prefix 分支意味着 .** 匹配前缀自身（零段）
3模式以 .* 结尾前缀匹配且剩余部分不含点.* 不匹配前缀自身——它要求至少一段
4其它False这是「模式中间出现 *」与「模式不含通配符但不相等」的落点

4.3 按算法推导的匹配结果​

下表必须与实现一致：

模式语义匹配示例不匹配示例
ai.state精确ai.stateai.state.x、ai、ai.states
ai.*恰好一段ai.state、ai.progressai、ai.state.x
system.**零或多段system、system.cpu、system.cpu.load.1systematic、system.cpuX（不含点则 path == prefix 只对 system 成立）
*中间/落单通配符（字面量）——全部路径（恒为 False）
ai.*.state中间的 * 视为字面量——全部路径（恒为 False）
**不是以 .** 结尾——全部路径（恒为 False）
*.state中间的 * 视为字面量（不以 .* / .** 结尾，落第 4 分支）仅逐字相同的路径 *.state其余全部，含 ai.state、*.x、*.a.b
`` (空串)精确分支命中空路径空路径 ""其余全部

上表第 7、8 行的行为是算法的字面结果，不是设计意图。实现不得为了让它们「看起来更合理」而偏离算法——匹配规则是互操作契约的一部分（README.md §1.3 规定改匹配算法必须发新修订号）。

4.4 两个易错点（必须明确）​

易错点 1：通配符只在模式末尾有效，中间的 * 是字面量且恒不匹配。

ai.*.state 不会匹配 ai.cpu.state。算法的第 3 分支只认「以 .* 结尾」，而 ai.*.state 以 state 结尾，于是落到第 4 分支返回 False。同理：

  • system.*.cpu → 恒 False；
  • *.state → 仅当路径逐字等于 *.state 时为真，其余一律 False（它不以 .* 结尾，落第 4 分支）。

结论：需要「任意一层」时不得把 * 写在中间。改用 ** 放在末尾（ai.**），它会匹配 ai 及其下任意深度——代价是它也匹配单段与更深的多段，精度低于「恰好一段」。

易错点 2：空模式与「不含点号的前缀」按算法实际结果，不要臆测。

逐个推导（prefix 为空的情况）：

模式prefix分支 2/3 的实际行为实际结果
*不适用不以 .** 也不以 .* 结尾 → 落第 4 分支恒 False（除逐字相等的路径 "*"）
.*""第 3 分支：要求 path.startswith(".")，然后要求 path[1:] 不含点匹配 .a 这类路径（字面以点开头）；对 a.b 为 False
.**""第 2 分支：path == "" 或 path.startswith(".")匹配 "" 与任何以点开头的路径
system.*system第 3 分支：path.startswith("system.")，且 path[7:] 不含点匹配 system.cpu，不匹配 system（.* 不匹配前缀自身）与 system.cpu.load
system.**system第 2 分支：path == "system" 或 path.startswith("system.")匹配 system、system.cpu、system.cpu.load（.** 匹配前缀自身）
**不适用不以 .** 结尾（只有 2 个字符）→ 落第 4 分支恒 False

两个由此推出的规范级结论：

  1. system.* 不匹配 system，而 system.** 匹配 system。想「域下所有内容（含域本身）」必须用 .**。
  2. 裸 * 与裸 ** 都不是有效模式。它们恒不匹配（除逐字相等），应当被视为使用者笔误；实现可以在注册时警告，但不得把它们当成「匹配一切」的简写。

4.5 匹配的作用域​

场景是否使用路径通配符
signal 的本地回调过滤（on()）✅ 是
工具名（payload.tool）❌ 否——必须精确匹配（_tools 是字典查表）
Pattern ID（Signal.pattern）❌ 否——必须精确匹配（protocol.patterns 是字典查表）
node_id❌ 否——必须精确匹配（connections / _neighbors 是字典查表）
授权表的 pub / sub 条目✅ 复用 pattern_matches（security.md §3.3）
因此：工具调用不受通配符影响。声明 get_* 这样的工具名不会让 get_weather 可被 get_* 调用。

5. 消息流​

5.1 广播与本地过滤​

 发布方 node_c                                   接收方 node_d
      │                                              │
      │ 1. @node.signal("ai.state") 的生成器 yield    │
      │      {"status": "thinking", "seq": 0}        │
      │ 2. node.publish("ai.state", payload)          │
      │ 3. 加锁快照 connections ─────────────────────┐│
      │                                              ││
      │ ── signal(path="ai.state", payload=…) ──────▶│ 4. 读循环 _dispatch
      │        （对每个已连对端各发一份）             │     第 1 步不命中
      │                                              │     第 2 步不命中（pattern=None）
      │                                              │     → _dispatch_core → _on_signal
      │                                              │ 5. 遍历回调表
      │                                              │     on("ai.state") 命中 → 调用

      │                                              │ 6. 命中回调异常 → 记 warning，继续下一个
      ▼                                              ▼

5.2 扇出时的失败处理​

 publish(path, payload)
        │
        ├─ 加锁：peers = list(connections.items())
        │
        └─ for peer_id, conn in peers:
               try:
                   conn.send(encoded)
               except ConnectionClosed:
                   _handle_disconnect(peer_id, conn)   ← 清理该对端，继续下一个

必须：一个对端的发送失败不得中断循环，不得向外抛出异常。

5.3 「没有总线的总线」​

广播模型不需要中心 broker 就能拼出中间件拓扑：每个中间件就是一个普通节点。

 来源节点群                     中间件节点 fmt                观察者节点群
   │                              │                              │
   │ ── signal(log.app.raw) ────▶ │                              │
   │ ── signal(log.web.raw) ────▶ │                              │
   │                              │ @on("log.**") 收全部原始日志  │
   │                              │ 转换（时间戳、级别、脱敏）    │
   │                              │ publish("log.formatted.**")  │
   │                              │ ───────────────────────────▶ │ @on("log.formatted.**")
   ▼                              ▼                              ▼

规范条文：

  1. 中间件必须是一个普通 MSPNode——不得要求协议层提供任何 broker/代理角色；
  2. 中间件应当「订阅一个域、发布到另一个域」（log.** → log.formatted.**），使下游可以用域粒度切换「原始流」与「加工流」；
  3. 中间件不得修改它转发的路径语义——应当通过新增域或层级（log.formatted.*）来表达加工，而不是复用原路径；
  4. 中间件的转发不得造成同一路径上的自激循环（例如同时 @on("log.**") 与 publish("log.x")）；实现应当通过域隔离避免。

5.4 版本化路径​

路径是字符串，因此演进靠并行挂载而不是改语义：

做法评价
x.changed 与 x.changed.v2 并行发布✅ 推荐：老订阅者继续收 x.changed，新订阅者用 x.changed.v2；两者互不干扰，切换是订阅侧的选择
直接把 x.changed 的含义改成 v2❌ 不得：老订阅者会静默收到语义不同的数据

论证：

  1. 匹配算法是前缀式的。x.changed.** 会同时匹配 x.changed 与 x.changed.v2——因为第 2 分支要求 path == "x.changed" 或 path.startswith("x.changed.")，两种都成立。因此「用通配符一次订阅全部版本」可以做到，是升级期的便利。
  2. 精确订阅是隔离手段。只想锁定 v1 的订阅者用精确模式 x.changed，它不会匹配 x.changed.v2。
  3. 域优先约定让版本可以放在动作之后。<域>.<实体>.<动作> 的第三层是动作，版本号应当作为动作之后的新分段出现（x.changed.v2），不得插在域与实体之间（x.v2.changed 会破坏 x.** 的域粒度）。

应当：破坏性变更时同时发布旧版与新版至少一个版本周期，并在 Manifest.signals 中把两者都声明。

5.5 发布方的自我可见性​

发布不回环到本节点：publish() 只遍历 connections，调用方自己的 on() 回调不会被自己发布的信号触发。

必须明确这一点——实现不得依赖「本地发布也会触发本地回调」的假设：

  • 需要本地处理时必须在 publish() 之后直接调用本地函数，或可以实现一个显式的本地回环（非本规范要求）；
  • 这是与 MQTT 等「客户端订阅自己的主题会收到自己消息」的模型的已知差异，跨实现互操作时不得假设对方会回环。

6. 数据类型​

6.1 signal 信号的字段​

字段类型必需说明
type"signal"必须
sourcestr必须发布方 node_id；接收方可以据此做来源过滤（当前未实现，见 §10 G4）

payloadobject必须任意 JSON 对象；缺省 {}
targetnull必须广播无目标
patternnull必须核心模式不写路由键

JSON 示例：

{
  "type": "signal",
  "source": "node_c",
  "pattern": null,
  "target": null,
  "path": "ai.state",
  "reqid": null,
  "payload": {"status": "thinking", "seq": 0},

Signal 信封字段一律 snake_case。payload 内部字段名由发布者自定，应当与发布者 Manifest.signals[path].schema 的声明一致；接收方必须对未知字段宽容（不得因未知字段报错）。

6.2 回调注册项​

handlers 是 list[tuple[Optional[str], Callable]]：

没有注销 API、没有优先级、没有「只触发一次」语义。遍历顺序是注册顺序，但不得依赖顺序——见 §10 G2。

6.3 无订阅表​

必须明确：实现中不存在订阅表（PathMatcher 容器已在广播模型落地时删除）。

维度已删除的订阅表本模式的 handlerssub 授权过滤

sub 授权与已删除的订阅表形状相似但性质不同：订阅表回答「谁想要」，sub 授权回答「谁能看」。因此按安全需要加回 per-peer 过滤，不掺带宽优化（security.md §3.7）。

7. 边界​

7.1 通配符的用武之地​

场景说明
观察 / 监控面板on("metric.**") 一次覆盖全部指标
日志聚合on("log.**") 收全部日志域
权限审计on("auth.**") 收全部鉴权事件
粗粒度感知on("notify.**") 覆盖全部现有与未来通知来源
任务旁观on("task.**") 旁观 msp/task 的状态与产物广播

共同点：接收方预先不知道未来会出现哪些具体路径，但知道它们一定落在某个域下。这正是域优先约定的服务对象。

7.2 通配符不适用之处​

场景原因
工具调用payload.tool 必须精确匹配（_tools 字典查表）；工具名集合是封闭的、随握手宣告的
Pattern 路由Signal.pattern 必须精确匹配（protocol.patterns 字典查表）
node_id 定位连接表与邻居表是字典查表；node.connections() / on_connected 的 peer 参数都是精确 ID

不应把「通配符很方便」推广到这三处——它们都需要确定性：调用一个工具、路由一个模式、对着一个对端发包，都不能有「可能匹配到多个」的歧义。

7.3 已知行为边界​

边界说明
无送达确认publish() 返回 None，不知道谁收到了
无顺序承诺跨对端不同对端的接收顺序不保证一致
无去重同一路径收到两条内容相同的信号，必须当作两次事件
无历史晚连接的对端收不到连接前的信号；不得期待补发
无本地回环见 §5.5
无过滤下推见 §8

8. 安全考量​

8.1 广播 = 全发，无法按内容过滤​

必须认清本模式的默认形态：publish() 把信号发给每一个已连对端，不区分对象，也不看内容。

由此推出的规范后果：

  1. 发布敏感数据前，发布方必须确认接收面的信任假设：本机自组网下所有对端共享同一 OS 用户（§8.1 的前提，此时 sub 授权按设计整表绕过），跨机部署则必须配置 sub 授权——两者都不成立时，协议没有可依赖的拦阻；
  2. 需要「只给某些对端看」时，不得依赖路径命名（给路径起个晦涩名字不构成访问控制）；
  3. 正确的收窄手段是发送侧扇出过滤（sub 授权），见 §8.2。

8.2 sub 授权是发送侧扇出过滤（✅ 已实现）​

按 security.md §3.6 的设计，出站过滤的执行点只有一处：publish() 的扇出循环——每个对端查 sub 授权，未授权的跳过。

项规定状态
位置publish() 的扇出循环内，每个对端一次判定🔵 规划中（设计已定稿）
匹配方式复用 pattern_matches，对 sub 的 path 模式列表逐条比对🔵
默认sub: False（网络对端默认不收我的广播）🔵
本机例外loopback / UDS 同用户跳过整张授权表🔵
与订阅表的区别「谁能看」（安全），不是「谁想要」（带宽）—

必须：

  1. sub 过滤必须在发送侧执行——不得依赖接收方自律（接收方可能是攻击者）；
  2. 过滤不得改变报文字节（不裁剪 payload、不改 path），只决定「发或不发」；
  3. 未实现授权时必须在文档与部署说明中明确「广播对全部已连对端可见」，不得默默假定安全。

8.3 接收侧不受信任​

风险对策
恶意对端洪泛广播接收方应当做本地限流；协议层当前没有入站速率限制（§10 G5）
回调抛出异常被用作放大手段异常被捕获并记日志（§2.3 第 3 条）——但日志本身可能被洪泛淹没，实现应当做日志采样
回调中执行副作用回调运行在读循环线程；实现必须把重活移交给工作线程（§2.3 第 5 条）
payload 承载恶意内容接收方必须把 payload 当不可信输入解析；协议层不校验 payload 结构

8.4 路径命名不是权限​

不得用路径命名承担授权功能：

  • 路径是公开的（随广播发出，亦随 Manifest.signals 交换）；
  • 路径匹配是接收方本地行为，攻击者可以注册任意模式；
  • 因此「只有知道路径的人才能收到」不成立——在广播模型下，知道与否不影响是否收到，只影响是否处理。真正决定「是否收到」的只有发送侧的 sub 过滤。

辅助手段（可以采用，但不得当作唯一防线）：

  • 内容级加密：payload 用对端公钥加密，使无密钥的对端即使收到也读不出；
  • 分域发布：把敏感数据发到独立的传输/网络（如单独的 UDS 监听、单独的 TLS 通道），让不可信对端在传输层就够不着。

8.5 本机自组网的现实​

在默认部署形态（localhost 自组网、同一 OS 用户）下，security.md 的结论适用：所有节点权限集合相等，广播可见性不构成额外风险——能够连上来的进程本来就能读到同样的东西。

必须明确的反面条件：一旦把监听扩展到 0.0.0.0 或跨机，上述前提立即失效，此时必须同时具备 TLS + 节点认证 + sub 授权（见 security.md §2.4）。

10. 已知缺口​

#缺口影响依据
G1没有注销 API。handlers 只增不减，没有 off() / unsubscribe()动态订阅的生命周期只能靠「回调内部自行置标志位」模拟；长期运行且频繁注册的进程会持续增长MSPProtocol.on 只有注册路径；handlers 无移除点
G2无优先级的顺序依赖。回调按注册顺序遍历，且无「停止传播」机制实现不得依赖顺序；一个回调无法阻止后续回调运行_on_signal 的 for path_filter, func in handlers
G3pattern_matches 无输入校验。空模式、裸通配符、中间通配符都静默返回 False订阅写错时没有任何反馈——表现为「一条都收不到」matcher.py 第 36 行的兜底 return False
G4无来源过滤。on() 只有路径维度，没有 sig.source 维度无法「只听 node_a 的 notify.**」；节点通配是 DESIGN.md 记录的下一步handlers 的元素是 (path, callback) 二元组
G5无入站限速恶意对端可以洪泛广播耗尽接收方 CPU / 日志_on_signal 逐条即时处理，无令牌桶
G6sub 授权未实现 ✅ 已实现未授权的对端不再收到广播（发送侧逐对端过滤）publish() 的扇出循环逐对端调 grant_sub()（src/msp/protocol/protocol.py）；本机对端按设计整表绕过（security.md §3.5）。残留：pub / sub 没有「单模式全量放行」的写法（security.md §9 第 5 条）
G7发布无确认、无重传对端掉线期间的信号永久丢失；晚连接者拿不到历史publish() 返回 None
G8无本地回环与 MQTT 语义不同，跨实现互操作时容易踩坑publish() 只遍历 connections
G9payload 无 schema 校验declare_signal(schema=...) 只用于宣告，与 node.tool 的 inputSchema 同一缺口declare_signal 文档字符串明示「发布时不做校验」
G10节点层 on() 不支持 callback= 关键字node.on(path="x", callback=cb) 会失败；只能装饰器或直接用 node.protocol.on(...)MSPNode.on(path=None) 只接收一个参数
G11pattern_matches 对 pattern == path 的逐字分支若路径本身含 *（违反命名规范），含通配符的模式可能逐字命中，产生非预期匹配matcher.py 第 22–23 行
