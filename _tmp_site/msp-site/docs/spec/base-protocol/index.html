基础协议 — Base Protocol

协议修订 2026-10-10 ｜ 状态 ✅ 已实现（cancel / progress 为 🔵 规划中）

本页定义 MSP 的报文层：统一 Signal 信封、JSON / UTF-8 编解码、连接生命周期（握手、能力交换、心跳、关闭）、请求—响应关联（reqid）与错误处理。它对应 MCP 规范的 Base Protocol ——凡不属某个具体模式的行为，都定义在这里。

1. 概述​

MSP 只有一种报文：Signal。

握手、心跳、广播、工具调用、任务状态、错误通告，全部是 Signal 的实例，只有 type 字段不同。这是「Everything is a signal」在报文层的全部含义，也是本协议能被第三方独立实现的边界所在：理解本页 + 模式路由 即可实现一个可互通的节点。

报文层不定义任何交互语义。它只做四件事：

  1. 封装 —— 把一切交互装进同一个信封（§2）；
  2. 编解码 —— 信封 ↔ 字节（§3）；
  3. 维护连接 —— 建立、握手、去重、探活、关闭（§4）；
  4. 关联请求与响应 —— 用 reqid 把响应配回请求（§5）。

其余一切（工具怎么调、信号怎么广播、任务怎么委派）由模式层定义，协议层不认识它们（patterns.md）。

2. Signal 信封​

2.1 字段​

字段类型必填默认语义
typestring必须—信号类型。核心类型见 §2.2；模式可定义私有类型
sourcestring必须—发送方 node_id。必须与连接握手时声明的 node_id 一致（§4.3）
patternstring | null可选null路由键：该信号属于哪个通讯模式。命中已注册模式则交由该模式处理，否则走默认核心分发
targetstring | null可选null目标 node_id。点对点交互时填写；广播（signal）不得填写
pathstring | null可选null逻辑路径，用于发布—订阅（publish-subscribe）。必须符合 §2.4
reqidstring | null可选null请求 ID，用于把响应关联回请求（§5）
payloadobject可选{}负载。语义由 type + pattern 共同决定
timestampnumber可选发送方当前时间发送时间，Unix 秒（浮点）

pattern 字段是 MSP 的设计要点。 它把「该信号属于哪种通讯模式」显式编码进信号本身，协议层的分发因此只需做一次「按 pattern 查表路由」的判定，不需要理解任何具体模式的语义。这是模式层得以零改动扩展的关键，也是 MSP 与「用一个 method 字符串兼做路由」的协议（如 JSON-RPC）在信封层的根本差别。

2.2 核心信号类型​

以下 9 个类型（ping / pong 各算一个）由协议层自处理。其归属由 pattern 决定：pattern 为空的报文走协议层核心路径，语义与载荷由本规范冻结，不得被模式改写；带非空 pattern 的同名报文不属于核心路径，由该模式自行定义（见下方「模式私有类型」，以及 multi-round.md 的实例——它就用 tool_call / tool_result 作为自己的报文类型，载荷与核心略有差异）。

type分类有 reqid说明
hello请求否握手请求，payload.manifest 携带能力清单
ack响应否握手应答，payload.manifest 携带能力清单
ping请求否探活请求
pong响应否探活应答
signal通知否发布一条数据信号：path + payload
tool_call请求是工具调用请求：payload.tool / payload.args
tool_result响应是工具调用结果：payload.content / payload.structuredContent / payload.error
manifest_update通知否能力清单推送：payload.manifest
error通知视情况错误通告：payload.code / payload.message；回应某个请求时应当回填该请求的 reqid

分类规则（与 MCP 的 requests / responses / notifications 三分法同构）：

  • reqid 为空 → 通知：单程，接收方不得为之发送响应；
  • reqid 非空且类型属请求类 → 请求：接收方必须最终发送对应的响应或 error；
  • reqid 非空且类型属响应类 → 响应：仅用于唤醒等待中的调用方。

参考实现以 is_request() / is_response() 两个谓词给出当前判据：请求类 = tool_call / hello / ping；响应类 = tool_result / ack / pong。注意它们是判据不是机制——路由不依赖这两个谓词。

模式私有类型：模式可以定义自己的信号类型（如 input_required、task_submit）。规则有三：

  1. 必须同时携带非空 pattern，否则接收方无从路由；
  2. 可以复用核心类型的名字（msp/multi-round 即复用 tool_call / tool_result），但该报文必须携带本模式的 pattern，其 payload 形态由该模式定义——因此读到一个 type="tool_result" 的报文时，必须先据 pattern 判断它属于哪条语义路径，不得无条件套用核心载荷表；
  3. msp/ 前缀命名空间由本规范保留。第三方模式必须为自己的类型加自有前缀，避免跨模式撞名——因为 pattern 不同的两个模式可以安全地使用同名类型（路由键不同，见 patterns.md §3）。

2.3 宽容读取​

MSP 的信封必须按「宽容读取」处理（Postel 原则），这是互通的前提：

情形必须的行为
出现未定义字段忽略，不得报错
pattern 指向未注册的模式按无 pattern 处理，走默认核心分发；不得中断连接
type 为未知值应当回 error（code = -32600），回填原 reqid；不得中断连接
未知类型的内容块原样透传给上层（schema.md）
payload 缺字段缺失字段取该类型的默认值；不得因缺字段而崩溃

禁止的行为：因任何单条报文的内容问题而关闭连接。连接关闭只由传输层错误、心跳失联或去重仲裁触发（§4）。理由：报文错误是应用层问题，连接是全节点的共享资源，为一条坏消息拆掉整条连接会连带破坏该对端上的其它模式与在途请求。

2.4 路径语法​

path 必须符合以下文法：

path    = segment ( "." segment )*
segment = 1*( ALPHA / DIGIT / "_" / "-" )

分层约定：域优先——<域>.<实体>.<动作>，域在最前。

层级含义示例
域稳定、面向功能的分类notify, system, ai, sensor
实体信号的来源或主体web, file, state, temperature
动作具体发生了什么download, modified, progress

notify.web.download（而非 web.notify.download）：域是稳定、面向功能的分类，实体是可变、面向实现的来源。域放最前，接收方用 notify.** 即可一劳永逸地捕获全部现有与未来的通知，不因新增一个来源而修改过滤规则。

path 与 pattern 是两个不同概念，不得混用：path 是信号的逻辑地址（点号分层），pattern 是模式标识（斜杠分隔的全局命名空间，如 msp/multi-round）。

3. 编解码​

3.1 线格式​

Signal 必须编码为 UTF-8 编码的 JSON 对象：

# 编码（参考实现 protocol._encode）
json.dumps(signal.to_dict(), ensure_ascii=False).encode("utf-8")

由此得到三条规范要求：

  1. 字段名使用 snake_case（to_dict() 的键即线上字段名）。这与 Manifest 内部的 camelCase 是两套命名的分野：信封是 snake，清单与 payload 内部多为 camel（schema.md）。
  2. 非 ASCII 字符按原始 UTF-8 字节发送，不得转义为 \uXXXX。接收方必须按 UTF-8 解码。这使抓包与日志可直接阅读中文负载。
  3. payload 必须是 JSON 对象（可含任意嵌套值），不得是数组或标量。需要传数组时包一层键。

一条报文一个帧：信封不得被拆分到多个传输帧，传输帧不得包含多个信封——分帧由传输层负责（transports.md）。不得对 payload 另作压缩；大对象走 blob_ref 引用独立通道（schema.md）。

3.2 timestamp 的语义边界​

timestamp 是发送方本地时钟的读数，用于观测与诊断。

  • 应当填写；接收方可以忽略。
  • 不得用于因果排序、去重、幂等判定或超时计算——不同节点的时钟不保证同步，跨机时可能有任意偏移。
  • 需要判断新鲜度的场景（如声明过期）使用接收方自己的时钟测量本地观察到的间隔，而不是比较 timestamp 的绝对值（discovery.md）。

4. 连接生命周期​

4.1 状态机​

   ┌──────────┐  建立 TCP/WS/UDS 连接   ┌───────────┐
   │  空闲    │ ───────────────────────► │  已连接   │

4.2 握手​

握手是双向能力交换：双方在建立连接后立即交换各自的能力清单。它必须是连接建立后的第一对报文，任何其它报文不得先于握手发出。

  发起方 (dialer)                          接受方 (acceptor)
      │                                          │
      │  ── hello  {payload.manifest} ─────────► │
      │                                          │  记录 peer_manifests[peer]
      │                                          │  启动读循环
      │  ◄──────── ack  {payload.manifest} ───── │
      │                                          │
      │  记录 peer_manifests[peer]                │
      │  启动读循环                               │
      ▼                                          ▼

规范条文：

  1. 发起方必须以 hello 开启握手，payload.manifest 必须为发送方当前的能力清单（schema.md）。
  2. 接受方必须先校验首条报文是 hello；若不是，必须关闭连接。参考实现在此处抛错并关闭。
  3. 接受方若接受该连接，必须回 ack 且同样携带自己的能力清单。
  4. 双方必须在对端清单到达后才认为对端可用（peer.manifest 非空）。
  5. hello / ack 必须使用 source 声明发送方 node_id；该值随后成为本次连接的对端标识（peer_id）。
  6. 握手不得携带 reqid（能力交换是连接级事件，不是请求—响应）。

4.3 重复连接去重​

为什么需要：发现是对称的——A 发现 B 的同时 B 也发现 A，双方可能同时向对方拨号，于是同一对节点之间存在两条连接。两条连接会造成广播重复投递与请求状态分裂，因此必须仲裁为一条。

仲裁规则：

  1. 首条连接无条件登记，不论其方向。方向仲裁只在「同一 peer_id 已有连接」时生效。
  2. 已有连接时，以 node_id 的字典序决定规范方向：node_id 较小的一方必须是发起方（dialer）。 
    canonical_is_outbound = (self.node_id < peer_id)
  3. 新来的连接若符合规范方向 → 替换旧连接，旧连接被关闭（即「较小 ID 者拨号」的连接胜出）。
  4. 新来的连接若不符合规范方向 → 关闭新连接，保留旧连接。

必须注意的后果（接受方视角）：被判定为非规范方向的入站连接，接受方会直接关闭它且不回 ack。

必须注意的后果（发起方视角）：因此发起方在 receive() 上见到的是一次连接关闭，而不是显式的错误报文。参考实现把它归类为「对端不可达」，并写入连接冷却（connect_backoff，默认 5 s）。

这是既有行为，不是建议实现：两个同时拨号的节点最终仍会连上（另一方向的规范连接会建立），但被丢弃的那次拨号会留下一条无害的冷却记录。实现者若采用不同的去重算法（如连接建立后按既定规则择一保留、把落选方优雅关闭并回错误），必须保证：同一对节点在稳定状态下仅有一条活跃连接，且双方对「保留哪条」的判断一致——否则会出现双方各保留一条、广播重复投递的分裂状态。

断开时的自我保护：读循环结束时上报断开，但必须校验「当前登记的连接是否仍是我这条」。若该连接已被新连接替换，则不得清理状态——否则旧连接的断开会把新连接的状态误删。

4.4 能力清单交换与更新​

时机机制
连接建立hello / ack 的 payload.manifest
运行中变化manifest_update 广播给全部已连对端
查询缓存节点本地保存的 peer_manifests[peer_id]

规范条文：

  1. Manifest.version 必须单调递增（schema.md）。任何使清单内容发生变化的操作必须使其自增。
  2. 收到 manifest_update 时，接收方必须只在 new_version > current_version 时替换本地副本，否则必须丢弃该更新。这使乱序到达的推送不会让状态回退。
  3. manifest_update 不得携带 reqid，也不得要求应答；能力同步是单向的尽力而为（best-effort）通知。
  4. 节点不得假设对端已收到自己发出的 manifest_update。需要强同步时，以一次工具调用或重新握手为准。

4.5 心跳与失联判定​

参数默认含义
heartbeat_interval15.0 s心跳线程的 PING 周期
heartbeat_timeout45.0 s超过此时长未收到任何报文即判定失联
  每 15 s                                每个已连对端
     │  ── ping {target: peer} ─────────► │
     │  ◄──────────── pong ────────────── │
     │                                     │
  每 15 s 检查一次 _last_seen：
     now - last_seen(peer) > 45 s  →  判定失联，关闭连接

规范条文：

  1. 节点应当周期发送 ping（target 指向具体对端）。
  2. 收到 ping 必须回 pong，且 pong.target 必须为 ping.source。
  3. 失联判据是「任意报文的到达」，不是「收到 pong」。 参考实现在读循环中收到任何报文都会刷新 last_seen。这意味着一个持续发布信号但从不回 pong 的实现也可以存活——宽容处理，不构成违规。
  4. 判定失联后必须关闭连接并执行 §4.6 的清理；应当记录日志。
  5. 心跳不得被用作「对端应用健康」的判断——它只判断链路是否仍在工作。一个卡在长任务里的对端仍然会回 pong。

4.6 关闭与清理​

连接关闭（传输错误、心跳失联、stop()、对端主动关闭）时，必须原子地完成：

  1. 从 connections 移除该对端；
  2. 从 peer_manifests 移除其清单；
  3. 从 _last_seen 移除其记录；
  4. 唤醒该对端上所有在途请求，以 ToolResult(error=...) 返回——不得让调用方永久阻塞；
  5. 触发 on_disconnected(peer_id) 回调；
  6. 关闭底层连接。

第 4 条是本节最重要的一条。 它是「错误即值」在连接层的体现（request-reply.md §6）：对端消失是一个值，不是异常，调用方必须能收到它并继续运行。

节点停止（stop()）时，与关闭单个连接相同的清理必须施加于全部连接；此外必须停止心跳线程、撤销宣告、关闭全部监听套接字。

5. 请求—响应关联（reqid）​

5.1 生成与生命周期​

项规定
生成方发起请求的一方生成
格式16 位小写十六进制字符串（uuid4().hex[:16]），如 "3f2a91c0d4e8b7a5"
唯一性在同一连接的生命周期内不得复用
响应义务接收方必须在响应中原样回填 reqid
解除登记响应到达、超时、或连接断开时，发起方必须解除本地登记
超时发起方负责；默认 5.0 s。超时必须解除登记，必须以错误值返回给调用方

5.2 关联规则​

  调用方                                        被调方
     │                                             │
     │  1. reqid = 新生成                          │
     │  2. pending_calls[reqid] = (event, slot)     │
     │  ── tool_call {reqid, payload} ───────────► │
     │                                             │  3. 并发执行（独立线程）
     │                                             │  4. 结果写回
     │  ◄──────────── tool_result {reqid} ──────── │
     │  5. 按 reqid 命中 → 写入 slot → 唤醒         │
     │  6. 解除登记，返回 ToolResult                │
     ▼                                             ▼

规范条文：

  1. 响应必须按 reqid 匹配，不得按到达顺序匹配——同一连接上可以有任意多个并发在途请求，其响应可以乱序返回。
  2. 收到未知 reqid 的响应时，接收方必须静默丢弃（应当记日志）。典型成因是请求已超时并解除登记、或进程刚重启。不得因此中断连接或回错误。
  3. reqid 不得在 hello / ack / ping / pong / signal / manifest_update 上使用——这些是通知或连接级交互。error 可以携带 reqid 以指明它回应的是哪个请求。
  4. 模式可以引入自己的关联标识（如 msp/task 的 taskId），但凡复用请求—响应语义的交互，应当复用 reqid——msp/multi-round 与 msp/task 的追问都贯穿同一个 reqid 正是此意（multi-round.md）。

6. 错误处理​

6.1 两条错误通道​

MSP 刻意区分协议级失败与工具执行失败：

通道载体用于
错误即值tool_result.payload.error工具执行失败、对端不可达、超时、中途断连
error 信号payload.code + payload.message协议级失败：未知信号类型、参数不合法、内部错误

分界线：错误是否属于某一次调用的预期结果。是 → 走 tool_result（调用方拿到一个值，程序继续）；不是（整个报文都无法处理）→ 走 error 信号。

6.2 error 信号​

{
  "type": "error",
  "source": "node_a",
  "pattern": null,
  "target": "node_b",
  "path": null,
  "reqid": "3f2a91c0d4e8b7a5",
  "payload": { "code": -32600, "message": "未知信号类型: foo" },
  "timestamp": 1791321600.123
}

规范条文：

  1. 回应某个请求时，error 应当回填该请求的 reqid。
  2. error 必须携带 payload.code（整数）与 payload.message（字符串）。
  3. 收到 error 时，接收方必须记录日志；不得自动重试——重试策略属于调用方或模式层，协议层不代劳。
  4. 错误码取 JSON-RPC 2.0 的约定值，使工具调用子集可直接映射（interop.md）：
code名称出现位置
-32600无效请求收到未知 type
-32601方法不存在工具调用指向未注册工具
-32602参数无效参数不满足声明的 inputSchema
-32603内部错误工具执行中抛出异常
-32000 ~ -32099实现自定义保留给模式层；应当在实现文档中说明

6.3 取消​

状态：🔵 规划中。协议层当前没有取消机制。实现者可以不实现，但一旦实现必须符合以下条文。

新增核心信号 cancel：

字段值
type"cancel"
target必须为被取消请求的执行方
reqid必须为被取消请求的 ID
payload.reason可选，字符串，人类可读的取消原因

规范条文：

  1. 取消是协作式的：接收方应当尽快停止工作，但可以在停止前完成当前不可中断的步骤。
  2. 取消不得被依赖来保证正确性——发送方不得假设对端一定收到了 cancel，也不得假设对端一定停下了。
  3. 收到 cancel 后，接收方必须仍然发送该请求的终态响应（tool_result 带 error，或 msp/task 的 task_result 终态）。换句话说：取消改变的是结果，不是「是否应答」的义务。
  4. 对未知 reqid 的 cancel，接收方必须静默忽略。
  5. msp/task 的取消不走此信号，走模式自己的 task_cancel（task.md）。

6.4 进度​

状态：🔵 规划中。

新增核心信号 progress：

字段值
type"progress"
reqid必须为被跟踪请求的 ID
payload.progressToken必须，字符串，由发起方在请求的 payload.progressToken 中给出
payload.progress必须，数值，已完成量
payload.total可选，数值，总量；缺省表示总量未知

规范条文：

  1. progress 是通知：接收方不得为之应答。
  2. 同一 progressToken 的 payload.progress 必须单调不减；接收方应当忽略任何使进度回退的报文。
  3. 发起方若未在请求中给出 progressToken，执行方不得发送进度——无标识的进度无法关联。
  4. progress 可以被丢弃或合并；不得把它当作可靠传输使用。
  5. 缺省情况下进度不进入模型上下文；是否暴露给模型由宿主决定。

6.5 超时​

状态：🟡 部分实现。

当前仅实现调用方侧超时：call(timeout=5.0)，超时后解除本地登记并返回 ToolResult(error=...)。

已知缺口：协议没有服务端截止时间的概念——tool_call 不携带 deadline，被调方无法知道调用方已经放弃，因此仍在执行的工作不会被自动停止。补法是：① 引入 cancel（§6.3）；② 或在请求中加可选 payload.deadline，约定为发送方时钟的绝对时间，仅作提示、不得作为强约束（跨机时钟不同步）。

7. 规范条文汇总​

必须（MUST）：

  1. 一切报文必须是 Signal 信封，编码为 UTF-8 JSON 对象。
  2. type 与 source 必须存在；source 必须与握手时声明的 node_id 一致。
  3. 连接建立后必须先完成 hello / ack 握手，再交换其它报文。
  4. 同一对节点在稳定状态下必须只有一条活跃连接（§4.3）。
  5. Manifest.version 必须单调递增；只有更新版本才被接受。
  6. reqid 在一条连接内不得复用；响应必须原样回填 reqid。
  7. 响应必须按 reqid 匹配，不得按到达顺序匹配。
  8. 连接关闭时必须唤醒该对端全部在途请求，以错误值返回。
  9. 收到 ping 必须回 pong。
  10. 收到未知 type 应当回 error（-32600）；不得因此中断连接。
  11. 对未知字段、未知模式、未知内容块必须宽容处理。
  12. payload 必须是 JSON 对象。

不得（MUST NOT）：

  1. 不得为一条报文的语义问题关闭连接。
  2. 不得把 timestamp 用于排序、去重或超时计算。
  3. 不得用 reqid 承载通知类报文。
  4. 不得在 signal 广播上填 target。
  5. 收到 error 不得自动重试。
  6. msp/ 前缀不得被第三方模式占用。

应当（SHOULD）：

  1. manifest_update 应当在能力变化后尽快推送。
  2. 失联判定应当以「任意报文到达」为判据，而不是仅看 pong。
  3. 收到未知 reqid 的响应或 cancel 应当静默忽略并记日志。

8. 安全考量​

  1. source 不可信。 source 是发送方自报的字段。协议层当前不校验它是否与连接的握手身份一致（因为信任边界就是传输可达范围，见 security.md）。跨机部署时必须在握手阶段做身份绑定，否则任何能连上来的节点都能冒充任意 node_id，搅乱去重与发现注册表。
  2. reqid 是本地标识，不是授权凭据。 不得把「持有某个 reqid」当作有权接收该响应的证明；响应的接受方由连接身份决定。
  3. manifest 是自述，不是承诺。 节点可以在清单里宣告自己并不实现的工具。安全判断不得依据对端清单，必须依据本地授权表（security.md）。
  4. payload 无大小限制。 协议层不设消息上限；实现应当在传输层或解码前设置上限，否则一个超大帧即可耗尽内存。
  5. error.message 可能泄露内部信息（如异常文本）。实现应当区分「对外错误文案」与「内部日志文案」。
  6. 心跳不构成存活证明。 心跳只反映链路；一个被攻陷但仍在回 pong 的节点与正常节点在协议层无法区分。

9. 已知缺口​

#缺口后果补法
1握手无读超时 ✅ 已修复对端 accept 了 TCP 却永不回 ack 时，发起方的 receive() 曾永久阻塞该线程Connection.set_read_timeout() + MSPProtocol.handshake_timeout（默认 10 s，可经节点 config 覆盖）：超时以 ConnectionClosed 结束、关闭连接并计为不可达
2无取消机制调用方超时放弃后，被调方的工作继续跑到结束，白烧算力实现 cancel（§6.3）
3无进度上报长任务对调用方是黑盒，只能靠轮询——这正是本协议要消除的形态实现 progress（§6.4）
4无背压 / 流控send() 阻塞在慢对端上，会拖住广播扇出循环传输层加发送队列上限与丢弃策略；或引入窗口协商
5无消息大小上限超大帧导致内存风险解码前设上限并回 error
6无服务端 deadline见 §6.5随 cancel 一并设计
7去重丢弃连接时不回 ack发起方只能从连接关闭推断失败，且留下无害冷却记录在关闭前回一个 error 说明原因
8error 无结构化详情调用方只能读到字符串payload.data 承载结构化详情（MCP error.data 同构）
9一次性 stream/blob 通道未定义大对象只能内嵌 Base64，膨胀 33%blob_ref + msp/streaming（patterns.md §6）
