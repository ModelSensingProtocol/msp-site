MSP 规范 — 能力面：resources / prompts / sampling / elicitation / roots

协议修订2026-10-10
状态🔵 规划中 — 报文已完整定义，参考实现尚未落地
上游依据../DESIGN.md「能力面：resources / prompts / sampling」、../whitepaper.md §5
本页定义MCP 能力面（resources / prompts / sampling / elicitation / roots）到 MSP 信号的完整映射、报文形态、消息流、错误归属与安全条文

本页把 MCP 在工具之外的能力面翻译成 MSP 信号。全部条文标 🔵：实现者可以不实现，但一旦实现必须符合条文。

1. 概述​

1.1 范围​

MCP（Model Context Protocol）在 tools 之外还有五组能力。按「Everything is a signal」（README §4），它们在 MSP 里不是五套机制，而是几组新的 Signal.type：

MCP 能力解决的问题MSP 落点
resources对端把上下文数据以 URI 暴露出来，本端按需读取resource_read / resource_content；订阅侧 resource_subscribe / resource_unsubscribe / resource_updated
prompts对端预定义可复用提示模板，本端取值后由对端渲染prompt_get / prompt_content
sampling本端执行中需要「让某个模型生成一段」，向持有 LLM 的对端发反向请求sampling_request / sampling_result
elicitation本端需要用户决策或输入，向持有用户界面的对端征询elicitation_request / elicitation_result
roots一个节点单向声明自己允许被访问的文件系统根，供对端裁剪范围roots_list / roots / roots_changed

MCP 的 */list 往返（resources/list、prompts/list、resources/templates/list）在 MSP 中没有对应信号，见 §2.2。

1.2 与索引和信封的关系​

本页定义的是一个规划中的新能力面：它不属于任何已注册的模式（README §5.2 的模式表保持不变），也不改变 README §5.1 已冻结的核心信号类型。

  • 信号命名：本页的 type 取值逐字取自 ../DESIGN.md 的映射表，一律为裸 snake_case；msp/ 前缀是模式 ID 与第三方模式私有信号类型的命名空间（README §1.4、§5.3、base-protocol §2.2），不出现在本页的 type 取值里。
  • 路由：本页全部信号不携带 pattern（pattern = null），由协议层的默认核心分发处理，论证见 §3.1。
  • 与 cancel / progress 的关系：核心已在 README §5.1 把二者列为 🔵 规划中的核心信号（条文见 base-protocol §6.3–6.4）。本页不重复定义其报文，只声明两条交互：请求方可以用 cancel 取消在途的 resource_read / sampling_request / elicitation_request（按被取消请求的 reqid 关联，协作式，且不免除应答义务）；执行方在请求方给出 payload.progressToken 时可以用 progress 上报进度。
  • 与索引的差异：本页的信号类型尚未进入 README §5.1 的表。并入核心表必须走 README §8 的演进流程并新增修订行；本页不修改索引。

实现收到本页未识别的信号类型时，不得断开连接，应当按 base-protocol §2.3 宽容读取处理；参考实现的现有行为是回 error（code = -32600，见 §9.1）。

1.3 内容承载​

资源内容、提示消息与采样结果一律复用 ../src/msp/core/content.py 的内容块（§5.1），不新造数据类型。

2. 映射与契约​

2.1 MSP 映射表​

下表与 ../DESIGN.md「MSP 映射：全部是信号」逐行一致：

MCP 操作MSP 信号方向
resources/readresource_read → resource_content读取方 → 资源持有方 请求 / 应答
resources/subscriberesource_subscribe / resource_unsubscribe → resource_updated订阅方 → 资源持有方 请求；持有方 → 订阅方 通知
prompts/getprompt_get → prompt_content调用方 → 提示持有方 请求 / 应答
sampling/createMessagesampling_request → sampling_result生成请求方 → 生成提供方 反向请求 / 应答
elicitation/createelicitation_request → elicitation_result征询方 → 用户宿主 反向请求 / 应答
roots/listroots_list → roots / roots_changed询问方 → roots 宿主 请求 / 应答；宿主 → 全部已连对端 通知

「反向」指请求方是 MCP 里的 server 角色；MSP 不预设角色，方向由能力声明决定（§2.3）。

2.2 取舍一：清单即列表，省掉 list 往返​

MCP 的「列出有什么」是一次额外往返：resources/list（可带 cursor 分页）、prompts/list、resources/templates/list。MSP 不设这些信号，因为清单本身就是列表：① Manifest.resources / Manifest.prompts 的 ResourceDescriptor（uri / name / description / mimeType / subscribable）与 PromptDescriptor（name / description / arguments）必须随 HELLO / ACK 交换（base-protocol §4.4）；② 清单变化时 manifest_update 推送新清单，接收方按 version 丢弃过期项；③ 于是「列出」是握手与推送的副产品。本页只定义 read / get 这类取值操作，其入参（uri / name）必须来自对端清单，取值方应当先做本地校验，避免用取值请求探测清单。

两条推论：收到清单中不存在的 uri / name 时，持有方应当在应答载荷的 error 字段说明失败，不应当当作协议错误（§6.1）；MCP 的 resources/templates/list（URI 模板）没有对应物——ResourceDescriptor 没有模板字段，需要模板语义时必须按 README §8 追加清单字段与新修订号，不得在本修订内私自扩展 uri 语法。分页同理：MSP 清单交换没有 cursor / nextCursor，应当一次性给出完整清单（§9.3）。

2.3 取舍二：反向能力是全双工的天然优势​

展开 ../DESIGN.md「三个关键取舍」的第 2 条。MCP 里 sampling / elicitation 之所以是「反转」，原因是角色：initialize 把两端固化为 client 与 server，client 在自己的 capabilities 里声明 sampling / elicitation / roots，于是「请求生成」「征询用户」必须由 server 侧发起、client 侧应答，能力位挂在 client 上。MSP 没有这种角色固化：双方都能主动发信号，sampling_request 与 tool_call 在协议层完全同构——同一条连接、同一个 reqid 关联机制（base-protocol §5）、同一套超时规则，差别只有 type、方向与载荷形状。因此不需要「角色翻转」机制，也不需要在握手时确认谁是 client；但能力位仍然必需（§2.5），且同一份实现可以既提供工具（rep）又请求生成（clientCapabilities.sampling = true）。

注意：方向不是理由。JSON-RPC 2.0 只定义单条消息的形状，不限制哪一方发起；MSP 与它的差别在信封字段，不在方向（见 interop）。

2.4 取舍三：资源订阅与路径过滤是两个维度​

展开 ../DESIGN.md「三个关键取舍」的第 3 条。MSP 已有发布—订阅：publish(path, payload) 把 signal 扇出到全部已连对端，接收方用 node.on(path) 做本地通配匹配（patterns/publish-subscribe、../src/msp/protocol/matcher.py）。一个自然的想法是让资源变更也走这条路，于是「订阅资源」退化为「订阅某个 path」。本页不采用，因为两个维度不同：路径过滤的寻址单位是 path（点号分段、域优先，base-protocol §2.4），匹配方式是发送方广播 + 接收方本地 * / ** 过滤，扇出到全部已连对端；资源订阅的寻址单位是 URI（file://、db://，含 /、:、.），匹配方式是请求—确认式点对点订阅、持有方维护订阅表，只扇出给订阅了该 URI 的对端。

把 URI 塞进 path 会让 path 不再承担「域优先的功能分类」，且需要为 /、:、. 设计转义，破坏 base-protocol §2.4 的文法（segment = 1*( ALPHA / DIGIT / "_" / "-" )，/ 与 : 都不合法）。所以单设 resource_subscribe，寻址单位是 URI。两者可以并存：持有方可以在资源变更时额外 publish 一条路径信号供旁观者使用，但 resource_updated 不得依赖它，订阅方也不得用路径过滤代替订阅声明。

2.5 能力声明与授权​

能力声明是自述（「我自称会什么」），与授权（「我允许你做什么」）严格分离（README §5.5）。因此：提供方必须把可读取的资源与可渲染的提示声明进 Manifest，未声明的 uri / name 不得被取值成功；subscribable = false 的资源不得被订阅成功；声明不得作为授权依据（接收方不得因对端声明了某能力就放宽本地授权，发送方也不得因对端声明了 clientCapabilities.sampling = true 就认定对方一定响应）；收到未声明能力位的请求时，接收方应当回 error（code = -32601，§6.2），与「调用未注册工具」同构。授权见 security。

3. 报文​

3.1 共同规则​

本页全部信号使用 base-protocol §2 的 Signal 信封，字段级条文以该页为准。pattern 取值：本页全部信号的 pattern 必须为 null（或缺省），即它们不属于任何模式。理由：① ../DESIGN.md 的补法明确是「给 _dispatch_core 加分支（与 tool_call 同构）」，而 _dispatch 只把带 pattern 的信号交给模式处理器（../src/msp/protocol/protocol.py MSPProtocol._dispatch），其余走 _dispatch_core；base-protocol §2.1 也把 pattern 默认值定为 null。② 这五组能力的声明已经住在 Manifest 里（resources / prompts descriptor 与 clientCapabilities 三个布尔位），再引入模式 ID 会让同一件事在两处声明。③ 每个信号都是形状固定的一次性操作，不构成「一类交互的语义集合」（README §4 对「模式」的定义）；先例是 tool_call / tool_result——它们是核心类型，而 msp/multi-round 在需要时用同一 type 加 pattern 覆盖路由。④ 因此本页的信号既不是 base-protocol §2.2 那 9 个核心类型（索引表 8 行，因 ping / pong 合并为一行），也不是「模式私有类型」（后者必须携带非空 pattern），而是规划中能力面的追加类型，按 README §1.2 第 2 条的增补规则给出。

其余共同条文：

  • source 必须是发送方自己的 node_id；target 上，请求与响应必须填接收方的 node_id（定向单播），roots_changed 必须为 null（广播给全部已连对端，与 signal 一致）。接收方收到 target 非空且不等于自身 node_id 的信号时应当忽略（现有核心分支不检查 target，本条为新增条文）。
  • path 必须为 null：本页信号不得用 path 承载 URI。
  • reqid：请求与响应必须携带，且响应的 reqid 必须原样回填请求值；reqid 必须是发送方在本次连接生命周期内唯一的非空字符串；resource_updated（event = "changed"）与 roots_changed 是通知，不得携带 reqid。分类规则与 base-protocol §2.2 一致：reqid 为空即通知，接收方不得为之应答。
  • 请求可以携带 payload.progressToken（string），供执行方用核心 progress 上报进度（base-protocol §6.4）。

信号总表（分类按 base-protocol §2.2 的三分法）：

type分类有 reqid方向
resource_read请求是读取方 → 资源持有方
resource_content响应是资源持有方 → 读取方
resource_subscribe / resource_unsubscribe请求是订阅方 → 资源持有方
resource_updated响应（subscribed / unsubscribed）/ 通知（changed）前者是，后者否资源持有方 → 订阅方
prompt_get请求是调用方 → 提示持有方
prompt_content响应是提示持有方 → 调用方
sampling_request / sampling_result请求 / 响应是生成请求方 ↔ 生成提供方（反向）
elicitation_request / elicitation_result请求 / 响应是征询方 ↔ 用户宿主（反向）
roots_list / roots请求 / 响应是询问方 ↔ roots 宿主
roots_changed通知否roots 宿主 → 全部已连对端

一次请求的线格式（信封字段名与 base-protocol §2.1 一致）：

{"type": "resource_read", "source": "agent_a", "pattern": null, "target": "file_monitor",
 "path": null, "reqid": "9f2c1ab34d5e6078", "payload": {"uri": "file:///tmp/report.md"},
 "timestamp": 1786000000.0}

3.2 resource_read / resource_content​

信号字段类型必填说明
resource_readpayload.uristring是必须是对端清单中已声明的 ResourceDescriptor.uri
resource_contentpayload.uristring是回填请求的 uri
resource_contentpayload.contentarray<ContentBlock>是可以为空数组；块类型见 §5.1
resource_contentpayload.mimeTypestring否与清单 mimeType 一致时可以省略
resource_contentpayload.errorstring否非空表示读取失败；此时 content 应当为空数组

失败形态：payload.error 非空（错误即值，§6.1）。二进制资源应当用 resource 块内嵌（小对象）或 blob_ref（大对象，§5.2）；不得在 resource_content 里内联超出接收方缓冲上限的字节。

3.3 resource_subscribe / resource_unsubscribe / resource_updated​

订阅、退订都是请求；接受与否用同一条 resource_updated 确认，用 event 区分三种事件，从而不为一个空 ACK 增加信号类型。

信号字段类型必填说明
resource_subscribepayload.uristring是必须指向 subscribable = true 的资源
resource_subscribepayload.ttlnumber否订阅存活秒数；缺省表示持续到连接断开或显式退订
resource_unsubscribepayload.uristring是退订目标
resource_updatedpayload.uristring是被订阅资源的 URI
resource_updatedpayload.eventstring是"subscribed" / "changed" / "unsubscribed"
resource_updatedpayload.contentarray<ContentBlock>视 eventsubscribed 与 changed 必须携带；unsubscribed 不得携带
resource_updatedpayload.versioninteger否资源版本号，单调不减，用于检测乱序与丢失

确认与变更的线格式（信封同 §3.1）：

// 订阅确认（响应，reqid = 请求的 reqid）
{"type": "resource_updated", "source": "file_monitor", "target": "agent_a",
 "reqid": "5b1e77c0a9d34f21",
 "payload": {"uri": "file:///tmp/report.md", "event": "subscribed",
             "content": [{"type": "text", "text": "# Report\n..."}], "version": 7}}
// 变更通知（通知，reqid 缺省）
{"type": "resource_updated", "source": "file_monitor", "target": "agent_a",
 "payload": {"uri": "file:///tmp/report.md", "event": "changed",
             "content": [{"type": "text", "text": "# Report\n... (v8)"}], "version": 8}}

条文：持有方接受订阅时必须立即以同一 reqid 回 event = "subscribed" 作为确认与初始快照，拒绝时必须回 error（§6.2）不得沉默；接受退订时必须以同一 reqid 回 event = "unsubscribed"，此后不得再向该对端发送该 uri 的任何 resource_updated；变更通知不得携带 reqid，version 不单调时接收方应当按最新值覆盖而不得视为协议错误；连接断开时该连接上的全部订阅必须失效，重连后必须重新订阅（订阅是连接级状态，不随 Manifest 交换）；ttl 到期时持有方应当停止推送并可以静默停止；ttl 不得被用作授权。

3.4 prompt_get / prompt_content​

信号字段类型必填说明
prompt_getpayload.namestring是必须是 Manifest.prompts 中已声明的 PromptDescriptor.name
prompt_getpayload.argumentsobject否键为 PromptDescriptor.arguments[].name，值为 string
prompt_contentpayload.namestring是回填请求的 name
prompt_contentpayload.messagesarray<object>是元素为 {"role": "user"|"assistant", "content": ContentBlock}；可以为空数组
prompt_contentpayload.description / payload.errorstring否渲染后的说明（缺省沿用清单值）/ 非空表示渲染失败，此时 messages 应当为空数组

arguments 不满足清单声明的参数时，持有方应当在 error 里说明（而不是协议错误）。渲染是提供方职责，调用方不得假设渲染结果与清单描述逐字一致。

3.5 sampling_request / sampling_result​

sampling_request.payload（字段名与 MCP sampling/createMessage 对齐，便于互通）：

字段类型必填说明
messagesarray<object>是元素为 {"role": "user"|"assistant", "content": ContentBlock}
systemPromptstring否系统提示
includeContextstring否"none" / "thisServer" / "allServers"（MCP 语义；实现可以忽略并视为 "none"）
modelPreferencesobject否{"hints": [{"name": string}], "costPriority", "speedPriority", "intelligencePriority"}，优先级取 0~1
maxTokens / temperature / stopSequencesinteger / number / array<string>否生成上限、采样温度、停止串
metadataobject否实现自定义元数据
progressTokenstring否进度标识（§3.1）

sampling_result.payload：role（string，必须为 "assistant"）、content（ContentBlock，单块，与 MCP CreateMessageResult.content 一致）、model（string，实际使用的模型标识，供请求方记账与复现）、stopReason（string，可选，如 "endTurn" / "maxTokens"）、error（string，可选，非空表示宿主拒绝或生成失败）。error 为空时 role / content / model 必须存在；error 非空时三者应当省略。 宿主可以拒绝（额度、隐私、策略），但拒绝必须通过 error 字段或 error 信号表达，不得沉默丢弃。

3.6 elicitation_request / elicitation_result​

信号字段类型必填说明
elicitation_requestpayload.messagestring是向用户呈现的问题文本；必须按不可信输入处理（§8）
elicitation_requestpayload.requestedSchemaobject是受限 JSON Schema：type 必须为 "object"；properties 的值必须是原始类型或 enum；required 为属性名数组
elicitation_resultpayload.actionstring是"accept" / "decline" / "cancel"
elicitation_resultpayload.contentobject视 actionaction = "accept" 时必须存在且必须满足 requestedSchema；其余取值不得携带

action = "decline" / "cancel" 是成功应答而非错误：请求已被正确处理，只是用户不同意或撤回了操作。宿主不得为这两种取值发送 error 信号。

3.7 roots_list / roots / roots_changed​

roots_list.payload 为空对象 {}（保留以承载未来扩展）。roots 与 roots_changed 的 payload.roots 必须是数组，元素为 {"uri": string, "name": string}：uri 必须是绝对 URI，name 可以为空串。

方向说明：../DESIGN.md 该行标注为「client→server 通知」，那是按 MCP 的 client / server 角色描述的。MSP 不预设角色（README §4），本页改用可判定的表述：roots 由声明了 clientCapabilities.roots = true 的节点（下称 roots 宿主）持有；roots_list 由任何已连对端发给宿主；roots、roots_changed 由宿主发出。这与 MCP 中「server 向 client 请求 roots」的形状一致。

条文：宿主应当在接受握手后主动发送一次 roots_changed（无 reqid，target = null）；roots 变化时必须发送 roots_changed；询问方收到后应当以最新值覆盖本地缓存，不得因为 roots 与 roots_changed 不一致而断开连接；收到 roots_list 但自身 clientCapabilities.roots = false 时必须回 error（code = -32601）；roots 不得被当作访问控制——它是声明不是授权，接收方不得因为某个路径不在 roots 里就认为对端允许访问其余路径（README §5.5）。

4. 消息流​

4.1 资源订阅 + 变更通知​

 agent_a（订阅方）                        file_monitor（资源持有方）
   │ HELLO / ACK：交换 Manifest              │
   │ ← resources[file:///tmp/report.md]      │
   │    .subscribable = true                 │
   │ ─ resource_subscribe ─────────────────▶ │ reqid=r1 {uri, ttl}
   │                                         │ 登记订阅表
   │ ◀ resource_updated ──────────────────── │ reqid=r1 event=subscribed
   │   {uri, event:"subscribed", content:[…]}│ 确认 + 初始快照
   │                       （文件被写入）     │
   │ ◀ resource_updated ──────────────────── │ 无 reqid event=changed
   │   {uri, event:"changed", version:8}     │
   │ ─ resource_unsubscribe ───────────────▶ │ reqid=r2 {uri}
   │ ◀ resource_updated ──────────────────── │ reqid=r2 event=unsubscribed
   │ （此后不再收到该 uri 的任何更新）        │

4.2 反向 sampling 请求​

 worker（生成请求方）                    llm_host（生成提供方）
   │ HELLO / ACK：清单里                    │
   │ clientCapabilities.sampling = true     │
   │ ─ sampling_request ──────────────────▶ │ reqid=s1
   │   {messages, systemPrompt, maxTokens}  │ 交给本机 LLM
   │ ◀ sampling_result ───────────────────  │ reqid=s1
   │   {role:"assistant", content, model}   │
   │ （宿主拒绝：payload.error 非空，        │
   │   或 error 信号 -32601）               │
   │ 与 tool_call 同构：同一连接、同一 reqid  │
   │ 关联、同一超时规则，方向相反而已。       │

4.3 elicitation 与取消​

elicitation 的消息流与 §4.2 同构，只是把 sampling_request / sampling_result 换成 elicitation_request / elicitation_result，且 action = "decline" / "cancel" 属成功应答。二者与核心 cancel / progress（base-protocol §6.3–6.4）的组合如下：

 agent_a（请求方）                     file_monitor（执行方）
   │ ─ resource_read ───────────────▶ │ reqid=r3 {uri:"file:///big.bin",
   │                                  │            progressToken:"p-num-1"}
   │ ◀ progress ───────────────────── │ reqid=r3（通知，不得应答）
   │   {progressToken, progress:40, total:100}
   │ ─ cancel ──────────────────────▶ │ reqid=r3 {reason:"用户取消"}
   │ ◀ resource_content ──────────── │ reqid=r3 终态 {uri, content:[],
   │                                  │   error:"已取消"}——取消改变的是结果，
   │                                  │   不是「是否应答」的义务

5. 数据类型​

5.1 内容块​

资源内容、prompt_content.messages[].content、sampling_request.messages[].content 与 sampling_result.content 必须使用 ../src/msp/core/content.py 中已定义的内容块类型：

type关键字段用途
texttext（必填）、annotations（可选）文本资源与提示
image / audiodata（Base64，必填）、mimeType（必填）图片 / 音频
resourceresource: {uri, mimeType, text?, blob?}内嵌文本或二进制资源
resource_linkuri、name、mimeType、description只给引用，内容由接收方自行取值
blob_refblobId、mimeType、size、checksumMSP 扩展：指向独立 blob 通道（§5.2）

接收方遇到未知块类型时必须原样保留（宽容读取，base-protocol §2.3；block_from_dict() 的行为），不得视为协议错误。

5.2 blob_ref 与大对象​

resource 块把字节内嵌进信号，受传输分帧与内存限制。超过实现自定阈值（应当在文档中声明，例如 1 MiB）的资源应当改用 blob_ref：blob_ref 只携带 blobId / mimeType / size / checksum，字节走独立的 blob 信号流（msp/streaming 规划中，见 README §5.2）；checksum 应当是全量内容的摘要，接收方取回后应当校验；blobId 必须在当前连接内唯一；收到 blob_ref 但未实现 blob 通道时，接收方应当回 resource_content.payload.error 说明失败，不得静默丢弃。

5.3 Manifest 声明槽​

声明槽源码形态本页用法
Manifest.resourcesarray<ResourceDescriptor>，序列化键 resources「列出有什么」的唯一来源；subscribable 决定是否可订阅
Manifest.promptsarray<PromptDescriptor>，序列化键 prompts同上；arguments 描述 prompt_get 的入参
Manifest.clientCapabilities.sampling布尔，序列化键 clientCapabilities.sampling是否接受 sampling_request
Manifest.clientCapabilities.elicitation布尔，序列化键 clientCapabilities.elicitation是否接受 elicitation_request
Manifest.clientCapabilities.roots布尔，序列化键 clientCapabilities.roots是否持有并宣告 roots

这三个客户端能力位在源码中已存在（supports_sampling / supports_elicitation / supports_roots，序列化为 clientCapabilities），但 README §5.5 的「角色能力位」表只列出 pub / sub / req / rep，未收录它们。本页因此把三者记为「源码已存在的声明槽」，不改动索引、也不把新语义塞进 pub/sub/req/rep（差异见 §9.3）。

6. 错误处理​

6.1 两条失败通道​

沿用 base-protocol §6.1：错误即值指请求已被正确解析、已路由到正确的提供方，业务上失败（URI 不存在、资源不可订阅、提示名不存在、参数不满足声明、生成失败）时，在应答信号的 payload.error 里放字符串，reqid 不变，不得再发 error 信号；协议层失败（未实现该信号、reqid 缺失、payload 不是对象、未声明该能力位）则发 error 信号，payload 为 {"code": <int>, "message": <string>}（base-protocol §6.2）。elicitation_result.action 取 decline / cancel 属于成功，不得走任一失败通道（§3.6）。

6.2 错误码归属​

失败情形通道code / 字段
收到未实现的能力面信号类型，或 reqid 缺失、payload 不是对象error 信号-32600
本节点未声明该能力（清单无 resources / prompts，或对应 clientCapabilities 位为 false）error 信号-32601（与「调用未注册工具」同构）
uri / name 不在对端清单中，或资源 subscribable = false应答载荷 error无 code
prompt_get.arguments 不满足 PromptDescriptor.arguments，或 elicitation_result.content 不满足 requestedSchema应答载荷 error无 code
提供方在渲染 / 生成应答时抛出未预期异常error 信号-32603
未在超时内收到应答本地超时（实现自定异常）不得发送 error
target 非空且不是本节点忽略并记日志不得回 error（避免环回）
收到未知 reqid 的 cancel静默忽略（base-protocol §6.3）—

-32000 ~ -32099 保留给模式层（README §5.4）。本页信号不携带 pattern，不得使用该区间；收到该区间的 error 时应当原样透传给上层而不是改写（见 interop 的桥接降级策略）。

6.3 超时、取消与进度​

未显式指定时，请求方应当沿用 call 的默认超时 5.0 s（README §5.6）；sampling_request 与 elicitation_request 依赖模型或人，应当使用更长的超时，但本页不冻结该值（msp/multi-round 的 ctx.ask() 用 30.0 s 作为参考，它不在 README §5.6 的冻结默认参数表内，实现可以自定）。请求方超时后必须丢弃该 reqid 的迟到应答，不得把它当作下一条请求的结果；协议没有服务端截止时间的概念（base-protocol §6.5），执行方不一定知道调用方已放弃。显式取消必须使用核心 cancel 信号（协作式、按被取消请求的 reqid 关联、收到后仍必须发送终态响应），本页信号不得自定义取消报文，msp/task 的取消走模式自己的 task_cancel。执行方在请求携带 payload.progressToken 时可以用核心 progress 上报进度，不得把 progress 当作可靠传输。

6.4 与 msp/multi-round 的关系​

elicitation_request / elicitation_result 与 msp/multi-round 的 input_required / input_response 都能达到「追问」的效果，但语义不同（逐信号差异另见 patterns/multi-round §6.8）：

msp/multi-roundelicitation_request
请求标识必须沿用原 tool_call 的 reqid，整段交互一个 reqid自己新开一个 reqid，不延续原调用
触发位置只在一次工具调用的执行过程中（ctx.ask()）任何时刻，包括没有工具调用时
前提对端必须激活 msp/multi-round 模式（pattern 字段）对端必须声明 clientCapabilities.elicitation = true
载荷{"prompt": string} / {"answer": 任意 JSON}{message, requestedSchema} / {action, content}，content 可被机器校验
声明位置Manifest.patternsManifest.clientCapabilities.elicitation

选择依据：追问属于「这一次工具调用缺参数」时应当用 msp/multi-round（同一 reqid，调用方有 input_fn 参与，失败降级目标是 msp/request-reply）；需要脱离工具调用向用户提问（执行前策略确认、选择资源范围），或对端没有激活 msp/multi-round 时应当用 elicitation_request；需要结构化、可校验的答案时应当用 elicitation_request（content 受 requestedSchema 约束，而 multi-round 的 answer 只是任意 JSON）；需要模型生成内容而不是向人提问时，两个都不得使用，必须用 sampling_request。

7. 规范条文汇总（MUST/SHOULD 清单）​

必须：① 全部信号的 pattern 为 null，source 为发送方 node_id，请求与响应携带 reqid 且响应原样回填（§3.1）；② resource_read 的 uri 来自对端清单，resource_content 携带 uri 与 content（§3.2）；③ 订阅被接受时立即回 event = "subscribed" 并带初始快照，被拒绝时回 error（§3.3）；④ 退订被接受时回 event = "unsubscribed"，此后不再推送该 URI（§3.3）；⑤ event = "changed" 的 resource_updated 与 roots_changed 不带 reqid，unsubscribed 不带 content（§3.1、§3.3）；⑥ 连接断开时该连接上的订阅全部失效，重连后重新订阅（§3.3）；⑦ 收到 roots_list 而自身 clientCapabilities.roots = false 时回 -32601（§3.7）；⑧ requestedSchema 的 type 为 "object"、properties 的值为原始类型或 enum（§3.6）；⑨ 能力面失败按 §6.1 走对应通道，不得两者并用；⑩ 未知块类型与未识别的信号类型不得被视为协议错误或导致断开（§5.1、§1.2）；⑪ 取消使用核心 cancel，收到后仍发送终态响应（§6.3）。

应当：⑫ 取值前本地校验 uri / name 是否在对端清单中（§2.2）；⑬ blob_ref 的 checksum 存在并在取回后校验，大对象阈值在实现文档中声明（§5.2）；⑭ sampling / elicitation 的超时长于 call 默认值，超时后丢弃迟到应答（§6.3）；⑮ roots 宿主在握手后主动发一次 roots_changed（§3.7）。

不得：⑯ 用 path 承载 URI（§3.1）；⑰ 把 roots 或 ResourceDescriptor.subscribable 当作授权依据（§2.5、§3.7）；⑱ 使用 -32000 ~ -32099 错误码区间（§6.2）；⑲ 把 ttl / maxTokens 等载荷字段用作访问控制（§3.3）。

可以：⑳ 资源变更时额外 publish 一条路径信号，但 resource_updated 不得依赖它（§2.4）；㉑ 忽略 includeContext 并视为 "none"（§3.5）；㉒ ttl 到期时静默停止推送（§3.3）；㉓ 请求携带 payload.progressToken，执行方用 progress 上报进度（§3.1、§6.3）。

8. 安全考量​

信任边界是传输可达范围，认证不等于授权（security）。

  1. 数据外泄面：resource_read 与 resource_subscribe 让对端持续或按需获取本机数据。提供方必须在授权层按 URI 前缀做判定，不得只依据清单声明（清单是自述）；订阅是持续数据流，应当默认短 ttl 并可即时退订。
  2. 提示注入面：prompt_content.messages 的文本会进入请求方的模型上下文，请求方应当把它标注为外部不可信内容，不得当作系统指令执行。
  3. 反向生成面：sampling_request 把对端的提示词送进本机 LLM，存在提示注入与额度滥用风险。宿主必须能拒绝，并应当按来源节点做策略判定；宿主不得因为 source 自报的身份就放宽策略（README §5.5）。
  4. 面向人的征询面：elicitation_request.message 是外部不可信文本，宿主必须在呈现时标明来源 sig.source；requestedSchema 不得用于构造可执行动作（例如「输入要执行的命令」），只应当用于结构化选项。
  5. roots 与扇出面的误用：任何把 roots 当作白名单或黑名单的实现都偏离 §3.7 的条文；roots_changed 广播给全部已连对端，订阅表按对端维护，二者都有放大风险。实现应当对订阅数量、单条 content 体积、单位时间推送次数设上限，超限时应当回 error 而不是静默降级。

9.2 补法​

  1. 在 SignalType 追加本页 §3.1 总表列出的 14 个类型名（与唯一权威源 schema/2026-10-10/msp.yaml 的条目数一致）。
  2. 在 MSPProtocol._dispatch_core() 追加分支，与 tool_call / tool_result 同构：请求分支解析 payload、按 reqid 关联，响应分支唤醒等待方。所有可能耗时的操作（资源读取、提示渲染、模型生成、向人征询）必须在独立线程执行，不得在读循环线程里同步执行——理由与 MSPProtocol._on_tool_call() 的注释一致：慢操作会阻塞该连接的消息接收，且操作内部若回调对端会死锁。
  3. 在 MSPNode 层追加装饰器与方法：@node.resource(uri, ...)、@node.prompt(name, ...)、node.read_resource(peer, uri)、node.get_prompt(peer, name, arguments)、node.subscribe_resource(peer, uri)、node.sample(peer, ...)、node.elicit(peer, ...)、node.set_roots([...])，以及接收侧的 node.on_resource_updated(...)。这些名字是规划 API，不构成规范常量；条文只约束 §3 的报文形态。
  4. 复用既有能力，不新造：内容块用 core/content.py 与 block_from_dict()；结果规范化可复用 _normalize_tool_result()；请求—应答的等待/唤醒结构可参照 MultiRoundHandler 的 _pending_calls / _active_asks；取消与进度直接复用核心 cancel / progress（base-protocol §6.3–6.4），不得为能力面另造一套。
