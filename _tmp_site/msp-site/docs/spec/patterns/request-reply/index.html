核心模式：请求—响应（msp/request-reply）

协议修订2026-10-10
状态✅ 已实现
本页定义核心通讯模式 msp/request-reply：tool_call / tool_result 的完整载荷字段、reqid 关联与并发隔离、调用方与被调方的逐步流程、返回值规范化规则、「错误即值」语义、工具注册与超时语义、错误码归属边界

本页是 patterns.md 的具体化。模式层契约、路由判定顺序、PatternHandler 与本文无关——msp/request-reply 是核心模式，直接实现在协议层，不进 PATTERN_REGISTRY，也没有 Handler 实例。

1. 概述​

msp/request-reply 是 MSP 的最低公分母：一条 TCP 连接 + Signal 信封 + 本模式，两个各自独立实现即可互相调用工具（README.md §7）。

它的语义一句话：A 向 B 发一条带 reqid 的 tool_call，B 在独立线程里执行工具，回一条带同一个 reqid 的 tool_result；A 靠 reqid 从 pending_calls 中找回自己的等待者。

与 JSON-RPC 2.0 的语义对应关系见 interop.md：

MSPJSON-RPC 2.0
reqidid
payload.toolmethod
payload.argsparams
payload.content / payload.structuredContentresult
payload.errorerror.message
type: "tool_call"request
type: "tool_result"response

2. 契约​

2.1 reqid​

项规定
类型str
生成必须由发起方生成，Signal.new_reqid()，即 uuid.uuid4().hex[:16]（32 位十六进制取前 16 位）
位置Signal.reqid（信封字段，不是 payload 字段）
语义在一对连接上唯一标识一次请求；tool_result 必须回显同一个值
生命周期发起时登记进 pending_calls，收到结果或超时后必须注销

必须满足：

  1. tool_call 必须携带非空 reqid。被调方收到 reqid 为空的 tool_call 必须直接忽略（当前实现即 return，见 §11 G1）。
  2. tool_result 必须回显 reqid。接收方对未知 reqid 的 tool_result 必须静默忽略——它不是错误，通常只是「我早已超时放弃」的迟到回包。
  3. reqid 不得在 payload 内重复出现。

2.2 pending_calls​

协议层用一个受 threading.Lock 保护的字典登记未完成的请求：

self.pending_calls: dict[str, tuple[threading.Event, list]] = {}
#                        reqid          (event,        [peer_id, result])

必须满足：

  1. 登记发生在发包之前（否则对端回包可能先于登记到达）。实现的顺序是：生成 reqid → 建 Event → 加锁写入 pending_calls[reqid] = (event, [peer_id, None]) → _send(...)。
  2. 等待者只可以通过 event.wait(timeout) 阻塞；不得轮询 pending_calls——那是忙等。
  3. 结果写入由读线程完成（_on_tool_result）：加锁取回 (event, holder)，写 holder[1] = ToolResult(...)，再 event.set()。
  4. 注销由等待者完成，且必须从字典弹出（pop），否则字典无界增长。
  5. 并发隔离：不同 reqid 的条目互不影响，因此同一连接上可以有任意多个在飞请求；不同线程并发 call() 是安全的。
  6. peer_id 存在 holder[0]，用于连接断开时按对端批量唤醒。

2.3 结果读取路径​

tool_result 到达
      │
      ├─ reqid 为空 ─────────────────▶ 忽略
      │
      └─ 加锁查 pending_calls[reqid]
             ├─ 未登记（已超时/已注销）─▶ 忽略
             └─ 命中
                  holder[1] = ToolResult(
                      content    = payload.get("content", []),
                      structured = payload.get("structuredContent"),
                      error      = payload.get("error", ""),
                  )
                  event.set()          ← 唤醒 call()

注意 structuredContent 的缺省值是 None（dict.get 的无默认重载），而 content / error 的缺省分别是 [] / ""。

2.4 超时后的清理​

event.wait(timeout) 返回 False 时必须：

  1. 加锁 pending_calls.pop(reqid, None) —— 注销条目，防止迟到回包误唤醒；
  2. 抛 TimeoutError(f"调用 {tool} 超时")。

node.call() 会把该 TimeoutError 转换为 ToolResult(error="调用 <tool> 超时")（§6）。

3.4 content 块类型​

content 数组的元素必须是 §5.2 列出的块之一。未知 type 的块必须原样保留（宽容读取），不得因此报错或丢弃整个结果。

4.1 时序图​

4.2 调用方逐步​

步动作失败时的表现
1node.call(peer_id, tool, args, timeout=5.0)—
2ensure_connected(peer_id)：已连接直接返回；未知节点抛 UnknownPeer；拨号/握手失败抛 PeerUnavailable；冷却期内抛 PeerUnavailable转 ToolResult(error=str(e))（§6）
3生成 reqid、登记 pending_calls—
4发 tool_call（_send 在未连接时抛 RuntimeError）转 ToolResult(error="未连接到 <peer>")
5event.wait(timeout)超时 → 注销条目 → TimeoutError → 转 ToolResult(error="调用 <tool> 超时")
6醒来后 pop 条目，取 holder[1]若期间断开，holder[1] 已被读线程写为 ToolResult(error="连接断开")
7返回 ToolResult—

4.3 被调方逐步​

步动作依据
1读线程收到 tool_call_read_loop
2_dispatch 第 1 步不命中（tool_call 不是核心信号类型）→ 第 2 步不命中（pattern 为 None）→ 第 3 步_dispatch
3_dispatch_core 命中 SignalType.TOOL_CALL → _on_tool_call_dispatch_core
4reqid 为空 → 直接返回（忽略）_on_tool_call
5取 tool = payload.get("tool")、args = payload.get("args", {})同上
6起独立线程执行 _run_tool，读循环立即返回同上，见 §4.4
7工作线程查 _tools[tool]；未注册 → raise ValueError(f"未知工具: {tool}")_run_tool
8调用 func(**args)，规范化返回值_run_tool + _normalize_tool_result
9发 tool_result；_send 失败（对端已断）只记调试日志，不得重试_run_tool

4.4 为什么必须在独立线程执行​

读循环线程（_read_loop）是该连接唯一的消息接收者。若在被调方在读循环线程里同步执行工具：

  1. 阻塞该连接的消息接收。一个 30 秒的慢工具会让这条连接 30 秒内收不到任何消息——包括心跳 ping，于是对端按 heartbeat_timeout（默认 45 秒）判定失联并断开；也收不到同一连接上的其它 tool_call（并发度退化为 1）。
  2. 工具内部回调对端会死锁。这是更严重的一条：多轮模式的服务端在工具执行中调用 ctx.ask() 向调用方追问，然后阻塞等待 input_response。而 input_response 正需要读循环来接收——读循环却在等工具返回。互相等待，永久死锁。

因此规范条文：

被调方必须在独立线程中执行工具函数，不得在协议层读循环线程内同步执行。

参考实现在 MSPProtocol._on_tool_call 的文档字符串里把这两条理由都写明了，并注明与 msp/multi-round 的 _run_tool 同理。

5. 数据类型​

5.1 ToolResult​

node.call() 的返回值。定义在 src/msp/core/content.py。

成员类型缺省说明
contentlist[]content 块列表
structuredAnyNone结构化结果（对应线上 structuredContent）。注意本地属性名是 structured，线上字段名是 structuredContent
errorstr""失败原因
方法 / 属性返回值语义
is_errorboolbool(self.error) —— 只要 error 非空串即为错误
unwrap()Anyerror 非空时抛 ToolError(error)；否则返回 structured
text()str把所有 type="text" 块（dict 或对象）的文本用 "\n" 拼接

必须满足：

  1. content / structured / error 三者不得同时表达矛盾语义。规范要求：error 非空时 structured 的含义未定义，调用方应当先查 is_error。
  2. 不得用 content 是否为空判断成功失败——成功也可能没有 content 块（例如工具返回 None）。

5.2 content 块类型​

type关键字段说明
texttext（str）、可选 annotations纯文本
imagedata（Base64）、mimeType、可选 annotations图片
audiodata（Base64）、mimeType、可选 annotations音频

块内字段名混用两种风格，必须逐字遵守：mimeType、blobId 是 camelCase；annotations、text、data、uri、size、checksum、description 无大小写歧义；resource 是嵌套对象而不是块自己的键。

未知 type 的块必须原样返回（block_from_dict 对未知类型返回输入 dict 本身），不得抛错。

5.3 返回值规范化规则​

_normalize_tool_result(result) 返回 (content_blocks, structured_data) 二元组。工具函数的返回值必须按以下顺序判定，命中即返回：

#输入形态contentstructured备注
1None[]None显式空结果
2非空 list 且每个元素都是 content 块逐元素 to_dict() 后的列表None「已经是 content 块列表」
3单个对象且有 to_dict()[result.to_dict()]None「单个 ContentBlock」
4str[{"type": "text", "text": result}]result（同时给）字符串既当 content 又当 structured
5其它（dict / list / int / float / bool）[{"type": "text", "text": json.dumps(result, ensure_ascii=False)}]result结构化数据

判定「是不是 content 块」的规则（_is_content_block）：有 to_dict 属性，或是含 "type" 键的 dict。普通数据 dict（如 {"name": "Alice"}）不算 content 块——这是为了不让结构化数据被误判成块列表。

5.3.1 空列表陷阱（易错点，必须注意）​

判定顺序中的第 2 分支带一个非空前置条件：

if isinstance(result, list) and result and all(_is_content_block(b) for b in result):

若不写 and result，那么 all(...) 对空列表恒为 True，于是：

  • 工具返回 [] 会被当成「空 content 块列表」，structured 变成 None；
  • 实际期望是走第 5 分支——content 得到一条 text 块 "[]"，structured 得到 []。

因此：

返回值 [] 必须走结构化分支（第 5 分支），得到 content=[{"type": "text", "text": "[]"}]、structured=[]。

参考实现在源码里以注释显式标注了这个陷阱（「注意：空列表 [] 走结构化分支，避免 all() 恒真的陷阱」）。

5.3.2 为什么 content 与 structuredContent 同时给​

第 4、5 分支同时填两个字段，原因是两类消费者：

  • 面向人 / 面向模型的消费者读 content——它已经是可直接渲染的块（文本、图片…），不需要知道原始 Python 类型的 JSON 表示；
  • 面向程序的消费者读 structuredContent——它保留原始数据结构（dict / list / 数值），unwrap() 直接把它交回，避免「先 JSON 序列化、再解析回来」的往返。

二者不得被视为冗余而省略其一：省略 structuredContent 会迫使程序消费者解析文本块；省略 content 会使结果在只懂 content 块的实现（MCP 风格）里不可读。

6. 错误处理​

6.1 错误即值​

node.call() 对对端侧的一切失败一律返回 ToolResult(error=...)，不得抛出异常打断调用方；只有程序性错误才 raise。

程序性错误指「调用方自己用错了 API」，例如把 args 传成 None（func(**args) 会 TypeError，但那发生在被调方）、或对未注册的 node 对象调用方法。必须显式拿到异常时，用 ToolResult.unwrap() —— 它在 error 非空时抛 ToolError。

6.2 五类失败与 error 文案来源​

#失败触发点error 文案来源文案形态
F1对端不可达ensure_connected → PeerUnavailableMSPNode.call 的 except (PeerUnavailable, UnknownPeer)节点 <id> 不可达: <e> 或 节点 <id> 疑似失效，冷却中
F2未知节点ensure_connected → UnknownPeer同上未知节点 <id>，无法连接
F3调用超时MSPProtocol.call → TimeoutErrorMSPNode.call 的 except (TimeoutError, ...)调用 <tool> 超时
F4中途断连_handle_disconnect 写入 holder[1]协议层直接构造连接断开
F5协议已停止MSPProtocol.stop 写入 holder[1]协议层直接构造协议已停止

补充一条同通道的失败：

#失败触发点error 文案归属
F6发包时发现未连接_send → RuntimeError未连接到 <peer>MSPNode.call 的 except (TimeoutError, ConnectionClosed, RuntimeError)

必须满足：

  1. F1–F6 全部必须以 ToolResult(error=...) 返回；调用方不得为了捕获它们而包裹 try/except。
  2. 对端侧的失败（F3 除外）必须由调用方本地判定，不得依赖对端发 error 信号——对端可能已经死了，发不出任何东西。
  3. F5 的覆盖范围：stop() 只唤醒 holder[1] is None 的条目，因此已经拿到 F4 结果的调用不会被 协议已停止 覆盖。

6.3 工具侧的失败与错误码归属​

工具执行失败有两条通道，边界必须清楚：

协议错误信号层级的问题：未知 typeerror 信号-32600

错误码归属边界（对照 README.md §5.4）：

-32602参数不满足工具声明的 inputSchema🟡 未在核心协议层落地：核心不做 schema 校验（§7.3），参数不匹配表现为 TypeError → payload.error 字符串

6.4 未知工具的具体行为​

被调方收到指向未注册工具的 tool_call：

  1. _run_tool 中 self._tools.get(tool_name) 返回 None → raise ValueError(f"未知工具: {tool_name}")；
  2. 异常被 _run_tool 的 except Exception as e 捕获 → payload = {"content": [], "error": str(e)}；
  3. 发 tool_result（不是 error 信号），reqid 回显。

因此不会产生协议层 error 信号。协议层的 error（-32600）只在未知 type 时发出。这条边界不得混淆：把「未知工具」升级成 error 信号会破坏 reqid 关联（error 信号虽带 reqid，但接收端没有对应的唤醒路径）。

7. 工具注册​

7.1 装饰器签名​

@node.tool(name, description="", input_schema=None)
def my_tool(...) -> ...: ...
参数类型缺省说明
namestr必须工具名，必须精确匹配调用方的 payload.tool；必须符合 [a-z0-9_-]+
descriptionstr""人类可读描述，进 Manifest
input_schemadict | NoneNone参数 JSON Schema

注册动作必须同时完成三件事：

  1. manifest.add_tool(ToolDescriptor(name=..., description=..., input_schema=schema)) —— 进能力清单，随握手交换；
  2. protocol.tool(name)(func) —— 进协议层的 _tools 派发表，运行时只查这张表；
  3. _push_manifest() —— 若已连接则推 manifest_update。

7.2 input_schema 的产生​

  • 缺省（input_schema is None）：由 schema_from_func(func) 从函数签名自省生成（含 Annotated 参数描述）；
  • 显式传入：以传入为准，不得与自省结果合并。

细节（Annotated 描述、Field 约束、enum、Optional[Literal] 的 anyOf 表达、零硬依赖 Pydantic 兼容）见 schema.md。

inputSchema 也是客户端生成调用接口的依据。 对端可以把清单里的 inputSchema 投影成宿主语言的可调用接口（参考实现：peer.t，见仓库 README 的「把对端的工具当函数调用」）。由此：

  • 提供方应当让 inputSchema 与实现一致——它不再只是给人看的说明，而是对端生成 API 的依据；
  • 但参考实现当前不保证：schema_from_func 不产出 default，pydantic v2 下 Field(ge=…) 一类约束会静默丢失（见 schema.md 的「边界行为与脆弱性」）。因此生成方必须按「认不出就退化为 Any」处理，不得假定约束存在；
  • JSON Schema → 宿主语言的映射是客户端行为，非规范性。 它不在线上、不构成互操作面，不得被写进本规范；线上只多这一条：inputSchema 是宣告契约的一部分。

7.3 自省结果只用于宣告（已知缺口）​

自省 / 显式传入的 inputSchema 不参与运行时校验——但这不等于它「只是说明」：它同时是对端生成调用接口的依据（§7.2），因此提供方应当让它与实现一致。

即：Manifest 里会如实列出参数约束，但被调方的 _run_tool 只做 func(**args)，不校验 args 是否满足 inputSchema。

后果必须如实预期：

  1. 缺少必填参数 → TypeError → payload.error（不是 -32602）；
  2. 多传参数 → TypeError: unexpected keyword argument → payload.error；
  3. 类型不符（如把 "3" 传给 int）→ 不报错，函数体拿到 "3"，行为由工具自身决定。

因此：

需要参数校验的实现必须在工具函数内部自行校验，不得假设框架会拦下非法参数。将来若加入运行时校验，报文形态可以通过在同一修订内「追加」payload.code 完成（README.md §1）。

7.4 声明的工具与派发表的一致性​

Manifest.tools 与 protocol._tools 是两张独立的表，同一次 @node.tool 会同时写两张。实现不得只写其中一张——只写清单会出现「宣告了但调不通」，只写派发表会出现「调得通但别人不知道」。

8. 超时、连接兜底与生命周期​

8.1 超时语义​

项规定
缺省5.0 秒（README.md §5.6）
作用域只覆盖等待 tool_result 的时间，不覆盖 ensure_connected 的拨号与握手
超时行为注销 pending_calls[reqid] → raise TimeoutError(f"调用 {tool} 超时") → MSPNode.call 转 ToolResult(error="调用 <tool> 超时")
超时后的迟到结果_on_tool_result 查不到 reqid → 静默忽略；不得记成错误
被调方的执行超时不通知被调方，工具照常执行完毕（其 tool_result 会被忽略）。需要真正取消长任务请用 msp/task 的协作式取消

8.2 ensure_connected 兜底​

ensure_connected(peer_id) 是所有需要连接的用户 API 的统一入口（call / fetch_manifest）。行为：

状态行为
已在 protocol.connections立即返回（无锁快路径）
在 _neighbors 且未连接取该 peer 的连接锁（_connect_locks[peer_id]），锁内二次检查后拨号 + 握手
不在 _neighborsraise UnknownPeer(f"未知节点 {peer_id}，无法连接")
在冷却期（_unavailable[peer_id] > now）raise PeerUnavailable(f"节点 {peer_id} 疑似失效，冷却中")
拨号 / 握手失败记 _unavailable[peer_id] = now + connect_backoff（默认 5.0 s）并抛 PeerUnavailable；不删邻居
拨号成功清除 _unavailable[peer_id]

必须满足：

  1. 每个对端必须有独立的连接锁（「每个对端一把连接锁」），避免并发触发重复建连；
  2. 锁内必须二次检查 connections，防止等锁期间对端已由他人连上；
  3. 冷却失败不得删除 _neighbors 条目——声明文件还在，硬删会让该对端永久失去（DESIGN.md 的「软标记与硬清理分离」）；
  4. connect_policy="lazy" 的节点必须由本方法按需建连，不得期望发现层替它连。

8.3 RuntimeError("未连接到 X") 的转换​

MSPProtocol.call 在第一步就检查 if peer_id not in self.connections: raise RuntimeError(f"未连接到 {peer_id}")；_send 在找不到连接时抛同样的 RuntimeError。

MSPNode.call 的 except (TimeoutError, ConnectionClosed, RuntimeError) 必须把它转成 ToolResult(error="未连接到 <peer>")。转换不得吞掉其它异常类型。

8.4 连接丢失时的清理​

_handle_disconnect(peer_id, conn) 必须：

  1. 若传入的 conn 已不是当前登记的那条（去重场景下被淘汰的旧连接），必须直接返回，不得误删新连接的状态；
  2. 清理 connections / peer_manifests / _last_seen；
  3. 遍历 pending_calls，把 holder[0] == peer_id 的条目写成 ToolResult(error="连接断开") 并 event.set()（唤醒所有等待者）；
  4. 在锁外关闭连接，避免 shutdown 阻塞持锁；
  5. 调用 _on_disconnected 回调。

10. 安全考量​

  1. 工具调用是最需要授权的动作。 按 security.md 的设计，req 授权（允许对端调我的哪些工具）必须在 _dispatch 的最前面执行，工具名列表必须精确匹配（True = 全部）。参考实现尚未落地授权（见 §11 G6），因此不得把当前版本暴露到不可信网络。
  2. pattern 不能充当访问控制。 路由契约规定未登记 pattern 的信号降级到核心分发（patterns.md §3.4），所以给 tool_call 加一个未登记的 pattern 不会让调用失败——它仍会被执行。访问控制必须基于 payload.tool。
  3. 参数未经校验即执行。 §7.3 的缺口意味着 args 直接进入 func(**args)。工具实现必须把参数当作不可信输入处理（路径穿越、命令注入、反序列化）。
  4. error 文案会泄漏内部信息。 F1–F6 与工具异常都直接用 str(e)，可能泄露文件路径、依赖版本、SQL 片段。面向不可信对端的实现应当在回包前做错误信息脱敏，并在本地日志保留原文。
  5. 一个连接上的请求数无上限。 pending_calls 没有容量限制，客户端可以发起任意多并发调用。面向不可信对端的实现应当加 per-peer 在飞请求上限。
  6. 工具在线程池外执行。 每次 tool_call 起一个 daemon 线程，没有并发上限。占用型工具的洪泛会耗尽线程资源——这属于部署层面的限流责任，不得指望协议层拦截。

11. 已知缺口​

#缺口影响依据
G1reqid 为空的 tool_call / tool_result 被静默忽略，无日志、无回包调用方会一直等到超时_on_tool_call / _on_tool_result 的 if not reqid: return
G2-32601 / -32602 / -32603 在核心协议层无实现，仅在 JSON-RPC 桥中定义payload.error 是纯文本，程序化分派需要适配层全代码库仅 mcp/jsonrpc.py 使用这三个常量
G3inputSchema 不参与运行时校验非法参数只能靠工具自己挡（§7.3）_run_tool 直接 func(**args)

G5_run_tool 的 except Exception 过宽，会把 KeyboardInterrupt 之外的编程错误一并当成工具业务错误实现 bug 被报成业务失败，难以区分except Exception as e: payload = {..., "error": str(e)}
