MSP 数据模型参考 —— JSON 形态的完整字段定义

协议修订2026-10-10
状态✅ 已实现（Signal / Manifest / Endpoint / 内容块 / Preset 的全部字段与序列化形态；grants 等规划字段标注为 🔵）
本页定义各页报文所用的全部数据模型：Signal 信封、Manifest 与四个 descriptor、Endpoint、声明文件、内容块、ToolResult、核心与模式私有载荷、schema_from_func 的产出规则、Preset 与内置预设

规范性用语与状态标记见规范索引 §2；正文中加粗的关键词承担规范效力。

字段的权威源是 schema/2026-10-10/msp.yaml——字段名、类型、必填性、默认值、约束，以及 Signal.type（+pattern）→ payload 的绑定关系，都只在那一个文件里定义；由它生成 msp.schema.json（JSON Schema 2020-12）供第三方实现与校验器消费，生成物不要手改。

本页是它的解释性视图：负责讲清「为什么这样设计」与「序列化时有哪些坑」，字段清单不得在别处再抄一份。两者不一致时以 YAML 为准，并视为本页缺陷——tools/check_schema_drift.py 会把「权威源 ↔ 参考实现 ↔ 本页」三方的不一致报出来，tests/test_schema_source.py 让它成为测试失败。

1. 概述​

类型记号约定​

记号含义
string / integer / number / booleanJSON 标量：字符串 / 整数 / 数（含浮点） / 布尔
objectJSON 对象（键为字符串的映射）
array<T>元素类型为 T 的 JSON 数组；array<string> 即字符串数组
map<K, V>以 K 为键、V 为值的对象（序列化后仍是 object）
A | B联合类型：取值属于 A 或 B 之一
nullJSON null
T?（如 string?）可选字段：报文中可以缺省或为 null
any任意 JSON 值（对象、数组、标量、null 均可）

「必填」列描述报文中的必填性，「默认」列描述读取方在字段缺省时必须采用的语义——它不要求发送方省略该字段：参考实现的 Signal.to_dict() 会写出全部 8 个键（含 null），接收方必须同时容忍显式 null 与缺省。

序列化总则​

  1. 命名风格分区：Signal 信封的 8 个字段是 snake_case；payload 内部字段、Manifest 及其 descriptor、内容块中的 MSP 扩展字段多为 camelCase（如 structuredContent、inputSchema、taskId、blobId）。字段名必须逐字一致，不得混用。
  2. 编码：JSON 文本、UTF-8；参考实现用 json.dumps(..., ensure_ascii=False)，非 ASCII 原样传输。
  3. 分帧：TCP / UDS 为 4 字节大端长度前缀 + 负载；WebSocket 用二进制帧；单条消息上限 16 MiB。
  4. 宽容读取：未识别的字段、信号类型、内容块类型、模式 ID 不得被视为协议错误而断开连接（README §7）。
  5. 键序无意义：除 Manifest.capabilities 被实现为 sorted 外，键序不构成语义。

2. 模型与契约​

Signal 信封​

Signal 是「万物皆信号」的统一数据原子：握手、广播、工具调用、任务、心跳都是它的实例，区别只在 type。

字段类型必填默认语义与约束
typestring是—信号类型：SignalType 的 9 个核心值之一，或模式私有类型（必须同时带 pattern）
sourcestring是—发送方 node_id，[a-z0-9_-]+（README §5.3）
patternstring?否null路由键：模式 ID。核心信号通常为 null；模式私有信号必须携带
payloadobject否{}类型相关载荷，结构由 type + pattern 决定（见 §3）
targetstring?否null目标 node_id，建议性字段；广播与握手不设
pathstring?否null信号逻辑路径，点号分段、域优先（notify.web.download）；signal 类型必须填写
reqidstring?否null请求关联 ID；tool_call 与 tool_result 必须携带同一值
timestampnumber否发送时刻Unix 秒（浮点）
  • type 与 source 是唯二无默认值的字段：缺任一个，Signal.from_dict 抛 KeyError → 读循环异常 → 连接断开。
  • pattern 是路由键而不是收件人：_dispatch 先看 type 是否属于核心信号，再看 pattern 能否命中已注册的模式处理器，最后回退核心处理（未知 pattern 不得导致断开，见 §6）。
  • payload 必须是对象；数组或标量载荷不得直接放在 payload 里，而应包一层（如 {"items": [...]}）。
  • 核心模式可以不带 pattern（参考实现为 null），也可以带 msp/request-reply / msp/publish-subscribe；两种形态都必须被接受。
{"type": "tool_call", "source": "node_a", "pattern": null, "target": "node_b",
 "path": null, "reqid": "9f2c1a4b7e0d3856",
 "payload": {"tool": "get_weather", "args": {"location": "上海"}}, "timestamp": 1791500000.0}

SignalType 枚举与扩展规则​

SignalType 定义 9 个字符串常量（规范索引 §5.1 的表把 ping / pong 合并为一行，故该表只有 8 行）：

type有 reqidpayload 形态（权威定义见 §3）
hello否{"manifest": {...}}
ack否{"manifest": {...}}
signal否任意对象；路径在 path 字段
tool_call是{"tool": <string>, "args": <object>}
tool_result是{"content": [...], "structuredContent": <any>} 或 {"content": [], "error": <string>}
manifest_update否{"manifest": {...}}
ping / pong否{}（空对象）
error视情况{"code": <integer>, "message": <string>}

分类谓词：请求类为 tool_call / hello / ping，响应类为 tool_result / ack / pong；signal / manifest_update / error 不属于任一类。

模式私有类型的扩展规则：

  • 模式可以定义私有类型（现有：input_required / input_response、9 个 task_*），与核心类型共用同一个 type 字段空间。
  • 模式私有报文必须携带 pattern（值等于该模式 ID），否则接收方无法路由；接收方不得因 type 未知而断开连接，应当按 patterns.md 的未知模式规则处理。
  • msp/ 前缀由本规范保留；第三方模式必须为私有类型加自有前缀（如 acme_stream_chunk）。
  • 同名类型可以在不同模式下语义不同：input_required 同时定义于 msp/multi-round 与 msp/task，靠 pattern 区分。

Manifest​

Manifest 是节点自述的能力清单，属于节点而不属于协议；协议层只在握手时交换、在变化时推送。

顶层字段​

序列化形态是 camelCase；四个能力列表是数组而不是对象；capabilities 是有序（sorted）字符串数组；clientCapabilities 是含三个布尔的对象。

字段内部类型线格式类型默认语义
versionintinteger0单调递增版本号，只在内容变化时递增（见下）
patternslist[str]array<string>[]本节点支持的模式 ID
patternMetadatadict[str, dict]object{}pattern_id → 任意对象；格式由模式自定义，清单不感知、不校验
capabilitiesset[str]array<string>[]能力位，取值 pub / sub / req / rep；序列化时 sorted
signalsdict[str, SignalDescriptor]array<object>[]发布的信号路径（内部以 path 为键）
toolsdict[str, ToolDescriptor]array<object>[]提供的工具（内部以 name 为键）
resourcesdict[str, ResourceDescriptor]array<object>[]可读 / 可订阅资源（内部以 uri 为键）
promptsdict[str, PromptDescriptor]array<object>[]预定义提示模板（内部以 name 为键）
clientCapabilities三个 boolobject三个 false{"sampling": …, "elicitation": …, "roots": …}
  • signals / tools / resources / prompts 必须是数组。from_dict 对它们逐项迭代：若对端写成对象映射，迭代会拿到字符串键并抛 TypeError，握手随之失败。
  • capabilities 的 sorted 只是规范化：其值为集合语义，读取方不得依赖顺序，也不得因看到未列出的能力位而断开。
  • clientCapabilities 必须是对象（三个布尔），不得写成数组。
  • patternMetadata 的键应当同时出现在 patterns 中（set_pattern_metadata 会自动补齐）。
{"version": 3, "patterns": ["msp/publish-subscribe", "msp/request-reply", "msp/task"],
 "patternMetadata": {}, "capabilities": ["pub", "rep", "req", "sub"],
 "signals": [{"path": "notify.web.download", "description": "下载完成通知"}],
 "tools": [{"name": "get_weather", "description": "查询城市天气",
            "inputSchema": {"type": "object", "properties": {"location": {"type": "string"}}, "required": ["location"]},
            "outputTypes": [], "annotations": {}}],
 "resources": [], "prompts": [],
 "clientCapabilities": {"sampling": false, "elicitation": false, "roots": false}}

四个 descriptor 的精确字段​

SignalDescriptor（键为 path）：path（string，必填，总是出现）、schema（object，仅当非空时出现）、description（string，仅当非空时出现）。

ToolDescriptor（键为 name，五个字段总是出现）：name（string，[a-z0-9_-]+）、description（string，可为 ""）、inputSchema（object，可为 {}；缺省由 schema_from_func 生成）、outputTypes（array<string>，可为 []）、annotations（object，可为 {}）。

ResourceDescriptor（键为 uri，五个字段总是出现）：uri（string）、name（string）、description（string）、mimeType（string）、subscribable（boolean，默认 false）。

PromptDescriptor（键为 name，三个字段总是出现）：name（string）、description（string）、arguments（array<object>，可为 []；元素内部结构本修订未定义，参考实现原样透传）。

形态差异：只有 SignalDescriptor 对空 schema / 空 description 做条件省略，其余三个 descriptor 全部无条件写出。读取侧一律以缺省值兜底。

Manifest 变更与版本​

version 是单调递增的变更计数，不是时间戳也不是内容哈希。

操作何时递增 version
add_signal(path, schema, description)若 path 已存在且新 descriptor 相等 → 直接返回、不递增（去重短路）；否则写入并 +1（内容变化也算变更）
remove_signal(path)仅当存在时删除并 +1
add_tool(descriptor)无条件写入并 +1（即使与既有 descriptor 完全相同）
remove_tool(name)仅当存在时 +1
add_resource(descriptor) / remove_resource(uri)同上：写入无条件 +1，删除仅存在时 +1
add_prompt(descriptor) / remove_prompt(name)同上
add_pattern(pattern_id)仅当不在 patterns 中时追加并 +1
set_pattern_metadata(pattern_id, metadata)两处变更判定：① pattern_id 不在 patterns（追加）；② 现值与 metadata 不等（替换）。任一成立则 +1（只加一次）
apply_diff(diff)不递增；把 version 覆盖为 diff["version"]（缺键则保留原值）
  • add_tool / add_resource / add_prompt 没有去重短路（与 add_signal 不对称）：重复注册同名 descriptor 会产生一次无内容变化的版本递增与多余的 manifest_update。
  • MSPNode.start() 把 preset.patterns 并入 manifest.patterns（sorted(set(preset) | set(current))）、把 preset.capabilities 并入能力位（集合并集）。这一步不经过变更操作，因此不递增 version，随后直接推送整份清单。
  • 清单推送是整份替换：manifest_update.payload.manifest 是完整 Manifest；接收方必须丢弃 version 不大于当前值的推送。

diff() 与 apply_diff()​

Manifest.diff(old) 的精确键名如下（新增 / 更新项是 descriptor 字典，删除项是排序后的键名数组）：

键类型含义
signals_added / signals_updatedarray<SignalDescriptor>新有旧无 / 两边都有但不等
signals_removedarray<string>旧有新无的 path（sorted）
tools_added / tools_removed / tools_updated同上（键为 name）工具
resources_added / resources_removed / resources_updated同上（键为 uri）资源
prompts_added / prompts_removed / prompts_updated同上（键为 name）提示模板
versioninteger新清单的 version（不是旧值，也不是差值）

apply_diff(diff)：按 *_added / *_updated 覆盖写入、按 *_removed 删除（缺键视为空数组），最后 version = diff.get("version", version)。

  • diff() 不含 patterns / patternMetadata / capabilities / clientCapabilities：需要传递这些变化时必须走整份 manifest_update。
  • apply_diff 无条件把 version 设为 diff 中的值，缺少「拒绝更旧版本」的保护；跨机增量同步的实现必须自行加版本单调性校验。
  • 当前状态（源码事实）：diff() / apply_diff() 在参考实现中没有任何调用点（全仓仅在 manifest.py 内出现定义与实现）。增量同步是已定义但未接线的能力，实现可以不实现。

Endpoint​

字段类型必填默认语义
transport_typestring是—传输后端标识：tcp / websocket / uds（quic 为实现预留）
addressobject是—地址对象，键随 transport_type 变化（见下表）
node_idstring?否null节点身份；手动发现时可能尚不知道
  • Endpoint 没有 to_dict() / from_dict()：它不直接上线，而是由发现层产出、由宣告层手工拼进声明文件。
  • address_key() 返回 (transport_type, tuple(sorted(address.items())))；源码事实：该方法无任何调用点，实际的重复发现抑制由发现层的 _known[node_id] 声明哈希完成。调用 address_key() 本身不会抛错（sorted 只比较互不相同的键）；但它的返回值在用作 set / dict 键时要求 address 的值可哈希，因此 address 的值应当是简单可排序类型（字符串 / 数字），不得放嵌套对象。
transport_typeaddress 形态说明
tcp{"host": "127.0.0.1", "port": 45678}listen 默认 host="127.0.0.1"、port=0（动态），实际端口取自 getsockname
websocket{"url": "ws://127.0.0.1:45678/msp"}listen 默认 host 127.0.0.1、port 0、path /msp；解析器只接受 ws://
uds{"path": "/tmp/msp-1234-abcd.sock"}仅 Linux / macOS；默认在临时目录生成 msp-<pid>-<rand>.sock，权限 0o600
quic 🔵未定义TRANSPORT_REGISTRY 中仅有注释占位

声明文件（共享目录宣告）​

节点把 Endpoint 写进共享目录（默认 ~/.msp/nodes），扫描方据此发现它。精确 JSON 形态（三个顶层键，endpoint 恰好两个子键）：

{"node_id": "node_a",
 "endpoint": {"transport_type": "tcp", "address": {"host": "127.0.0.1", "port": 45678}},
 "timestamp": 1791500000.0}
  1. 文件名规则：{node_id}.json，位于 nodes_dir（默认 ~/.msp/nodes，~ 必须展开）；扫描方不得读取非 *.json 文件。
  2. endpoint 不含 node_id：节点身份只出现在顶层；读取侧只取 transport_type 与 address。
  3. timestamp 是租约：发送方按 renew_interval（默认 10.0 s，见 README §5.6）覆写；接收方丢弃 time.time() - timestamp > stale_after 的声明（DirectoryScan 默认 stale_after = 30.0 s）。缺 timestamp 视为永不过期。
  4. 原子写入：必须先写 {文件名}.tmp，再 os.replace 覆写，避免扫描方读到半个 JSON；参考实现用 json.dump(..., ensure_ascii=False, indent=2)。
  5. 撤销：withdraw() 停止续租并 unlink；文件缺失不得报错。
  6. 只放端点信息：不得写入本地策略（grants）、密钥或任何本地安全配置；身份材料只经握手报文交换。
  7. 扫描侧校验：缺 node_id、缺 endpoint、node_id 等于自身、JSON 解析失败的声明必须跳过而不报错；未变的声明（按内容哈希判定）不得重复触发新增事件。

内容块（ContentBlock）​

内容块出现在 tool_result.payload.content、Artifact.parts 等位置。annotations 是可选注解对象，仅当非空时出现在报文里。

type字段说明
texttext、annotations?纯文本
imagedata、mimeType、annotations?图片，data 为 Base64 编码字节
audiodata、mimeType、annotations?音频，data 为 Base64 编码字节
resourceresource（嵌套对象）、annotations?嵌入资源，内容在嵌套对象里
resource_linkuri、name、mimeType、description资源引用（只给 URI）；无 annotations 字段
blob_refblobId、mimeType、size、checksumMSP 扩展：指向独立 blob 通道的引用

resource 的嵌套对象：resource.uri（string，必填）、resource.mimeType（string，总是出现，可为 ""）、resource.text（仅当非空）、resource.blob（Base64，仅当非空）。

{"type": "text", "text": "上海 21℃ 多云"}
{"type": "resource", "resource": {"uri": "file:///etc/hosts", "mimeType": "text/plain", "text": "127.0.0.1 localhost"}}
{"type": "resource_link", "uri": "file:///var/log/app.log", "name": "app.log", "mimeType": "text/plain", "description": "应用日志"}
{"type": "blob_ref", "blobId": "b-7f3a1c", "mimeType": "video/mp4", "size": 104857600, "checksum": "sha256:…"}

宽容读取规则：block_from_dict 按 type 查表构造类型化对象；type 未识别时原样返回该字典。因此消费方必须同时接受「类型化对象」与「原始字典」两种形态（ToolResult.text() 两条路径都处理）。

ToolResult​

字段类型默认语义
contentarray<ContentBlock>[]内容块数组（线格式键为 content）
structuredanynull结构化结果；线格式键为 structuredContent
errorstring""错误消息字符串（非空即失败）
  • is_error = bool(error)；unwrap() 在 error 非空时抛 ToolError(error)，否则返回 structured。
  • text() 把所有 type == "text" 块的 text 用 "\n" 连接；非文本块忽略。
  • 接收 tool_result 时按 content / structuredContent / error 三键构造，缺省分别为 [] / null / ""。
  • 注意区分：ToolResult.error 是字符串，error 信号的 payload 是 {"code": <integer>, "message": <string>} 对象（见 §3.4），二者不可互相替代。

msp/multi-round 载荷​

模式 ID msp/multi-round（fallback_to = "msp/request-reply"）；所有报文必须带 pattern: "msp/multi-round"。

报文（type）payload 精确形态

input_response{"answer": <any>}；reqid 沿用该次调用的 reqid
tool_result{"content": <工具原样返回值，falsy 值归一为 []>, "error": <string>}

与核心模式的两处不一致（源码事实）：① tool_result.payload.content 是工具函数原样返回值，不经 _normalize_tool_result 规范化，也不带 structuredContent；② error 键总是出现（成功为空串 ""），而核心模式的成功结果不含 error 键。

msp/task 载荷​

模式 ID msp/task（fallback_to = "msp/request-reply"）；所有报文必须带 pattern: "msp/task"。

错误对象​

error 信号的 payload 固定两个键：

{"code": -32600, "message": "未知信号类型: stream_start"}

错误码取 JSON-RPC 2.0 约定值，权威表见规范索引 §5.4。源码事实：MSP 协议核心只在「收到未知 type」时发出 -32600；-32601 / -32602 / -32603 仅定义于 msp/mcp/jsonrpc.py（JSON-RPC 桥），MSP 工具执行失败一律走 tool_result.payload.error 字符串通道。

5. 数据类型​

schema_from_func 的投影规则​

inputSchema 缺省时由工具函数签名自省生成；显式传入的 input_schema 优先，自省只在缺省时兜底。函数级产出恒为 {"type": "object", "properties": {...}}，存在必填参数时追加 required（按参数声明顺序）。

注解形态JSON Schema 片段
str / int / float / bool{"type":"string"} / {"type":"integer"} / {"type":"number"} / {"type":"boolean"}（类型对象精确相等查表，bool 不会误判为 int）
无注解 / Any / inspect.Parameter.empty{}（无约束，但参数仍进 properties）
None（type(None)）{"type":"null"}
Annotated[str, "城市名"]{"type":"string","description":"城市名"}
Annotated[int, Field(ge=0, le=100)]仅 pydantic v1 形态成立：{"type":"integer","minimum":0,"maximum":100}；pydantic v2 形态下约束被静默丢弃，只剩 {"type":"integer"}（见下方第 7 条）
Field(gt=0) / Field(lt=10)命中时 → exclusiveMinimum / exclusiveMaximum
Field(min_length=1) / Field(max_length=64)命中时 → minLength / maxLength
Field(pattern="^a") / Field(description="…")命中时 → pattern / description（description 在 v1/v2 均命中：v2 的 FieldInfo.description 仍是实例属性）
enum.Enum 子类{"enum":[成员1.value, 成员2.value, …]}（取 .value，不写 type）
Literal["a", "b"]{"enum":["a","b"]}（取字面量本身）
Optional[str] / str | None{"type":["string","null"]}
Optional[MyEnum] / Optional[Literal[...]]（内层无标量 type）{"anyOf":[{…内层…},{"type":"null"}]}
Union[A, B]（≥ 2 个非 None 成员）{"anyOf":[A 的片段, B 的片段]}（丢弃 None 成员）
list[T] / set[T] / tuple[T]{"type":"array","items":<T 的片段>}；tuple[T1, T2] → {"type":"array"}（无 items）
裸 list / set / tuple{"type":"array"}
dict{"type":"object"}
dict[str, T]{"type":"object","additionalProperties":<T 的片段>}
其他（自定义类、TypeVar）{}（无约束，不报错）

关键结论：约束输出的是 JSON Schema 关键字（minimum / exclusiveMinimum / maximum / exclusiveMaximum / minLength / maxLength / pattern），不是 pydantic 字段名（ge / le / gt / lt / min_length / max_length）。实现不得把 ge 之类直接透传进 inputSchema。

边界行为与脆弱性​

  1. get_type_hints(func, include_extras=True) 是必需的：默认调用会剥掉 Annotated 元数据，描述与约束全部丢失；from __future__ import annotations 使注解成为字符串，也必须经它解析。
  2. 自省失败即「无约束」：get_type_hints 抛异常时 hints 退化为空——所有参数变无约束但仍进 properties，required 仍按签名默认值判定；inspect.signature 失败时返回 {"type":"object","properties":{}}（没有 required 键）。
  3. 跳过与兜底：self / cls、*args / **kwargs 跳过；无注解参数不丢弃，而是产出 {}。
  4. 不产出 default：_field_extra 明确不提取默认值——签名里的 Python 默认值只决定参数是否进 required，JSON Schema 的 default 关键字从不由本实现生成；Field(default=...) 也不被读取。
  5. 零 pydantic 硬依赖的识别方式：用 type(meta).__name__ == "FieldInfo" 做 duck-typing，避免 import pydantic（项目唯一第三方依赖是 watchdog）。
  6. 脆弱性：① 类名字符串匹配——pydantic 改名、包装或子类化会让约束静默丢失，同名自定义类会被误识别；② 非 pydantic 的约束载体（如 annotated_types）不被识别；③ 多个 Annotated 约束对象会依次 update，后者覆盖前者同名键；④ 自省结果只用于对外宣告，不参与运行时校验——协议层不按 inputSchema 校验 args，工具函数自身的 TypeError 只会变成 tool_result.payload.error。
  7. pydantic v2 下约束全部丢失（实测，重要）：_field_extra 用 getattr(field, "ge" / "gt" / "le" / "lt" / "min_length" / "max_length" / "pattern") 取约束，这套属性是 pydantic v1 的 FieldInfo 形态。pydantic v2 把约束搬进了 field.metadata（形如 Ge(ge=0) / Le(le=100) 的对象），FieldInfo 不再有 ge / le 等属性，于是上述 getattr 全部返回 None，约束被静默丢弃；description 仍保留（它是 v2 的实例属性）。在 pydantic 2.13.4 上实测：Annotated[int, Field(ge=0, le=100, description="pct")] 产出 {"type":"integer","description":"pct"}——minimum / maximum 不出现。因此：依赖约束宣告的实现必须自行读取 field.metadata（v2）或显式传入 input_schema；不得假定本函数会为 Field(...) 生成约束。

7. 规范条文汇总（MUST / SHOULD 清单）​

  1. Signal 必须使用 snake_case 字段名；type 与 source 必须存在，其余字段缺省时按默认值语义处理。
  2. 模式私有信号必须携带 pattern；接收方必须优先按 pattern 路由。
  3. type: "signal" 必须填写 path；tool_call / tool_result 必须携带同一 reqid。
  4. Manifest 必须使用 camelCase；signals / tools / resources / prompts 必须是数组，capabilities 必须是字符串数组，clientCapabilities 必须是含三个布尔的对象。
  5. Manifest.version 必须单调递增；接收方必须丢弃 version 不大于当前值的 manifest_update。
  6. SignalDescriptor 的空 schema / description 可以省略；其余 descriptor 的字段应当全部写出，读取侧必须以缺省值兜底。
  7. 声明文件必须是 {node_id}.json，必须原子写入，不得写入本地策略或密钥。
  8. Endpoint.address 不得含嵌套对象（address_key 依赖可排序的简单值）。
  9. 未知内容块类型必须原样保留；消费方必须同时接受类型化对象与原始字典。
  10. 线格式用 structuredContent，内存模型叫 structured；实现不得把 structured 直接写上线。
  11. ToolResult.error（字符串）与 error.payload（对象）不得混用；工具失败必须走 tool_result.payload.error。
  12. inputSchema 缺省时应当由 schema_from_func 生成，且必须用 get_type_hints(..., include_extras=True)，输出必须是 JSON Schema 关键字而非 pydantic 字段名。
  13. schema_from_func 不得产出 default 关键字，不得因未识别注解而抛异常。
  14. grants 不得出现在 Manifest、声明文件或任何上线报文中。
  15. 未识别的字段 / 信号类型 / 内容块类型 / 模式 ID 不得被视为协议错误而断开连接。

8. 安全考量​

  • 清单是自述，不是承诺：capabilities / tools / patterns 都可能虚报；授权判定不得引用清单（security.md §授权），清单只用于「要不要尝试」的本地优化。
  • 自省不是校验：inputSchema 是告示而非运行时闸门；参数校验应当在工具函数内完成，不得依赖 schema。
  • 宽容读取的边界：宽容读取要求不断开连接，不要求执行未识别语义；不得把「未知块原样保留」理解为「未知数据可进入执行路径」。
  • 声明文件是本地策略禁入区：grants / 密钥 / 白名单不得进入声明文件或 Manifest。
  • 完整性字段是提示性的：blob_ref.size / checksum 不得作为内存预分配的唯一下界，其校验责任见 security.md §8。
  • reqid 必须不可预测：它是 tool_result 唯一的关联依据（16 位十六进制），可预测的 reqid 会留下结果伪造面（security.md §8）。
  • version 是回滚防线：拒绝更旧的 manifest_update 可防止对端用旧清单回滚本地能力视图；apply_diff 目前没有这层保护。

9. 已知缺口​

  1. Endpoint.address_key() 无调用点：端点去重实际由发现层的 _known[node_id] 声明哈希完成，(transport_type, address) 级去重「已定义未使用」。
  2. diff() / apply_diff() 未被协议层使用：全仓仅在 manifest.py 内出现，清单更新走整份 manifest_update。
  3. apply_diff 无版本单调性保护：会把 version 无条件覆盖为 diff 中的值，可能造成版本倒退。
  4. schema 不参与运行时校验：协议层不按 inputSchema 校验 args，工具函数也不自动获得校验。
  5. PromptDescriptor.arguments 元素结构未定义：源码为 list[dict]，内部字段本修订未规定（capabilities.md 🔵 补齐）。
  6. add_tool / add_resource / add_prompt 无去重短路：与 add_signal 不对称，重复注册会产生无内容的 version 递增与多余的 manifest_update。
  7. msp/multi-round 的 tool_result 与核心模式不一致：content 是原样返回值、无 structuredContent、error 键总是存在。
  8. msp/task 的 input_required / input_response 不带 reqid：只能靠 taskId 关联；跨模式复用的实现不得假定二者同构。
  9. 缺失字段行为不对称：缺 type / source 会断开连接，其他缺失字段静默兜底。
  10. 无 schema 版本化：Manifest.version 只是单调计数，不能表达「数据结构变了」，也没有兼容性声明字段。
  11. quic 传输未注册：仅有注释占位，使用会抛 ValueError，其 address 形态未定义。
