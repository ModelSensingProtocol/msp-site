# Core pattern: request/reply (`msp/request-reply`)

| | |
|---|---|
| **Protocol revision** | `2026-10-10` |
| **Status** | ✅ Implemented |
| **This page defines** | The core communication pattern `msp/request-reply`: the complete payload fields of `tool_call` / `tool_result`, `reqid` correlation and concurrent isolation, the step-by-step flow of the caller and the callee, the return-value normalisation rules, the "errors as values" semantics, tool registration and timeout semantics, and the boundary for attributing error codes |

> This page makes [patterns.md](../patterns.md) concrete. The pattern-layer contract, the routing decision order and `PatternHandler` are none of this page's business — `msp/request-reply` is a **core pattern**, implemented directly in the protocol layer; it does not enter `PATTERN_REGISTRY` and has no Handler instance.

---

## 1. Overview

`msp/request-reply` is MSP's **lowest common denominator**: one TCP connection + the `Signal` envelope + this pattern, and two independent implementations can call each other's tools ([README.md §7](https://github.com/hxh230802/MSP/blob/master/docs/spec/README.md#7-一致性)).

Its semantics in one sentence: **A sends B a `tool_call` carrying a `reqid`; B runs the tool on a separate thread and sends back a `tool_result` carrying the same `reqid`; A uses that `reqid` to find its own waiter in `pending_calls`.**

The semantic correspondence with JSON-RPC 2.0 is in [interop.md](../interop.md#json-rpc-20-semantic-alignment):

| MSP | JSON-RPC 2.0 |
|---|---|
| `reqid` | `id` |
| `payload.tool` | `method` |
| `payload.args` | `params` |
| `payload.content` / `payload.structuredContent` | `result` |
| `payload.error` | `error.message` |
| `type: "tool_call"` | request |
| `type: "tool_result"` | response |

## 2. Contract

### 2.1 `reqid`

| Item | Provision |
|---|---|
| Type | `str` |
| Generated by | **MUST** be generated by the **initiating side**, through `Signal.new_reqid()`, that is `uuid.uuid4().hex[:16]` (the first 16 characters of a 32-character hexadecimal string) |
| Location | `Signal.reqid` (an **envelope field**, not a `payload` field) |
| Semantics | Uniquely identifies one request on a connection pair; the `tool_result` **MUST** echo the same value |
| Lifetime | Registered in `pending_calls` when the request is initiated; **MUST** be deregistered when the result arrives or on timeout |

**MUST** be satisfied:

1. A `tool_call` **MUST** carry a non-empty `reqid`. On receiving a `tool_call` whose `reqid` is empty, the callee **MUST** ignore it outright (in the current implementation that is a plain `return`; see §11 G1).
2. A `tool_result` **MUST** echo the `reqid`. A receiver **MUST** silently ignore a `tool_result` with an unknown `reqid` — it is not an error; usually it is just a late reply to a request that was abandoned on timeout long ago.
3. The `reqid` **MUST NOT** appear a second time inside `payload`.

### 2.2 `pending_calls`

The protocol layer registers unfinished requests in a dictionary guarded by a `threading.Lock`:

```python
self.pending_calls: dict[str, tuple[threading.Event, list]] = {}
#                        reqid          (event,        [peer_id, result])
```

**MUST** be satisfied:

1. **Registration** happens **before** the packet is sent (otherwise the peer's reply may arrive before registration). The implementation order is: generate `reqid` → create the `Event` → take the lock and write `pending_calls[reqid] = (event, [peer_id, None])` → `_send(...)`.
2. A waiter **MAY** block only through `event.wait(timeout)`; it **MUST NOT** poll `pending_calls` — that is busy waiting.
3. **Writing the result** is done by the read loop (`_on_tool_result`): take the lock and fetch `(event, holder)`, write `holder[1] = ToolResult(...)`, then `event.set()`.
4. **Deregistration** is done by the waiter, and it **MUST** pop the entry out of the dictionary (`pop`), otherwise the dictionary grows without bound.
5. **Concurrent isolation**: entries with different `reqid` values do not affect each other, so there **MAY** be any number of in-flight requests on the same connection; concurrent `call()` from different threads is safe.
6. `peer_id` is stored in `holder[0]`, so that on disconnect all waiters for that peer can be woken in a batch.

### 2.3 Result read path

```
tool_result arrives
      │
      ├─ reqid is empty ─────────────▶ ignore
      │
      └─ lock, look up pending_calls[reqid]
             ├─ not registered (already timed out / deregistered) ─▶ ignore
             └─ hit
                  holder[1] = ToolResult(
                      content    = payload.get("content", []),
                      structured = payload.get("structuredContent"),
                      error      = payload.get("error", ""),
                  )
                  event.set()          ← wake call()
```

Note that the default of `structuredContent` is `None` (the no-default overload of `dict.get`), whereas the defaults of `content` / `error` are `[]` / `""` respectively.

### 2.4 Cleanup after a timeout

When `event.wait(timeout)` returns `False`, it **MUST**:

1. take the lock and `pending_calls.pop(reqid, None)` — deregister the entry, so that a late reply cannot wake the wrong waiter;
2. raise `TimeoutError(f"call to {tool} timed out")`.

`node.call()` turns that `TimeoutError` into `ToolResult(error="call to <tool> timed out")` (§6).

## 3. Messages

### 3.1 Envelope fields

Both signals are standard `Signal` objects. The `pattern` field **MUST** be `null` (a core pattern writes no routing key), and `target` **SHOULD** carry the peer's `node_id`.

| Field | `tool_call` | `tool_result` |
|---|---|---|
| `type` | `"tool_call"` | `"tool_result"` |
| `source` | the caller's `node_id` | the callee's `node_id` |
| `target` | the callee's `node_id` | the caller's `node_id` |
| `reqid` | **MUST**, non-empty | **MUST**, echoes the request value |
| `payload` | see §3.2 | see §3.3 |
| `pattern` | `null` | `null` |
| `path` | `null` | `null` |
| `timestamp` | filled in automatically | filled in automatically |

`Signal` envelope fields are always **snake_case** (`type` / `source` / `pattern` / `target` / `path` / `reqid` / `payload` / `timestamp`).

### 3.2 `tool_call.payload`

| Field | Type | Required | Description |
|---|---|---|---|
| `tool` | `str` | **MUST** | Tool name, matched **exactly** (wildcards **MUST NOT** be used; see [publish-subscribe.md](publish-subscribe.md#7-boundaries)); **MUST** conform to `[a-z0-9_-]+` |
| `args` | `object` | **MAY** | Keyword-argument object, default `{}`; the key names **MUST** match the tool function's parameter names verbatim |

```jsonc
// tool_call: caller → callee
{
  "type": "tool_call",
  "source": "node_b",
  "pattern": null,
  "target": "node_a",
  "path": null,
  "reqid": "9f2c1ab34de5f607",
  "payload": {
    "tool": "get_weather",
    "args": {"location": "Beijing", "days": 3}
  },
  "timestamp": 1791331200.5
}
```

### 3.3 `tool_result.payload`

| Field | Type | Required | Description |
|---|---|---|---|
| `content` | `list` | **SHOULD** | List of content blocks. The field name is **snake_case** (consistent with the envelope); each value is a content-block dict |
| `structuredContent` | `any` | **MAY** | Structured result. The field name is **camelCase** (carried over from MCP naming), in the same style as `Manifest`'s `inputSchema` / `mimeType` |
| `error` | `str` | **MAY** | Failure reason; omitted on success (the success branch of `_run_tool` does **not write** this key, whereas `msp/multi-round` writes `""`) |

```jsonc
// success (the tool returned a dict)
{
  "type": "tool_result",
  "source": "node_a",
  "pattern": null,
  "target": "node_b",
  "path": null,
  "reqid": "9f2c1ab34de5f607",
  "payload": {
    "content": [{"type": "text", "text": "{\"temp\": 22, \"location\": \"Beijing\"}"}],
    "structuredContent": {"temp": 22, "location": "Beijing"}
  },
  "timestamp": 1791331201.1
}

// failure (unknown tool, or the tool raised)
{
  "type": "tool_result",
  "source": "node_a",
  "pattern": null,
  "target": "node_b",
  "path": null,
  "reqid": "9f2c1ab34de5f607",
  "payload": {"content": [], "error": "unknown tool: get_wether"},
  "timestamp": 1791331201.1
}
```

**Note**: on failure `structuredContent` is **absent** (the exception branch of `_run_tool` writes only `content` and `error`). The receiver's default for it is `None`.

### 3.4 Content block types

Every element of the `content` array **MUST** be one of the blocks listed in §5.2. A block of unknown `type` **MUST** be kept exactly as it is (lenient reading); it **MUST NOT** cause an error or the loss of the whole result.

## 4. Message flow

### 4.1 Sequence diagram

```
  Caller (node_b)                                                    Callee (node_a)
      │                                                                  │
      │ 1. node.call("node_a", "get_weather", {...})                     │
      │      └─ ensure_connected("node_a")                               │
      │            ├─ connected → continue directly                      │
      │            ├─ not connected but known → dial + handshake         │
      │            └─ not in the neighbour table → UnknownPeer           │
      │                                                                  │
      │ 2. reqid = Signal.new_reqid()                                    │
      │ 3. pending_calls[reqid] = (event, [peer, None])                  │
      │                                                                  │
      │ ── tool_call(reqid, tool, args) ───────────────────────────────▶ │
      │                                                                  │ 4. _dispatch → step 3
      │                                                                  │    → _on_tool_call
      │ 5. event.wait(5.0)   ← blocks the calling thread                 │ 6. start a worker thread _run_tool
      │                                                                  │      ├─ look up _tools[tool]
      │                                                                  │      ├─ not registered → raise
      │                                                                  │      └─ registered → func(**args)
      │                                                                  │ 7. _normalize_tool_result
      │ ◀── tool_result(reqid, content, structured…) ─────────────────── │
      │                                                                  │
      │ 8. read loop _on_tool_result                                     │
      │      └─ holder[1] = ToolResult(...); event.set()                 │
      │ 9. call() wakes up, pops pending_calls[reqid]                    │
      │ 10. return ToolResult to the user                                │
      ▼                                                                  ▼
```

### 4.2 Caller side, step by step

| Step | Action | Behaviour on failure |
|---|---|---|
| 1 | `node.call(peer_id, tool, args, timeout=5.0)` | — |
| 2 | `ensure_connected(peer_id)`: returns at once if already connected; raises `UnknownPeer` for an unknown node; raises `PeerUnavailable` if dialling / the handshake fails; raises `PeerUnavailable` during the cooldown | converted to `ToolResult(error=str(e))` (§6) |
| 3 | generate `reqid`, register in `pending_calls` | — |
| 4 | send `tool_call` (`_send` raises `RuntimeError` when not connected) | converted to `ToolResult(error="not connected to <peer>")` |
| 5 | `event.wait(timeout)` | timeout → deregister the entry → `TimeoutError` → converted to `ToolResult(error="call to <tool> timed out")` |
| 6 | after waking, `pop` the entry and take `holder[1]` | if the connection dropped in the meantime, `holder[1]` has already been written by the read loop as `ToolResult(error="connection closed")` |
| 7 | return `ToolResult` | — |

### 4.3 Callee side, step by step

| Step | Action | Basis |
|---|---|---|
| 1 | the read loop receives `tool_call` | `_read_loop` |
| 2 | step 1 of `_dispatch` does not match (`tool_call` is not a core signal type) → step 2 does not match (`pattern` is `None`) → step 3 | `_dispatch` |
| 3 | `_dispatch_core` matches `SignalType.TOOL_CALL` → `_on_tool_call` | `_dispatch_core` |
| 4 | `reqid` is empty → return at once (ignore) | `_on_tool_call` |
| 5 | take `tool = payload.get("tool")`, `args = payload.get("args", {})` | same as above |
| 6 | **start a separate thread** to run `_run_tool`; the read loop returns at once | same as above; see §4.4 |
| 7 | the worker thread looks up `_tools[tool]`; not registered → `raise ValueError(f"unknown tool: {tool}")` | `_run_tool` |
| 8 | call `func(**args)` and normalise the return value | `_run_tool` + `_normalize_tool_result` |
| 9 | send `tool_result`; if `_send` fails (the peer has gone) only a debug line is logged, and it **MUST NOT** retry | `_run_tool` |

### 4.4 Why it **MUST** run on a separate thread

The read-loop thread (`_read_loop`) is the **only** message receiver for that connection. If the callee ran the tool synchronously on the read-loop thread:

1. **It blocks message reception on that connection.** A slow 30-second tool would leave this connection unable to receive any message for 30 seconds — including the heartbeat `ping`, so the peer declares liveness loss after `heartbeat_timeout` (45 seconds by default) and closes the connection; nor would other `tool_call`s on the same connection arrive (concurrency degrades to 1).
2. **A callback from inside the tool to the peer deadlocks.** This is the more serious of the two: while running a tool, the multi-round server calls `ctx.ask()` to put a follow-up question to the caller, then blocks waiting for `input_response`. Receiving that `input_response` needs the read loop — which is itself waiting for the tool to return. **Each waits for the other; deadlock for ever.**

Hence the normative provision:

> The callee **MUST** run the tool function on a separate thread, and **MUST NOT** run it synchronously on the protocol layer's read-loop thread.

The reference implementation spells out both reasons in the docstring of `MSPProtocol._on_tool_call`, noting that the same reasoning applies to `_run_tool` in `msp/multi-round`.

## 5. Data types

### 5.1 `ToolResult`

The return value of `node.call()`. Defined in `src/msp/core/content.py`.

| Member | Type | Default | Description |
|---|---|---|---|
| `content` | `list` | `[]` | List of content blocks |
| `structured` | `Any` | `None` | Structured result (corresponds to `structuredContent` on the wire). **Note that the local attribute is named `structured`, while the field on the wire is named `structuredContent`** |
| `error` | `str` | `""` | Failure reason |

| Method / property | Return value | Semantics |
|---|---|---|
| `is_error` | `bool` | `bool(self.error)` — any non-empty `error` means an error |
| `unwrap()` | `Any` | **raises `ToolError(error)`** when `error` is non-empty; otherwise returns `structured` |
| `text()` | `str` | joins the text of every `type="text"` block (dict or object) with `"\n"` |

**MUST** be satisfied:

1. `content` / `structured` / `error` **MUST NOT** express contradictory semantics at the same time. The specification requires that when `error` is non-empty the meaning of `structured` is undefined, so the caller **SHOULD** check `is_error` first.
2. **MUST NOT** use "is `content` empty" to judge success or failure — a success may well have no content blocks (for example when the tool returns `None`).

### 5.2 Content block types

| `type` | Key fields | Description |
|---|---|---|
| `text` | `text` (`str`), optional `annotations` | Plain text |
| `image` | `data` (Base64), `mimeType`, optional `annotations` | Image |
| `audio` | `data` (Base64), `mimeType`, optional `annotations` | Audio |
| `resource` | nested `resource: {uri, mimeType, text?, blob?}`, optional `annotations` | Embedded resource |
| `resource_link` | `uri`, `name`, `mimeType`, `description` | Resource reference |
| `blob_ref` | `blobId`, `mimeType`, `size`, `checksum` | MSP extension, pointing at the separate blob channel |

Field names inside blocks mix two styles and **MUST** be followed verbatim: `mimeType` and `blobId` are camelCase; `annotations`, `text`, `data`, `uri`, `size`, `checksum` and `description` have no case ambiguity; `resource` is a nested object and **not** a key of the block itself.

A block of unknown `type` **MUST** be returned exactly as it is (`block_from_dict` returns the input dict itself for an unknown type), and **MUST NOT** raise.

### 5.3 Return-value normalisation rules

`_normalize_tool_result(result)` returns the pair `(content_blocks, structured_data)`. The return value of a tool function **MUST** be classified in the following **order**, returning on the first match:

| # | Input form | `content` | `structured` | Remarks |
|---|---|---|---|---|
| 1 | `None` | `[]` | `None` | Explicit empty result |
| 2 | A **non-empty** `list` whose **every** element is a content block | the list after `to_dict()` on each element | `None` | "already a list of content blocks" |
| 3 | A single object that has `to_dict()` | `[result.to_dict()]` | `None` | "a single ContentBlock" |
| 4 | `str` | `[{"type": "text", "text": result}]` | `result` (**both** are given) | a string serves as both content and structured |
| 5 | Everything else (`dict` / `list` / `int` / `float` / `bool`) | `[{"type": "text", "text": json.dumps(result, ensure_ascii=False)}]` | `result` | Structured data |

**The rule for deciding "is this a content block"** (`_is_content_block`): it has a `to_dict` attribute, **or** it is a `dict` containing a `"type"` key. An ordinary data dict (such as `{"name": "Alice"}`) does **not** count as a content block — this is so that structured data is not mistaken for a block list.

#### 5.3.1 The empty-list trap (an easy mistake, **MUST** be noted)

Branch 2 of the decision order carries a **non-empty** precondition:

```python
if isinstance(result, list) and result and all(_is_content_block(b) for b in result):
```

Without `and result`, `all(...)` is always `True` for an empty list, and so:

- a tool returning `[]` would be taken for "an empty list of content blocks", and `structured` would become `None`;
- whereas the expected behaviour is to take branch 5 — `content` gets one `text` block `"[]"`, and `structured` gets `[]`.

Therefore:

> A return value of `[]` **MUST** take the structured branch (branch 5), yielding `content=[{"type": "text", "text": "[]"}]` and `structured=[]`.

The reference implementation flags this trap explicitly in a source comment ("note: an empty list [] takes the structured branch, avoiding the trap of all() being vacuously true").

#### 5.3.2 Why `content` and `structuredContent` are both given

Branches 4 and 5 fill both fields **at the same time**, because there are two kinds of consumer:

- **human-facing / model-facing consumers** read `content` — it is already a directly renderable block (text, image, …) and does not need to know the JSON representation of the original Python type;
- **program-facing consumers** read `structuredContent` — it keeps the original data structure (`dict` / `list` / numeric), and `unwrap()` hands it straight back, avoiding the round trip of "serialise to JSON, then parse it back".

The two **MUST NOT** be treated as redundant with one of them omitted: omitting `structuredContent` forces program consumers to parse a text block; omitting `content` makes the result unreadable to an implementation that understands only content blocks (the MCP style).

## 6. Error handling

### 6.1 Errors as values

> `node.call()` returns `ToolResult(error=...)` for **every failure on the peer side**, and **MUST NOT** throw an exception that interrupts the caller; only **programming errors** `raise`.

A programming error means "the caller misused the API itself", for example passing `None` as `args` (`func(**args)` would raise `TypeError`, but that happens on the callee side), or calling a method on an unregistered `node` object. When an exception **MUST** be obtained explicitly, use `ToolResult.unwrap()` — it raises `ToolError` when `error` is non-empty.

### 6.2 The five failure classes and the source of the `error` text

| # | Failure | Trigger point | Source of the `error` text | Shape of the text |
|---|---|---|---|---|
| F1 | Peer unreachable | `ensure_connected` → `PeerUnavailable` | the `except (PeerUnavailable, UnknownPeer)` in `MSPNode.call` | `node <id> unreachable: <e>` or `node <id> suspected dead, cooling down` |
| F2 | Unknown node | `ensure_connected` → `UnknownPeer` | same as above | `unknown node <id>, cannot connect` |
| F3 | Call timed out | `MSPProtocol.call` → `TimeoutError` | the `except (TimeoutError, ...)` in `MSPNode.call` | `call to <tool> timed out` |
| F4 | Disconnected mid-flight | `_handle_disconnect` writes `holder[1]` | constructed directly by the protocol layer | `connection closed` |
| F5 | Protocol stopped | `MSPProtocol.stop` writes `holder[1]` | constructed directly by the protocol layer | `protocol stopped` |

One further failure on the **same channel**:

| # | Failure | Trigger point | `error` text | Attribution |
|---|---|---|---|---|
| F6 | Not connected when sending | `_send` → `RuntimeError` | `not connected to <peer>` | the `except (TimeoutError, ConnectionClosed, RuntimeError)` in `MSPNode.call` |

**MUST** be satisfied:

1. All of F1–F6 **MUST** be returned as `ToolResult(error=...)`; a caller **MUST NOT** wrap them in `try/except` in order to catch them.
2. Peer-side failures (F3 excepted) **MUST** be determined locally by the caller, and **MUST NOT** depend on the peer sending an `error` signal — the peer may already be dead and able to send nothing.
3. Scope of F5: `stop()` wakes only entries whose `holder[1] is None`, so a call that has already received an F4 result is not overwritten by `protocol stopped`.

### 6.3 Failures on the tool side and error-code ownership

**Tool execution failure has two channels**, and the boundary **MUST** be clear:

| Channel | When it is used | Carrier | Error code |
|---|---|---|---|
| **Errors as values** | The tool does not exist, the tool raises, or mismatched arguments cause a `TypeError` | `tool_result.payload.error` (a string) | no error code (see below) |
| **Protocol error** | A signal-level problem: unknown `type` | the `error` signal | `-32600` |

**Error-code ownership boundary** (compare [README.md §5.4](https://github.com/hxh230802/MSP/blob/master/docs/spec/README.md#54-错误码)):

| Code | Where the specification defines it to appear | Current state of the reference implementation |
|---|---|---|
| `-32600` | Reply with `error` on receiving an unknown `type` | ✅ Implemented: the `else` of `_dispatch_core` → `_reply_error(code=-32600, message="unknown signal type: <type>")` |
| `-32601` | A tool call names an unregistered tool | 🟡 **Not landed in the core protocol layer**: `_run_tool` turns it into the string `unknown tool: <name>` in `tool_result.payload.error`, **without** a `code` |
| `-32602` | Arguments do not satisfy the tool's declared `inputSchema` | 🟡 **Not landed in the core protocol layer**: the core performs no schema validation (§7.3); mismatched arguments show up as a `TypeError` → a `payload.error` string |
| `-32603` | The tool raises while executing | 🟡 **Not landed in the core protocol layer**: the exception message goes into `payload.error` verbatim, **without** a `code` |
| `-32000`~`-32099` | Implementation-defined, reserved for the pattern layer | not used by the core |

The three constants `-32601` / `-32602` / `-32603` are defined **only** in `src/msp/mcp/jsonrpc.py` (the JSON-RPC bridge); the core protocol layer has no reference site for them. Therefore:

> An implementation **MUST NOT** expect to see a `code` field in `tool_result.payload`. Mapping the `payload.error` string onto error codes **SHOULD** be done by the adaptation layer (such as the JSON-RPC bridge in [interop.md](../interop.md)).

### 6.4 Concrete behaviour with an unknown tool

When the callee receives a `tool_call` that names an unregistered tool:

1. `self._tools.get(tool_name)` in `_run_tool` returns `None` → `raise ValueError(f"unknown tool: {tool_name}")`;
2. the exception is caught by `_run_tool`'s `except Exception as e` → `payload = {"content": [], "error": str(e)}`;
3. send `tool_result` (**not** an `error` signal), echoing the `reqid`.

Hence no protocol-layer `error` signal is produced. A protocol-layer `error` (`-32600`) is emitted only for an **unknown `type`**. This boundary **MUST NOT** be blurred: upgrading "unknown tool" to an `error` signal would break `reqid` correlation (an `error` signal does carry a `reqid`, but the receiving side has no corresponding wake-up path).

## 7. Tool registration

### 7.1 Decorator signature

```python
@node.tool(name, description="", input_schema=None)
def my_tool(...) -> ...: ...
```

| Parameter | Type | Default | Description |
|---|---|---|---|
| `name` | `str` | **MUST** | Tool name, which **MUST** match the caller's `payload.tool` exactly; **MUST** conform to `[a-z0-9_-]+` |
| `description` | `str` | `""` | Human-readable description, goes into `Manifest` |
| `input_schema` | `dict \| None` | `None` | JSON Schema of the arguments |

The registration action **MUST** do three things at the same time:

1. `manifest.add_tool(ToolDescriptor(name=..., description=..., input_schema=schema))` — goes into the manifest, and is exchanged with the handshake;
2. `protocol.tool(name)(func)` — goes into the protocol layer's `_tools` dispatch table; **at runtime** only this table is consulted;
3. `_push_manifest()` — if a connection already exists, push `manifest_update`.

### 7.2 How `input_schema` arises

- **Default** (`input_schema is None`): generated by `schema_from_func(func)` by introspecting the function signature (including `Annotated` parameter descriptions);
- **Passed explicitly**: **what is passed wins**, and it **MUST NOT** be merged with the introspected result.

For the details (`Annotated` descriptions, `Field` constraints, `enum`, the `anyOf` form of `Optional[Literal]`, and Pydantic compatibility with no hard dependency) see [schema.md](../schema.md).

**`inputSchema` is also the basis on which clients generate call interfaces.** A peer **MAY** project the `inputSchema` from the manifest into a callable interface in the host language (reference implementation: `peer.t`; see "calling the peer's tools as functions" in the [repository README](https://github.com/hxh230802/MSP/blob/master/README.zh-CN.md)). Hence:

- a provider **SHOULD** keep `inputSchema` consistent with the implementation — it is no longer just documentation for humans, but the **basis on which the peer generates an API**;
- but the reference implementation currently **does not guarantee** this: `schema_from_func` emits no `default`, and under pydantic v2 constraints such as `Field(ge=…)` are silently lost (see "boundary behaviour and fragility" in [schema.md](../schema.md)). A generator **MUST** therefore treat anything it cannot recognise as `Any`, and **MUST NOT** assume that a constraint exists;
- **the mapping from JSON Schema to a host language is client behaviour, not normative.** It is not on the wire and forms no interoperability surface, and **MUST NOT** be written into this specification; the only wire-level point added here is that `inputSchema` is part of the announce contract.

### 7.3 The introspection result is used only for announcement (**known gap**)

> The introspected / explicitly passed `inputSchema` **takes no part in runtime validation** — but that does not mean it is "only documentation": it is at the same time the **basis on which the peer generates a call interface** (§7.2), so a provider **SHOULD** keep it consistent with the implementation.

That is: `Manifest` lists the parameter constraints faithfully, but the callee's `_run_tool` only does `func(**args)` and does **not** check whether `args` satisfies `inputSchema`.

The consequences **MUST** be expected as they are:

1. a missing required argument → `TypeError` → `payload.error` (not `-32602`);
2. an extra argument → `TypeError: unexpected keyword argument` → `payload.error`;
3. a type mismatch (such as passing `"3"` to an `int`) → **no error is reported**; the function body receives `"3"` and the behaviour is up to the tool itself.

Therefore:

> An implementation that needs argument validation **MUST** validate inside the tool function itself, and **MUST NOT** assume that the framework will reject invalid arguments. If runtime validation is added in future, the message shape **MAY** be extended by "appending" `payload.code` within the same revision ([README.md §1](https://github.com/hxh230802/MSP/blob/master/docs/spec/README.md#1-修订历史)).

### 7.4 Consistency between the declared tools and the dispatch table

`Manifest.tools` and `protocol._tools` are two independent tables, and one `@node.tool` writes both. An implementation **MUST NOT** write only one of them — writing only the manifest yields "announced but not callable", and writing only the dispatch table yields "callable but nobody knows about it".

## 8. Timeouts, connection fallback and lifecycle

### 8.1 Timeout semantics

| Item | Provision |
|---|---|
| Default | `5.0` seconds ([README.md §5.6](https://github.com/hxh230802/MSP/blob/master/docs/spec/README.md#56-默认参数)) |
| Scope | Covers only the time spent **waiting for `tool_result`**; it **does not cover** the dialling and handshaking of `ensure_connected` |
| Timeout behaviour | deregister `pending_calls[reqid]` → `raise TimeoutError(f"call to {tool} timed out")` → `MSPNode.call` converts it to `ToolResult(error="call to <tool> timed out")` |
| A late result after a timeout | `_on_tool_result` cannot find the `reqid` → it is ignored silently; it **MUST NOT** be recorded as an error |
| Execution on the callee | a timeout does **not** notify the callee; the tool runs to completion as usual (its `tool_result` is then ignored). To really cancel a long task, use the cooperative cancellation of `msp/task` |

### 8.2 The `ensure_connected` fallback

`ensure_connected(peer_id)` is the single entry point for **every user API that needs a connection** (`call` / `fetch_manifest`). Behaviour:

| State | Behaviour |
|---|---|
| Already in `protocol.connections` | return at once (a lock-free fast path) |
| In `_neighbors` but not connected | take that peer's connection lock (`_connect_locks[peer_id]`), re-check under the lock, then dial + handshake |
| Not in `_neighbors` | `raise UnknownPeer(f"unknown node {peer_id}, cannot connect")` |
| In the cooldown period (`_unavailable[peer_id] > now`) | `raise PeerUnavailable(f"node {peer_id} suspected dead, cooling down")` |
| Dialling / handshake fails | record `_unavailable[peer_id] = now + connect_backoff` (`5.0` s by default) and raise `PeerUnavailable`; **the neighbour is not deleted** |
| Dialling succeeds | clear `_unavailable[peer_id]` |

**MUST** be satisfied:

1. every peer **MUST** have its own connection lock ("one connection lock per peer"), so that concurrent calls do not trigger duplicate connection attempts;
2. `connections` **MUST** be checked a second time under the lock, in case the peer was connected by someone else while the lock was being waited for;
3. a failed attempt that starts a cooldown **MUST NOT** delete the `_neighbors` entry — the declaration file is still there, and a hard delete would lose that peer for good ("separation of soft marking from hard cleanup" in [DESIGN.md](/design));
4. a node with `connect_policy="lazy"` **MUST** be connected on demand by this method, and **MUST NOT** expect the discovery layer to connect on its behalf.

### 8.3 Converting `RuntimeError("not connected to X")`

`MSPProtocol.call` checks on its very first step `if peer_id not in self.connections: raise RuntimeError(f"not connected to {peer_id}")`; `_send` raises the same `RuntimeError` when it cannot find a connection.

The `except (TimeoutError, ConnectionClosed, RuntimeError)` in `MSPNode.call` **MUST** turn it into `ToolResult(error="not connected to <peer>")`. The conversion **MUST NOT** swallow other exception types.

### 8.4 Cleanup when a connection is lost

`_handle_disconnect(peer_id, conn)` **MUST**:

1. if the `conn` passed in is no longer the registered one (an old connection evicted by deduplication), **MUST** return immediately, and **MUST NOT** wrongly delete the state of the new connection;
2. clean up `connections` / `peer_manifests` / `_last_seen`;
3. walk `pending_calls` and write `ToolResult(error="connection closed")` into the entries whose `holder[0] == peer_id`, then `event.set()` (**wake every waiter**);
4. close the connection **outside** the lock, so that `shutdown` does not block while holding it;
5. invoke the `_on_disconnected` callback.

## 10. Security considerations

1. **A tool call is the action that most needs authorization.** As designed in [security.md](../security.md#3-authorization), `req` authorization (which of my tools a peer may call) **MUST** be performed at the very front of `_dispatch`, and the tool-name list **MUST** match exactly (`True` = all). The reference implementation has **not yet** landed authorization (see §11 G6), so the current version **MUST NOT** be exposed to an untrusted network.
2. **`pattern` cannot serve as access control.** The routing contract says that a signal with an unregistered `pattern` degrades to core dispatch ([patterns.md §3.4](../patterns.md#34-behaviour-with-unregistered-patterns-must-be-observed)), so adding an unregistered `pattern` to a `tool_call` does **not** make the call fail — it is still executed. Access control **MUST** be based on `payload.tool`.
3. **Arguments are executed without validation.** The gap in §7.3 means `args` goes straight into `func(**args)`. A tool implementation **MUST** treat its arguments as untrusted input (path traversal, command injection, deserialisation).
4. **The `error` text leaks internal information.** F1–F6 and tool exceptions all use `str(e)` directly and may leak file paths, dependency versions or SQL fragments. An implementation facing untrusted peers **SHOULD** redact error information before replying, and keep the original text in the local log.
5. **The number of requests on one connection is unbounded.** `pending_calls` has no capacity limit, and a client **MAY** start any number of concurrent calls. An implementation facing untrusted peers **SHOULD** impose a per-peer cap on in-flight requests.
6. **Tools run outside a thread pool.** Every `tool_call` starts a `daemon` thread, with no concurrency cap. A flood of resource-hungry tools will exhaust thread resources — this is a rate-limiting responsibility at the deployment level, and the protocol layer **MUST NOT** be expected to intercept it.

## 11. Known gaps

| # | Gap | Impact | Basis |
|---|---|---|---|
| G1 | A `tool_call` / `tool_result` with an empty `reqid` is **ignored silently**, with no log line and no reply | The caller waits until it times out | the `if not reqid: return` in `_on_tool_call` / `_on_tool_result` |
| G2 | `-32601` / `-32602` / `-32603` are **not implemented** in the core protocol layer and are defined only in the JSON-RPC bridge | `payload.error` is plain text, so programmatic dispatch needs an adaptation layer | these three constants are used only in `mcp/jsonrpc.py` across the whole codebase |
| G3 | `inputSchema` **takes no part in runtime validation** | invalid arguments can only be stopped by the tool itself (§7.3) | `_run_tool` calls `func(**args)` directly |
| G4 | **Tool execution has no concurrency cap**: one thread per call | flood risk | `_on_tool_call` unconditionally calls `Thread(...).start()` |
| G5 | `_run_tool`'s `except Exception` is **too broad** and treats programming errors other than `KeyboardInterrupt` as tool business errors | an implementation bug is reported as a business failure and is hard to tell apart | `except Exception as e: payload = {..., "error": str(e)}` |
| G6 | Authorization (`req` / `rep` of `grants`) is **not implemented** | any connected peer can call every local tool | [security.md](../security.md) marks it 🟡; `Preset` has no `grants` field |
| G7 | **A `call` timeout does not notify the peer** | the peer keeps executing a tool nobody is waiting for; there is no cancellation path | `MSPProtocol.call` only `pop`s locally |
| G8 | **Synchronous blocking is the only form** | `node.call()` blocks the calling thread; there is no asynchronous API | `MSPProtocol.call` uses `event.wait` |
| G9 | ~~The timeout **does not cover the handshake**~~ ✅ **Fixed** | `receive()` during the handshake is now bounded by `handshake_timeout` (10 s by default); a peer that accepts and then sends no ACK has its connection closed on timeout | [base-protocol.md §9](../base-protocol.md#9-known-gaps) |
| G10 | `structuredContent` is **omitted** from a failure reply, whereas in a success reply, when the tool returned `None`, its value is `null` | the receiver needs to tell "the key is absent" from "the value is null" | the two `payload` construction branches of `_run_tool` |
